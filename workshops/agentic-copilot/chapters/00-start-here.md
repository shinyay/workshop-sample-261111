# はじめに

**GitHub Copilot：開発の任せ方とトークンエコノミー**

**講師と受講者が共に使い、終了後も自習で振り返る教材**

このワークショップでは、一つの申請ポータルを改修しながら、Copilotへ何を任せ、その回答や変更を採用してよいかをどう確かめるかを学びます。最後には、自分の開発で試せる改善手順をまとめます。
Copilotへ送る依頼文を**プロンプト**と呼びます。機能を多く使うことや、プロンプトを短くすること自体が目標ではありません。**必要な品質を保ちながら、調査・確認・やり直しも含めて、仕事の進め方を改善すること**が目標です。

調査や実装・確認の進め方をCopilotに任せても、目的、変更する範囲、結果を採用するかどうかは人が判断します。これまでの開発経験を使いながら、AIへ必要な情報を渡し、その結果を確かめる練習をします。
本編へ進む前に、この「はじめに」で学べること、身に付ける力、共通シナリオ、各章のつながりを確認します。「はじめに」は、本編の第1章〜第8章とは別の導入章です。

### この教材の使い方

GitHubやCopilotを使い慣れていることは前提にしません。**GitHub**はコードや変更履歴を共有し、開発を進めるためのサービスです。**GitHub Copilot**は、コードの説明や変更案の作成などを支援するAIです。この教材では、コードを編集するアプリである**VS Code**からCopilotを使います。

各節では、最初にゴールを確かめ、解説を読んでから演習に取り組み、結果を確認します。迷ったときはヒントを開き、確認後に自分の言葉で説明し直してください。
Copilotへの依頼例は出発点です。自分が使うコード、参照する資料、確認方法に合わせて使ってください。例をすべてそのまま送ることが目的ではありません。

本編は各章を複数の節に分け、1節を1ページで表示します。「1-1」は第1章の第1節、「2-1」は第2章の第1節です。節番号は各章で1から始めます。「はじめに」と補足には番号を付けません。

<summary>自習を始めるときのヒント</summary>

初回は順に読み、各節の「結果を確かめる」に答えてください。再読時は、目次から必要な節へ戻れます。

講師が不在でも、読解や判断を考える学習は進められます。ただし、解説を読んだだけの作業を「自分で実行・測定した」と記録したり、自分の読み直しを「他の人にも確認してもらった」と記録したりはしません。

## はじめに｜学べることと身に付ける力

目指すのは、特定の依頼文を暗記することではなく、自分の仕事に合わせてCopilotの使い方を選べることです。
本編では次の5つの力を学びます。計画や設定ファイル、コードの変更内容、確認結果を残し、それらを使って自分の判断を説明します。

| 学べること（主な章） | 身に付ける力 | 成果・確認の例 |
| --- | --- | --- |
| 根拠に基づく調査と計画（第1章・第2章） | 事実と仮説を分け、何を、なぜ、どこまで変えるかを説明する | 現状の根拠、受け入れ条件、変更箇所と確認方法を結んだ計画 |
| 指示・役割・手順の使い分け（第3章・第4章） | 今回だけの依頼、繰り返し守る規則、担当の役割、再利用する手順を分けて任せる | 指示ファイル、レビューを担当するAgent、検証手順をまとめたSkillと、それらを使った記録 |
| 実装と品質判断（第5章・第6章） | 小さく変更して確かめ、失敗の原因やAIの指摘を調べ、人が判断すべき場面を見極める | 変更したコードとその確認結果、指摘を採用するかどうかの理由、人が作業を確認する方法 |
| 配備・自動化の定義と引き継ぎ（第7章） | アプリを動かす環境や自動確認の手順を設定ファイルで表し、内容と残る課題を説明する | 環境を定義するTerraformと自動処理を定義するAzure Pipelinesの案、未設定・未確認事項 |
| トークンエコノミーの評価と改善（第8章） | 条件と必要な品質を揃えて負担を比較し、採用する理由と次に試す手順を決める | 比較結果と言える範囲、開始・確認・停止・再開の方法をまとめた改善設計シート |

各章では、作成したメモ、設定ファイル、コードの変更内容、確認結果を使って、自分の判断を説明します。読んで分かったことと、自分で作成・実装・実行・測定したことは分け、行っていない作業は「未実施」と記録してください。

### 全編で扱う二つの主題

**Agentic（エージェンティック）な活用**は、目的と許可した範囲の中で、Copilotに必要な調査や作業の進め方を任せることです。例えば「この関数を説明して」だけでなく、「変更の影響を調べ、足りない情報があれば報告して」と依頼します。何でも任せるのではなく、渡す情報、使える道具、作業を止めて人に相談する条件を決めます。

**トークンエコノミー**は、必要な品質に到達するまでのAI利用量と、調査・確認・やり直しにかかる負担を考えることです。トークンは、AIが文章やコードを処理するときの単位です。短い依頼や少ない利用量だけを成功とせず、品質、時間、人が追加で行った判断や説明、取得できた利用量を分けて評価します。

**学習前の問い:** 自分の開発でCopilotに任せたい作業と、その結果を採用してよいか迷いそうな場面を一つ思い浮かべてください。実顧客の情報や秘密情報は持ち込まず、一般化した作業として考えます。

<details>
<summary>ヒント：機能名ではなく、仕事の場面から考える</summary>

「Agentを使いたい」から始める代わりに、「既存APIの変更影響を調べたい」「レビューの指摘が妥当か判断したい」などの場面を選びます。
何を任せたいか、何を根拠に結果を採用したいかを考えると、上の到達目標と自分の仕事を結び付けられます。

</details>

## はじめに｜共通シナリオの全体像

題材は、Pythonで作られた架空の社内申請ポータルです。Webアプリの処理にFlask、データの保存にSQLite、HTML画面の組み立てにJinja2を使っています。
開始時には、申請の一覧・詳細、新規申請、承認・差し戻しの機能があります。一覧画面の上部には、全申請の総数と状態別の件数（全体集計）が表示されます。他のプログラムから申請情報を読み取る窓口であるAPIもあり、データをJSONという形式で返します。
参加者は、この既存アプリを改修する開発担当として、次の変更依頼に取り組みます。

> 申請が増え、一覧から処理すべきものを探しにくくなっています。
> 担当部署と申請状態で絞り込めるようにしてください。
> 既存機能を維持し、画面とAPIの両方で正しく動作することを確認してください。

### 何を作り、何を守るか

追加するのは、一覧画面と一覧APIの絞り込みです。例えば、開発部の確認待ちの申請を探すときは、部署と状態の両方を指定します。

```text
GET /api/requests?department=engineering&status=pending
```

検索条件の組み合わせ、該当する申請がない場合、不正な入力、結果件数と全体集計の違いまで考えます。既存の作成・詳細・状態変更などを壊さず、画面とAPIの結果を揃えることが必要です。
完成したかどうかを判断する条件を、**受け入れ条件**（Acceptance Criteria、AC）と呼びます。この「はじめに」の「共通シナリオと受け入れ条件」で確認し、本編を通じて使います。開始版には絞り込みがまだ実装されていません。

### なぜ同じ改修を全編で使うのか

第2章で整理した要件と計画を、第5章の実装と第6章の品質判断で使います。第3章・第4章で準備した指示・役割・手順も、本編へ引き継いで使います。
こうすることで、調査、任せ方、実装、確認を別々の操作として終わらせず、前の工程の成果が次の判断にどう役立つかを学びます。
最後は、第7章でアプリの環境や自動処理を設定ファイルにまとめ、まだ確かめていないことも次の担当へ渡します。第8章では、自分の開発に再利用する手順をまとめます。完成コードだけが成果ではありません。

本編の改修と、指示の比較・欠陥検出などの独立演習は分けます。別教材で得たコードや成功結果をそのまま本編へ流用せず、学んだ任せ方や判断方法を本編の対象で確かめます。

### 今回扱わないこと

実際の利用者を認証する機能、通知、データベース（DB）の置き換え、一覧のページ分割、本番運用への対応、外部公開は追加しません。実データや秘密情報も使いません。
クラウドサービスのAzureと、開発を支援するAzure DevOpsは、設定ファイルの作成・レビューまでを扱います。実環境への接続や設定の反映、自動処理の実行は行いません。アプリを改修する学習と、本番運用できることの証明を分けます。

### 本編と独立演習を混ぜない

第3章のA/B/C、第4章のR0/R1・V0/V1は、条件を変えて比べるときの呼び名です。A/B/Cは指示の内容、R0/R1はレビュー担当の有無、V0/V1は検証手順の有無を変えて比べます。詳しくはその章で説明します。これらの比較、第6章の検索条件の誤り、第8章の件数の誤りを調べる演習では、本編とは別に用意した教材を使います。
第3章・第4章から本編へ戻すのは採用した指示・定義と記録だけです。別教材のコード・DB・成功結果を本編へ持ち込みません。

引き継ぐのは、次の判断に必要な情報です。例えば「この指示を使う理由」と「実際に使って確かめた結果」を渡します。計画や指示を作っただけで、まだ行っていない実装や動作確認まで終わったことにはしません。

**自分で説明する:** 第4章でレビュー担当を作ることと、第6章でレビューすることは、何が違うでしょうか。

<details>
<summary>解説：担当を作る学習と、指摘を判断する学習</summary>

第4章では、レビュー担当へ何を渡し、何を報告させ、どの道具を使わせるかを決め、実際に使って確かめます。第6章では、その担当が出した指摘を調べ、追加の確認や修正が必要かを人が判断します。
使えるレビュー担当があることは、今回の変更をレビュー済みという意味ではありません。

</details>

### 実習の条件をそろえる

ここでいう**モデル**は、Copilotが回答やコードを生成する際に使うAIです。比較の途中で別のモデルへ変えると、何によって結果が変わったか分からなくなるため、一つに揃えます。

| 項目 | このワークショップの条件 |
| --- | --- |
| VS Code | 実施時点の最新の安定版（Stable）。先行版のInsidersは使いません |
| Copilot機能 | 試験提供中のPreview／Experimental機能は使いません。VS Codeが安定版でも、画面や設定に「Preview」「Experimental」と表示される機能があるため、個別に確認します。迷う場合は講師に確認します |
| モデル | 講師が利用条件を確認して指定した一つを使い、比較中は変更しません。モデルを選ぶ画面に、推論の度合い（Effort Level）や一度に扱える情報の上限（Context Size）などの設定が表示される場合は、それらも揃えます |
| 実行方式 | Copilotのセッションの種類（実行方式）も講師の指定に揃え、比較中は変えません。VS Codeでは、チャットの入力欄の下に表示されます（例：Local）。種類によって、使われる指示やAgent・Skillが変わることがあります。新しい会話を始めるたびに、実行方式とモデルが指定どおりかを確かめます |
| 自動選択 | モデルの自動選択（Auto／HydraFusion）は解説だけで、演習では使いません |
| アプリ | 指定された開始版の申請ポータルと架空データを使い、本編と独立演習のコピーを分けます |
| クラウド | Azure・Azure DevOpsの実環境は使いません |
| ヒント | 必要なときに開きます。利用自体は減点せず、支援と自力の範囲を区別します |
| 記録 | 品質・時間・人が追加で行った判断や操作を記録します。AI利用量はPreview機能を使わずに取得できる範囲に限ります |

Copilotを使う通信と、アプリをローカルで動かすことは別です。利用条件を満たさない場合、別モデルやPreview機能で無断に代替せず、講師へ確認してください。

VS Codeでまだ信頼していない作業フォルダーを開くと、信頼を確認する画面や、制限モード（Restricted Mode）の案内が表示されることがあります。制限モードではCopilotのAI機能を使えないため、講師が指定した作業コピーであることを確かめてから信頼します。親フォルダーを信頼済みの場合など、確認が出ない環境もあります。確認画面の有無ではなく、開いたフォルダーと、その信頼の状態を確かめてください。
ウィンドウを開いた直後は、画面下端のステータスバーに拡張機能の起動中の表示（Activating Extensions...）が出ます。この表示が消えてから依頼してください。起動中に依頼すると、コマンドの実行結果がCopilotに届かないことがあります。
普段使っている個人の指示・Agent・Skill、所属する組織がGitHubで用意した指示・Agent、MCPサーバー（Copilotから外部の道具を使うための仕組み）が、演習の画面に表示されたり、結果に影響したりすることがあります。組織のAgentは、Agentを選ぶ一覧に並ぶことがあります。組織の指示は設定によって依頼へ自動で加わるため、講師の案内に従って確かめます。講師が指定していないものは使わず、MCPサーバーの起動を勧める表示が出ても起動しません。外せないものがある場合は講師に相談し、記録の条件に書きます。

比較用のA/B/CやR0/R1・V0/V1は、本編とは別の指定コピーを使います。

### コードの場所と変更を見分ける

Gitは、ファイルの変更履歴を管理する道具です。GitHubと一緒に使いますが、同じものではありません。以降の記録で使う言葉を、先に確認しましょう。

| 言葉 | 記録で確かめたいこと |
| --- | --- |
| リポジトリ | コードや資料と、その変更履歴をまとめた保管場所。教材用と実習アプリ用を区別する |
| 作業コピー | 自分が編集・実行するフォルダー。本編用か、比較用かを確認する |
| コミット（commit） | 変更をGitの履歴に記録したもの。コミットIDで、その時点のコードを識別できる |
| 差分 | 二つの状態を比べた変更内容。追加・削除・書き換えを確認する |
| 未コミット差分 | 作業コピーで加えた、まだコミットしていない変更。新しく作ったファイルも確認する |
| 対象版 | 今回調べたり実行したりするコードの状態。コミットIDに加え、未コミットの変更も記録する |
| 開始版 | 講師・準備担当者が配布する、絞り込みを実装する前の実習アプリ。本編はこの版から始める |
| 参照版 | この教材の説明の基にした実習アプリの固定版（コミット`1a411cd`）。手元の実習アプリと違う場合は、手元のファイルで確かめる |
| 講師用の完成例 | 講師が確認用に用意した絞り込みの実装例。自分の実装の合否基準にはしない |
| 演習版 | 開始版から、自分たちが絞り込みを実装していく本編の版。画面の段階名などで、開始版・完成例と区別する |

例えば、ターミナルで`git log -1 --oneline`を実行するとコミットIDを、`git status`を実行すると未コミットの変更や新しいファイルを確認できます。
同じフォルダー名でも、中身が変わっていれば別の確認対象です。講師が案内する版と自分の変更を区別し、版が分からなければそのまま演習を進めず確認してください。

### 記録は一つを育てる

次の欄を自分のメモに用意し、各章で必要な行だけを追記してください。「根拠」には、判断の裏付けとなるファイル、説明、実行結果などを書きます。会話全文を毎回コピーする必要はありません。

```text
章・節／演習名／条件（例：第3章-A）：
対象版／作業コピー／未コミット差分：
データと実行対象：
目的・AC・対象外：
参照した根拠／実行した確認：
結果：成功・失敗・未実施・未確認
人が判断したこと／受けたヒント：
残課題／次に渡すもの：
```

### 再開する前に

どのコピー、DB、会話、指示・定義を使っていたかを見直します。別チャットを開いてもコードやDBは初期化されません。
自分の変更は保持してください。別の準備済みコピーで続ける場合は提供された部分と自分の成果を分けます。未提供の復旧版を推測して取得・適用しません。

**自分で説明する:** テストのファイルを見つけた、テストを実行した、テストが成功した、の三つはどう違いますか。

<summary>解説：証拠の種類を区別する</summary>

テストファイルを読むと、何をどの結果と比べる予定なのかが分かります。しかし、読んだだけでは実際に動いたかは分かりません。テストを起動し、必要なテストが実行対象として選ばれ、結果が出た記録を確認します。成功と判断するには、対象のコードに対して必要な確認が実行され、期待する結果になったことが必要です。
未取得の利用量は「未取得」と書きます。0や推定の削減率で埋めたり、AIへ渡す情報の枠の使用率から消費量へ換算したりしません。

## はじめに｜共通シナリオと受け入れ条件

ここでは、概要で示した変更依頼の具体的な品質条件を確認します。第2章ではアプリ全体の調査と要件整理に使い、第5章以降は実装・検証・レビューへ引き継ぎます。まだ実装は始めません。

一覧画面は`/requests`、一覧APIは`GET /api/requests`です。APIの外形は`{"items": [...], "count": N}`で、`N`は返した一覧の実数を表します。これは外形の説明であり、そのまま送受信するJSONではありません。
部署のコードは`engineering`、`sales`、`corporate`、`design`、状態は`pending`、`approved`、`rejected`です。表示名はそれぞれ開発部・営業部・管理部・デザイン部、確認待ち・承認済み・差し戻しです。

URLの`?`以降で渡す`department=engineering`のような指定を、クエリパラメーターと呼びます。`department`が項目名（キー）、`engineering`が値です。表にある`400`は、不正な入力としてリクエストを受け付けなかったことを示すHTTPステータスです。正しい検索で該当する申請が0件だった場合とは区別します。

### 全員で揃える品質条件

次の条件はヒントではありません。実装前に全員が参照し、実装・検証・レビューで共通に使う判断基準です。
教材を画面に表示していても、その本文が自動でCopilotへ渡るわけではありません。ACを使う依頼では、AC番号だけでなく、対象のACの条件と期待する振る舞いを依頼に書き添えるか、作業コピーに置いたメモを示してください。メモを作業コピーに置く場合は、アプリの変更と一緒にコミットしないよう、`git status`で確かめます。
折りたたんだヒントも、本文のファイルを参照できる環境ではCopilotが読める場合があります。教材へのアクセスやヒントの引用は、比較条件として記録してください。
「ID集合」は結果に含まれる申請IDの集まり、「負のテスト」は不正な入力などを正しく拒否するかの確認です。「回帰テスト」は、今回の変更で既存機能が壊れていないかを確かめるテストです。

| ID | 条件 | 期待する振る舞い | 主な確認根拠 |
| --- | --- | --- | --- |
| AC-01 | 条件なし、または検索値が空文字 | 有効な絞り込み条件がなければ全件。片方だけ空なら、もう片方の条件は有効 | 未指定・空文字・混在のテスト |
| AC-02 | 部署だけ指定 | 指定部署の申請だけを返す | ID集合と部署値の照合 |
| AC-03 | 状態だけ指定 | 指定状態の申請だけを返す | ID集合と状態値の照合 |
| AC-04 | 部署と状態を指定 | 両方を満たす申請だけを返す | 片方だけ一致するデータを含む組み合わせテスト |
| AC-05 | 有効な条件だが該当なし | 正常な0件として扱う。APIは空の`items`と`count: 0`、画面は説明と解除手段を示す | APIと空状態の画面 |
| AC-06 | 不正な値、検索キーの重複、未対応の検索キー | 400と説明を返す。無視して全件や正常な0件を返さない | 負のテスト、HTTPステータス、画面・JSONの説明 |
| AC-07 | 画面とAPIへ同じ検索条件を渡す | 同じ取得処理に基づく同じ対象を表示・返却する | コードの参照関係と結果のID集合 |
| AC-08 | 一覧を絞り込む | APIの`count`と画面の結果件数は一覧の実数。全申請の総数・状態別集計は絞り込みで変えない | 絞り込み前後の件数と全体集計 |
| AC-09 | 条件指定後に表示・解除する | 選択条件を画面で確認でき、解除で条件なしの一覧へ戻る | 実画面の操作とリクエスト |
| AC-10 | 既存操作と表示 | 詳細、作成、状態変更、入力検証、既存の並び順・表示・配色を維持する。処理済み申請は再変更しない | 既存回帰テストと代表的な画面操作 |
| AC-11 | 変更全体 | SQLの値を文字列連結せず、パラメーター化を維持。実データ・秘密情報・外部公開・不要な依存を追加しない | 差分、既存の検証、実行設定 |

同じ値でも検索キーの重複はエラーです。例えば部署の指定を二つ渡した場合、両方が同じ部署でも、片方が空でもエラーにします。AC-06の400と説明は、画面とAPIのどちらへの要求にも当てはまります。配色用の`scoutTheme`は、既存の仕様（第2章で、実習アプリのREADMEとコードから確かめます）に従って扱い、未知の検索キーとして拒否しません。AC-10の配色の維持には、絞り込みのフォーム送信や条件の解除の後も、指定された配色が保たれることを含みます。
空白の削除や大文字・小文字の補正は行いません。部署・状態の値は、上で示したコードと完全に一致する場合だけ有効です。`Pending`のように大文字を含む値や、前後に空白がある値は、AC-06の不正な値として400にします。空白だけの値も空文字（AC-01）ではないため、同じく400です。
開始版は絞り込み未実装で、有効な検索キーも400です。追加後にその開始版限定の期待を更新することと、不正入力の確認を削除することは違います。
