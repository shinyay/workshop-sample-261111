## 3-1｜指示に残す情報を選ぶ

**この節のゴール:** 今回だけの依頼と、繰り返し使う規則を分け、情報の置き場所を選べることです。

第2章の調査・実装計画には、今後も守りたい規則と、今回だけの要求が含まれています。例えば「既存の配色を保つ」は別の改修でも必要ですが、「部署と状態で絞り込む」は今回の要求です。
繰り返し使う規則をファイルに残すと、依頼のたびに書き直さずに済みます。幅広い作業に使う**共通指示**と、テスト編集など特定の作業に使う**条件付き指示**を分けましょう。

### 一度きりの要求と継続的な規則

| 情報 | 主な置き場所 | 理由 |
| --- | --- | --- |
| 確認済みの構成、テストの実行方法、今後も保つ仕様 | AGENTS.md等の共通指示 | 別の変更でも必要になる |
| 今回の絞り込みの目的・AC・対象外 | 今回の依頼・実装計画 | 次の仕事まで古い要求を残さない |
| テスト編集時に必要な規則 | 条件付き指示 | 無関係な作業へ毎回渡さない |
| レビュー担当の責任と道具 | 第4章のCustom Agent | 役割ごとに任せ方を再利用する |
| 検証の順序、失敗の切り分け、報告 | 第4章のSkill | 必要な作業で手順を再利用する |

この教材では、繰り返し使う指示を伝える仕組みを**Custom Instructions**（カスタム指示）と呼びます。AGENTS.mdもプロジェクトの指示を記す形式の一つです。
この演習では、共通指示として実習アプリに既にあるAGENTS.mdを使い、条件付き指示として`.github/instructions/*.instructions.md`を作ります。`.github/copilot-instructions.md`もCopilot向けの共通指示の置き場所ですが、今回は作らず、AGENTS.mdとの違いを知っておくだけにします。同じ規則をすべてへ複製しません。
同じ規則を複数の場所に置く場合も、更新の基準にするファイル、つまり**正本**を決めておきます。
CLAUDE.mdはClaude Codeとの比較説明に限ります。CopilotでClaudeモデルを使うことと、Claude Codeで作業することは別です。今回はCopilotで実践します。
ただし、使用する環境によっては、CopilotもCLAUDE.mdをプロジェクトの指示として読み込みます。比較用コピーや上位フォルダーに意図しない指示ファイルがないかは、3-2で確かめます。

### 演習

1. 調査・実装計画から、継続的な規則、今回だけの要求、特定の作業だけに使う規則（条件付き指示の候補）、未確認の仮説を一つずつ選んでください。
2. 各項目について、置き場所と、その情報が必要になる作業を示してください。
3. 未確認の仮説は、規則にする前に何を調べる必要があるかを書いてください。

### 結果を確かめる

それぞれの項目で「なぜそこへ置くか」と、「その規則や要求が正しいことを何で確かめるか（例：AC、既存の仕様、テスト）」を説明してください。確かめていない設計上の意図を今後も守る規則にしていないか、今回の絞り込み要求を別の仕事にも当てはめていないかを確認します。

<details>
<summary>ヒント1：別の変更でも必要か</summary>

「次の仕事が絞り込み以外でも、この文章を読んでほしいか」と問い直します。今回だけの要求を共通指示に残すと、次の仕事でも古い目的に沿って作業してしまうことがあります。

</details>

<details>
<summary>ヒント2：根拠のない規則を除く</summary>

確認コマンドを書くときは、必要な設定・ライブラリ・実行対象が存在するかを確かめます。保つべき条件はACや既存仕様で裏付けます。まだ調べていないパスや、AIが推測した設計上の意図を、今後も守る規則にしてはいけません。

</details>

<details>
<summary>解説：ファイルを増やす前に正本を決める</summary>

規則が重複すると、片方だけ更新されて矛盾することがあります。役割が重なるAGENTS.mdとCopilot向け指示についても、何を正本にするかを決めます。
指示文は品質判断を助けますが、テスト、書き方や規約を機械的に調べるリンター、権限設定の代わりにはなりません。

</details>

## 3-2｜Aの観察から、改善したい指示を考える

**この節のゴール:** 既存の指示で作業した結果から、改善すべき情報の不足を見つけられることです。

一覧の入力を検査する処理を小さく整理する**リファクタリング**で、指示の違いを比べます。コードの構造を整理しても、画面やAPIが受け付ける入力と返す結果、つまり**外から見える動作**（公開挙動）は変えません。既存の動作を壊していないかを調べる回帰確認も行います。本編の絞り込みはまだ実装しません。
まず既存のAGENTS.mdを使う条件Aを観察し、その結果からBとCの指示を考えます。

| 条件 | 共通指示 | 条件付き指示 | 開始コード・データ |
| --- | --- | --- | --- |
| A | 既存のAGENTS.md | 今回追加するものはなし | 同じ開始版 |
| B | 改善したAGENTS.md | 今回追加するものはなし | Aの結果ではなく同じ開始版 |
| C | Bと同じ改善版 | 設計したものを追加 | Bの結果ではなく同じ開始版 |

全条件へ、同じ目的・品質・対象外・確認条件を渡します。Aだけを不利にするために、安全条件や必要な情報を取り除きません。
上位フォルダー・ユーザー・組織に設定された指示、開いているファイル、会話、モデル、ツール、データも確認します。フォルダーを分けただけで、他の指示や情報が入らなくなるとは限りません。

### 演習

1. 第3章用の比較コピーAを開き、開始版、データ、既存指示、確認方法を記録してください。第1・2章の読取専用の設定のまま依頼せず、講師の案内に従って編集・確認コマンドを使える担当へ切り替えます。例えばVS Code 1.145のLocalではAskからAgentへ切り替え、Configure Toolsで許可するツールを確かめます。モデル・実行方式は変えず、A・B・Cで同じ設定を使ってください。
2. 次の共通依頼を使って小さなリファクタリングを行い、必要な品質確認を実行してください。
3. Copilotが何を調べたか、人がどの説明を補ったか、どこを誤解したか、何を確認し忘れたかを記録してください。指示を変えると改善できそうな点と、指示以外の問題を分けます。

### A・B・Cで共通に使う依頼

```text
指定した比較用開始版で、一覧のクエリパラメーターを検査する処理を小さく整理してください。既存の動作を壊していないかも確認してください。
画面やAPIが受け付ける入力と返す結果、日本語の説明、並び順、配色、重複キー・未対応キーの扱いを維持してください。
部署・状態の検索はまだ実装せず、無関係な抽象化・依存追加はしないでください。
実習アプリで指定された共通の確認方法を使い、変更理由、実行結果、未確認事項を報告してください。
```

**依頼する前に確かめること**

開始版と確認方法は、依頼する前に実習資料とアプリのREADMEで確かめてください。Copilotに存在しないパスや手順を補わせません。確かめた対象版と確認コマンドは依頼の後ろに書き添え、A・B・Cで同じ文面にします。確認はそのコマンドだけにすることも書き添えます。BやCの指示に確認の進め方（変更に対応するテストから先に実行するなど）を書いた場合も、比較で使う確認は次の4つのコマンドだけです。その進め方の効果は、この比較では判断しません。アプリのREADMEにある「実ブラウザーでの確認（任意）」はアプリの起動を伴うため、この比較では使いません。
BとCでは指示ファイルを変えるため、未コミットの変更が残ることがあります。対象版は「アプリのコードとテストは開始版のまま」のように、三つの条件のどれでも正しい書き方にします。
成功したテストの件数だけで比較せず、全条件に共通の入力と期待結果を決めます。各条件が追加したテストの数が違っても、画面やAPIが同じ仕様を満たしているかを確かめられるようにしてください。

**全条件で使う確認コマンド**

```text
uv run --locked pytest --ignore=tests/test_reference_patch.py -q
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy
```

`uv`はPythonの実行環境や依存関係を管理する道具です。ここでは、依存関係の版を記録したロックファイルに従って確認コマンドを動かします。
`pytest`はテスト、`ruff check`はコードの規約、`ruff format --check`は書式、`mypy`は型の整合性を確かめます。コマンドが終了したかだけでなく、対象と結果も記録してください。
最初のコマンドは、`tests/test_reference_patch.py`にある2件のテストだけを外しています。このファイルは、講師用の完成例パッチを適用し、元に戻せるかを調べる配布物の確認用テストです。開始版の準備時には、これを含む全件を実行します。各自でコードを整理するA/B/Cでは、全条件で同じように外します。アプリの回帰確認と追加テストは残し、確認用のファイル自体は削除しません。
パスの区切りには`/`を使っています。WindowsのPowerShellでも、CodespacesなどのBashでも、同じ意味で実行できます。Bashで`\`を使うと、除外したいファイルを指定できないまま確認が進むことがあります。

**初めての編集と実行を許可する**

この節で初めて、Copilotにファイルの変更とコマンドの実行を任せます。
コマンドの実行前に許可を求められたら、依頼した確認コマンドか、実行する場所が比較用コピーかを読んでから許可します。依頼していない確認のためのコマンド（画面を確かめるためのアプリの起動や、対象を絞ったテストの実行など）は、A・B・Cのどれでも許可せず、その事実を記録します。読み取りだけのコマンド（`git status`など）を許可するかどうかも、三つの条件で揃えます。許可の画面に出る危険度の表示は自動で付く目安で、同じ種類のコマンドでも変わることがあります。表示の色ではなくコマンドそのものを読み、長いコマンドは展開して全文を確かめます。
変更を残すか取り消すかを選ぶ表示が出たら、差分と確認結果を見てから残します。許可した回数は、人が行った操作として記録します。

<details>
<summary>例：VS Code 1.145のLocalでの表示</summary>

試走で使ったVS Code 1.145のLocal（入力欄の下の権限の設定は「Default permissions」）では、次のように動きました。表示と操作は版や設定で変わるため、講師の案内を優先してください。

- ファイルの編集は、許可を求めずに作業コピーへ書き込まれます。その後、変更を残す（Keep）か取り消す（Undo）かを選ぶ表示が出ます。
- AgentやSkillの定義ファイルなど、Copilotの動きに関わるファイルは、書き込む前に許可を求められることがあります（Allow edits to sensitive files?）。Allow Onceを選び、書き込まれた差分を読みます。
- ターミナルのコマンドは、実行前に1件ずつ許可を求められます。複数のコマンドが並んでいても、1件ずつ読んで判断します。
- 許可のボタンの横の▼から自動承認を有効にすると、比較の条件が変わるため使いません。

</details>

確認方法を途中で修正した場合は、それまでの試行を予備試行として残し、修正した共通条件で比較をやり直します。条件の異なる結果から指示の効果を断定しません。

### 結果を確かめる

変更後のコードに対する結果を使い、外から見える動作が変わっていないことを確認してください。そのうえで、改善したい指示を一つ、実際に起きたことと結び付けて説明します。Aが問題なく進んだ場合も有効な結果です。改善点を作るために失敗を演出しません。

<details>
<summary>観察のヒント</summary>

どこを探したか、何を取り違えたか、確認を省いたか、人が何を追加したかを見ます。差がなくても構いません。Aを失敗させることが目的ではありません。

</details>

**自分で説明する:** Aのコード変更をそのままBへ渡すと、指示だけの比較にならないのはなぜでしょうか。

## 3-3｜共通指示と条件付き指示を設計する

**この節のゴール:** 根拠のある共通指示と、対象を限定した指示を書き分けられることです。

規則には、「何を扱うときに」「何をするか」「なぜ必要か」「どう確かめるか」を書きます。設計書の全文ではなく、コードだけでは気付きにくく、誤解するとやり直しにつながる条件を選びます。

### 演習

1. 調査・実装計画とAの記録から、今後も守る必要がある規則を選んでください。
2. AGENTS.mdを改善し、規則ごとに根拠と期待する行動を説明してください。BとCには同じ改善版を使います。
3. テスト作業だけに必要な規則を、C用の条件付き指示へ分けてください。対象パスは手元の実習アプリの配置に合わせます。

**Copilotへの依頼例**

```text
調査・実装計画の確認済みの事実と、Aで観察した不足から、AGENTS.mdの改善案を作ってください。
今回だけの要求や未確認の仮説は共通指示へ入れないでください。
規則ごとに根拠、適用する場面、期待する行動、確認方法を示してください。
テストだけに必要な規則は、条件付き指示の候補として分けてください。
```

![共通指示には繰り返し使う規則、条件付き指示には特定の作業の規則、今回の依頼には変更目的を置く。見つかること、今回使われること、行動でも守られることを分けて確かめる。](assets/instructions.svg)

図の三つは「どれが強いか」の順位ではなく、情報を置く目的の違いです。

### 書式の抜粋：対象限定の規則

次は`.github/instructions/tests.instructions.md`に書く規則の例です。冒頭の`applyTo`は、この指示を使うファイルの範囲を指定します。実際のテスト配置に合わせてください。`description`には、どの作業で使う指示かを短く書きます。環境によっては、この説明を手掛かりに指示が読み込まれます。
VS Codeの公式資料では、Copilotが`applyTo`に合うファイルを作成・変更するときに、この指示が自動で加わると説明されています。対象のファイルを読むだけの作業では使われない場合があるため、3-4で実際の使われ方を確かめます。
「テストの収集」は、テストツールが実行するテストを探し出す段階です。そこで失敗した状態と、アプリを動かして仕様との不一致が見つかった状態を分けます。

```markdown
---
description: "テストを作成・変更するときに使う規則"
applyTo: "tests/**/*.py"
---
期待する結果はACと既知のデータから決めてください。変更対象のコードと同じ条件式だけで答えを計算しないでください。
テストの起動・収集の失敗と、対象の仕様不一致を区別してください。
```

共通指示には、構成を調べるためのファイル、既存の確認手段、画面やAPIで保つ仕様を選びます。まだ提供されていないコマンドを、使えるかのように追加しません。
例の規則をすべてのプロジェクトで無条件に使うのではなく、既存の規約・仕組みとの重複や矛盾も確認してください。

### 結果を確かめる

AGENTS.mdと条件付き指示を見比べ、今回だけの要求、未確認の仮説、重複・矛盾する規則がないか確認してください。各規則について、適用したい作業と、守られたことを確かめる方法を説明します。

<details>
<summary>ヒント：規則を一文ずつ点検する</summary>

「この規則が必要な場面は何か」「守ったことは何で分かるか」「すでにテストや既存指示で表現されていないか」を確かめます。
単に「高品質に」「ベストプラクティスで」と書くより、今回確かめた「変えてはいけない動作」と、その確認方法を書きます。

</details>

## 3-4｜指示が見つかり、使われ、守られたかを確かめる

**この節のゴール:** 指示が保存されていることと、今回の作業に適用され、守られたことを区別して確認できることです。

BとCを比べる前に、意図した作業で指示が使われるかを確認します。ファイルが見つかること、今回の作業に使われること、書いたとおりに行動することは別です。次の三つを分けて記録します。

| 確認する段階 | 確認する問い | 根拠にならないもの |
| --- | --- | --- |
| 発見：指示が見つかる | 使用するCopilotの環境で、指示ファイルが見つかるか | ファイルを保存しただけ |
| 適用：今回の作業で使われる | 今回扱うファイルや依頼に、その指示が使われたか | 別の作業で一度見つかったこと |
| 遵守：指示が守られる | 期待する行動と結果が確認できるか | AIの「従いました」という自己申告だけ |

指示を読み込む条件は、使用する環境と設定によって変わります。VS Codeなどが最新のStable版でも、そこで使うすべての機能が正式提供済みとは限りません。
条件付き指示の使われ方にも違いがあります。指示の全文が自動で加わる環境もあれば、対象のパターンとファイルの場所の一覧だけが渡され、Copilotが自分でそのファイルを読む環境もあります。どちらの形で使われたかを、表示される参照情報や操作の記録で確かめます。例えばVS Codeでは、Copilotが条件付き指示のファイルを読むと、その操作がチャットの記録に表示されます。操作の一覧が折りたたまれている場合は、開いて確かめます。対象外の作業でも、Copilotが対象のファイル（例：テスト）を自分で開くと、条件付き指示も読まれることがあります。読まれたことと、その作業に指示が必要だったことは分けて記録します。
サブフォルダーに置くAGENTS.mdやPreviewの診断機能を必須にせず、事前に確認した方法で記録を残します。確認できなかった段階は、未確認とします。

### 演習

1. 指示の読み込みを調べる専用のコピーで、指示の配置、対象パス、使用する環境に表示される参照情報を確かめてください。
2. 条件付き指示の対象になる作業と対象外の作業を一つずつ決め、それぞれ新しい会話で依頼してください。遵守は作業の結果でしか確かめられないため、対象の作業は小さな変更にします。発見・適用・遵守のどこまで確認できたかを記録してください。
3. 演習1で読み込みを調べるために加えた変更（診断の変更）を含まない独立コピーBとCを用意し、それぞれ新しい会話で3-2と同じ依頼・品質確認を実施してください。
4. A・B・Cで品質、探索、再説明、手戻り、確認できた利用量を記録してください。利用量は1-2と同じく案内された画面や記録で確かめ、取得できない値は「未取得」とします。

### BとCを独立して試す

A/B/Cそれぞれのコード・DB・会話を初期状態から分けます。適用の診断で変更したコピーを、そのまま本試行へ使いません。
AとBで共通指示の改訂、BとCで条件付き指示の追加を観察します。Cだけへ解法や解説を渡さないでください。

**Copilotへの依頼例（適用確認用）**

```text
これは適用確認用の依頼です。本試行とは別に扱います。
今回の対象：［対象のファイルと作業。例：tests/test_portal.pyにテストを1件追加して実行する］
今回の対象にどの指示が関係するか、確認できる根拠と確認できない点を示してください。
指示を読めたことと、行動で守れたことを分けてください。
設定や権限は変更せず、非Previewで確認できない場合は未確認としてください。
```

<details>
<summary>つまずいたとき：適用が分からない</summary>

対象パス、配置、参照、実行基盤、既存の設定を確認します。分からないからといってPreview設定やログ機能を有効にしません。
適用が未確認の試行から、指示の有無の効果を断定することも避けます。
ファイルを明示的に開かせた場合は、その方法も記録します。「指示を読んだ」ことは確認できますが、`applyTo`により自動的に適用されたこととは区別してください。
Copilotが適用を確かめるために、作業コピーの外（VS Codeの保存データやログなど）を読む許可を求めた場合は、許可せず、その段階を未確認とします。表示された参照情報と操作の記録は、自分で確かめます。

</details>

### 結果を確かめる

三つの条件が同じ開始コード・データから始まったことと、変更した指示の違いを説明してください。条件付き指示の対象外で行った作業や、適用が未確認の試行を、その指示の効果の証拠にしていないことも確認します。

## 3-5｜比較を読み、規則を本編へ渡す

**この節のゴール:** 指示を増やしたこと自体ではなく、品質と作業の負担を根拠に、どの規則を採用するか判断できることです。

A・B・Cの記録を、同じ品質を満たしたかどうかから読みます。そのうえで、指示の追加が再説明や手戻りを減らしたか、準備・保守の負担を増やしたかを考えましょう。
要約だけでなく、実行時の出力など、その判断の基になった**原記録**も使います。

### 演習

1. A・B・Cの原記録を、次の表の観点で整理してください。未取得の値や条件差も残します。予備試行の利用量は比較に含めず、別に記録します。
2. 規則ごとに、採用・対象限定・保留・不採用を決め、その根拠を書いてください。比較課題（動作を変えない整理）のために作った規則が、本編の要求（絞り込みの追加）と矛盾しないかも確かめます。例えば「説明文を変えない」という規則は、本編で説明文を変える作業と衝突します。
3. 採用した指示だけを本編へ配置し、本編の対象で適用を再確認してください。比較用コード・DBは移しません。

| 記録 | A | B | C |
| --- | --- | --- | --- |
| 開始状態・実際の指示やツール | 実施後に記入 | 実施後に記入 | 実施後に記入 |
| 指示の発見・適用・遵守 | 確認できた段階を記入 | 確認できた段階を記入 | 確認できた段階を記入 |
| 共通の品質確認 | 結果と版 | 結果と版 | 結果と版 |
| 探索・再説明・手戻り・ヒント | 観察した事実 | 観察した事実 | 観察した事実 |
| 利用量・時間と取得範囲 | 未取得は未取得 | 未取得は未取得 | 未取得は未取得 |

**比較から言える範囲**

- 指示が増えると、Copilotが読む量も増えることがあります。再説明や誤りが減ったのか、読む量が増えただけなのかを分けて考えます。
- 複数の規則を同時に変えた比較では、どの一文が結果を変えたかまでは分かりません。人が前の試行で学んだことや、処理済みの入力の再利用（キャッシュ）の状態も、完全には揃いません。

**原記録から消さないもの**

- 途中のパス不在や権限拒否：最後に成功していても残します。誤った作業コピーを参照していた場合は、許可を広げる前に現在地と実際のパスを確かめます。指示を書くだけで、この種の誤りがなくなるとは限りません。
- 依頼範囲を越えた変更、その取り消し、失敗後の再実行：最終差分が空でも、一度も変更しなかったとは限りません。最終報告だけでなく、観察できる操作と終了結果を照合します。
- 依頼外の操作と、許可・拒否の判断：依頼していない`git status`やアプリの起動などです。条件によって違うことがあるため、表の「探索・再説明・手戻り・ヒント」の欄に残します。
- 権限エラーの実際の内容と参照先：「権限がない」という要約だけで、**コンテンツの除外**（指定したファイルをCopilotの利用対象から外すための管理設定）が原因とは決めません。対応する機能や環境は公式資料と管理者の案内で確認します。除外が確認されたファイルは、別の手段で読み直しません。

### 別の開発へ持ち帰ること

本編へ戻すのは採用した指示と比較記録だけです。比較用コード、DB、診断変更は戻しません。本編の配置で適用も再確認します。
別プロジェクトへは、根拠を確認して規則を分類する方法を持ち帰ります。パス、コマンド、業務条件は調べ直します。

<details>
<summary>解説：差がなくても学習はできる</summary>

既存指示で十分だった可能性、適用が未確認だった可能性、比較が一回だけだった可能性を分けます。「改善版だから勝つはず」と結果を選び直しません。
採用・限定・保留・不採用の理由を示せることが重要です。

</details>

### 結果を確かめる

一つの規則について、根拠、置き場所、適用の証拠、結果から言える範囲を説明してください。差が出なかった場合や、適用を確認できなかった場合も、その理由と次の確認が記録されていれば学習に使えます。

**第4章へ渡すもの:** 調査・実装計画、採用した共通・条件付き指示、比較の根拠と未確認事項です。次は、担当の役割と再利用する手順を作ります。
