## 1-1｜回答だけでなく、仕事の進み方を見る

**この節のゴール:** Copilotに任せる調査と、人が決めることを分けて説明できるようになることです。

Copilotの回答を評価するときは、文章の分かりやすさだけでなく、何を調べ、どの根拠から結論を出したかを見ます。まず、同じ申請ポータルについて目的の異なる二つの依頼を読み比べましょう。この節では依頼を送らず、文面から考えます。実際に送って結果を観察するのは1-3です。アプリも編集しません。

Copilotがファイルを読んだり、検索したり、編集したりするための道具を**ツール**と呼びます。依頼の内容に合わせて、使ってよいツールと操作を決めます。

### 二つの依頼を比べる

**依頼1：指定した範囲を説明してもらう**

```text
このアプリの申請一覧は、どの画面・HTTP処理・データ取得処理で構成されていますか。
根拠となるファイルを示してください。
ファイル編集やコマンド実行はせず、読んだ事実と推測を分けて説明してください。
```

**依頼2：次の判断に必要な材料を集めてもらう**

```text
部署と申請状態の絞り込みを追加する前に、関連するファイルと既存テストを調べてください。
読取・検索だけを使い、ファイル編集、コマンド実行、依存の追加、DB更新はしないでください。
得た根拠に応じて必要な追加調査を行い、まだ実装しないでください。
変更が必要そうな場所と、人に確認すべき仕様を分けて示してください。
```

どちらの依頼でも、ファイルを読む・検索するツールを使う場合があります。「質問への回答ならツールを使わない」「作業を任せるなら必ず編集する」という区別ではありません。
依頼1は指定した範囲の理解、依頼2は次の判断に必要な追加調査と、不明点の報告を求めています。目的が違うため、二つの条件を揃えるA/B比較として利用量の優劣を判断するものでもありません。

### 演習

1. 二つの依頼で、Copilotが行ってよい操作と、行ってはいけない操作を抜き出してください。
2. 依頼2について、追加調査の進め方を任せている箇所と、人の判断を待つ箇所を挙げてください。
3. それぞれの依頼に回答が返ってきたと想定し、採用する前に確かめたい根拠を一つずつ書いてください。

### 結果を確かめる

「調査の進め方を任せること」と「仕様や変更範囲をCopilotだけで決めてよいこと」を区別できれば、この節の目的に沿っています。回答の説明を裏付けるファイルや処理が示されているか、まだ分からないことが書かれているかも確認してください。

<details>
<summary>ヒント1：動詞を分ける</summary>

「調べる」「整理する」「候補を挙げる」と、「仕様を決める」「編集を始める」「公開する」を分けます。目的に必要な追加調査は任せていますが、変更範囲の独断確定は任せていません。

</details>

<details>
<summary>ヒント2：参照と主張を一組にする</summary>

「一覧の処理はここにある」という主張なら、実在するファイル・関数と呼び出し元が対応しているかを見ます。「この仕様でよい」という主張なら、コードとは別に業務上の判断が必要かを考えます。

</details>

<details>
<summary>解説：観察できるものを根拠にする</summary>

確認するのは、AIモデルの非公開の内部思考ではありません。読んだファイル、検索結果、追加で調べた対象、分からないと報告した事項など、画面や記録から分かる行動です。
もっともらしい回答でも、参照が別版だったり、テストの存在を実行成功と説明したりしていれば修正が必要です。

</details>

## 1-2｜Copilotに渡る情報と、作業全体の利用量を分ける

**この節のゴール:** 入力の短さだけで効率を判断せず、品質と作業全体の負担を評価するための記録を選べることです。

Copilotが回答を作るときに扱う情報を**コンテキスト**（文脈）と呼びます。入力欄の文章だけでなく、使われる指示、会話の履歴、参照したファイル、ツールの結果なども関わります。
例えば「このエラーを直して」という短い依頼でも、関連ファイルを調べ、テスト結果を読み、修正を考えるための情報が必要です。一つの依頼に対してAIへの処理要求が複数回行われる場合もあります。最後の回答の長さだけでは、その作業全体で使った量は分かりません。

![AIへの一回の処理要求に渡す依頼・指示・履歴・参照・ツールの結果と、複数回の要求を通じた利用量の合計を分けて示す。](assets/context.svg)

図は情報の種類と集計範囲の違いです。面積や矢印の長さはトークン数・価格を表していません。

| 見ているもの | 分かること | その値だけでは分からないこと |
| --- | --- | --- |
| 入力欄の文字数 | 自分が入力した文章の長さ | 適用された指示や参照を含む全入力 |
| コンテキストの使用状況 | その処理要求で扱う情報が、利用可能な枠をどのくらい使っているか | 作業を通じて使った合計量・請求額 |
| 取得できた利用量 | 表示された単位・期間・対象の利用 | 未取得の内訳や別の試行の利用 |
| 所要時間 | 記録した開始から終了までの時間 | 人の待ち時間、やり直しの原因、品質 |
| ツールの回数 | 観察できた操作回数 | 各出力の情報量や、必要性・有効性 |

利用量を転記するときは、合計・モデル別・担当別の欄に同じ利用が再掲されていないか確認します。内訳と合計を足すと二重計上になるため、一つの集計元を選び、入力にキャッシュ分が含まれるかも確かめてください。`input`という項目名だけで「入力欄に書いた文だけの量」とは判断しません。単位や意味が分からない値を、トークン数や請求額へ置き換えないでください。
応答の途中で表示が変わる環境では、応答が終わった後の値を記録します。依頼ごとの値のほかに、会話全体の合計を表示する環境もあります（VS Code 1.145の「Session Cost」など）。両方を足さず、どちらか一方を使います。アカウント全体の月間の利用量は、一つの依頼や試行の値には使いません。

毎回入力しなくて済む指示も、使われるときにはコンテキストに関わります。一方、すべての指示ファイルの全文が常に含まれるとは限りません。
キャッシュは対応環境で入力の一部を再利用する仕組みですが、「過去の会話は無料」とは言えません。Skillや担当を増やすだけでも節約は保証されません。

### 演習

1. 「短い依頼で誤解が起き、追加説明と修正を繰り返した」という場面を一つ想定し、どんな依頼で何が起きたかを2〜3行で書いてください。
2. 上の表から、この仕事の進め方を評価するために必要な記録を選び、選んだ理由を書いてください。
3. 利用環境で確認できる指標について、表示名、単位、対象期間・範囲を確認してください。どの画面や記録で確認できるかは、講師または準備担当者が案内します。確認できない値は「未取得」とします。

### 結果を確かめる

依頼文の文字数、コンテキストの使用状況、作業全体の累積利用量、費用を分けて説明してください。「必要な品質に到達したか」と「そのためにどれだけ調査・確認・やり直しがあったか」は別の問いです。ここでいう手戻りは、説明の不足や誤りなどによって調べ直したり、修正をやり直したりすることです。

<details>
<summary>ヒント：どこまでを一つの仕事として数えるか</summary>

依頼文だけでなく、必要な品質へ到達するまでを見ます。追加説明、誤りの発見、修正、再確認にかかった負担が増えていないかを調べます。

</details>

<details>
<summary>解説：トークンエコノミーの評価単位</summary>

短い依頼が適切な場合もあります。必要な背景が既に正しく適用されていれば、繰り返し説明する必要はありません。
逆に、必要な条件を省くと、調査や修正のやり直しが増えることがあります。「常に短く」ではなく、品質と仕事全体の記録から判断します。
取得できなかった利用量は未取得のままにし、第8章で比較できる範囲を限定します。

</details>

## 1-3｜一場面から次の問いを作る

**この節のゴール:** Copilotの調査から一つの主張と根拠を取り出し、次に調べる問いを作れることです。

調査の記録は、回答の全文を保存するだけでは活用しにくくなります。「何を根拠に、何が分かり、何がまだ分からないか」を短く残すと、次の依頼へつなげられます。

### 演習

1. 本編の作業フォルダー（全章を通して改修する実習アプリの作業コピー）とコードの状態を確認し、Copilotが使えるツールを読取・検索に限定してください。「編集しないで」と依頼するだけでなく、実際のツールの設定も確認します。限定する方法は利用環境によって異なるため、講師または準備担当者が案内した方法を使います。限定できない場合は、依頼を送らずに相談してください。
2. 1-1の依頼2を新しい会話で試し、参照先、追加調査、人への質問を観察してください。依頼1も試す場合は、別の新しい会話にします。講師デモを見る場合は、その対象版と記録の出所を確認します。
3. 次の表から一場面を選び、主張、根拠、次に必要な確認を自分のメモへ残してください。

| 観察するつながり | 記録するもの |
| --- | --- |
| 読んだ内容 → 追加調査 | どの記述を読んだ後に、どのファイルや資料を調べたか。調べた理由は、回答や画面に示された範囲で書く |
| 調査結果 → 人への確認 | コードだけでは決められないこととして、どのような質問を人へ示したか。回答の中で挙げた質問も含める |
| 人の判断 → 次の依頼 | 何を採用し、何をまだ任せないと決めたか |

該当する場面がなければ、その事実を記録します。観察のために不要な調査や架空の失敗を作りません。依頼文から予想したこと、デモで見たこと、自分で実行したことも分けてください。

<details>
<summary>例：VS Code 1.145のLocalで読取・検索に限定する</summary>

試走で使ったVS Code 1.145のLocalでは、次の方法で限定しました。表示と操作は版や設定で変わるため、講師の案内を優先してください。

- 新しい会話を作り、エージェントの選択欄（入力欄の近くで、使うエージェントを切り替える欄）でAskを選びます。Askは、質問への回答を中心にした組み込みのエージェントです。
- 入力欄のツールの設定（Configure Tools）を開き、webとmemoryのチェックを外します。1.145では、memoryはvscodeの中にあります。execute（コマンドの実行）には一部だけチェックが残りますが、残るのはコマンドの出力やテストの失敗を読む道具（getTerminalOutput、testFailure）で、コマンドは実行しません。読取・検索だけにする場合は、これらも外します。
- この設定はその会話だけに適用されるため、新しい会話を作るたびに確かめます。1.145では、新しい会話でもエージェントとモデルは前の会話のまま残りますが、ツールの設定は元に戻ります。
- 既定のAgentを選んだままツールを絞ると、その設定は他の会話にも引き継がれます。絞った場合は、作業の後で元に戻します。

</details>

### 結果を確かめる

メモだけを見て、「Copilotが何と説明したか」「その裏付けは何か」「次に何を確かめるか」を説明してください。分かったことと未確認のことが分かれ、まだアプリの編集を始めない理由が説明できるかを確かめます。

<details>
<summary>つまずいたとき：何を記録すればよいか分からない</summary>

回答の全文を要約せず、一場面に絞ります。「何を読んだか」「それで何が分かったか」「まだ何が分からないか」の三つで始めます。
実行結果が手元にない場合は、観察した事実として埋めず、確認したい問いだけを書いてください。

</details>

**第2章へ渡すもの:** 変更依頼、観察の観点、調べたい問いです。アプリは開始状態を保ちます。利用量の勝敗や変更済みコードは渡しません。
