## 8-1｜経験を、比較できる一つの問いへ変える

**この節のゴール:** これまでの経験から、観測と仮説を分け、比較できる問いを作れることです。

最後に作るのは、便利だった機能の一覧ではなく、**必要な品質を守って再試行できる改善手順**です。まず、自分の記録から一場面を取り出しましょう。

前の章から、Copilotが調べた場面、人が説明を補った場面、結果の確認、やり直し、人の判断のいずれかを選びます。問題なく進んだ場面でも構いません。
実際に起きたこと、その理由として考えたこと、次に試したいことを分けます。記録がなければ「記録なし」とし、成功談や測定したかのような数字を作りません。

### 演習

1. 前の章で残した記録から、探索、再説明、検証、手戻り、人の判断のいずれか一場面を選んでください。
2. 次の表で、観測した事実、原因の仮説、次に試したい変更を分けてください。
3. 共通の比較課題に取り組む前に、関連ファイルを明示すると何が変わりそうか、予想と確かめたい記録を書いてください。

| 区分 | 記入すること |
| --- | --- |
| 観測：実際に起きたこと | どの版・場面で何が起きたか、裏付けとなる記録 |
| 仮説：理由として考えたこと | なぜそうなったと考えるか、他の説明もあり得るか |
| 次の問い | 一つだけ変えるなら何を試したいか |

### 今回の共通の問い

> 関連ファイルを最初に明示すると、同じ品質に到達するまでの探索や手戻りはどう変わるか。

ここでの「同じ品質」とは、8-2で両条件に共通して決める品質確認を、どちらもすべて満たすことです。

小課題はAC-08の件数不整合です。検索結果は正しい一方、APIの`count`に全申請件数を返してしまう独立した比較用アプリを使います。
本編にこの不具合があることは前提にしません。検索未実装の開始版、第6章のAND/OR欠陥とも別です。

<details>
<summary>ヒント：問いを一つに絞る</summary>

モデル、指示、Agent、Skill、関連ファイルを同時に変えると、何の効果かを区別できません。前の章の経験は仮説の材料にし、今回のA/Bの入力へそのまま足し込みません。

</details>

### 結果を確かめる

実際に起きたことを記録で示せるか、原因の説明と分けているかを確認してください。「関連ファイルを示すと改善するかもしれない」という予想を、必ず費用が下がるという結論に変えていないことも確かめます。

## 8-2｜A/Bで変えるもの、揃えるもの

**この節のゴール:** 関連ファイルの明示だけを変え、品質と比較条件を先にそろえられることです。

A/B比較は、一つの違いが結果にどう関わるかを、条件を揃えて比べる方法です。今回は「関連ファイルの場所を最初に示すか」だけを変えます。
結果を見てから有利な条件を選ぶのではなく、先に条件を記録します。Aにも必要な目的・品質・安全条件を渡し、関連ファイルをCopilot自身で調べることを許します。

| 条件 | A | B |
| --- | --- | --- |
| 課題・AC・対象外・品質確認 | 同じ | 同じ |
| 開始コード・データ・依存 | 同じ開始状態の独立コピー | 同じ開始状態の別コピー |
| モデル・設定・担当・実効ツール | 同じ | 同じ |
| 共通・条件付き指示・Skill | 同じ | 同じ |
| 人の関与方針（許可するコマンドの範囲を含む）・停止条件 | 同じ | 同じ |
| 会話 | 新しい会話 | 別の新しい会話 |
| 関連ファイルの明示 | 明示しない。調査は許す | 確認済みのファイルパスだけを追加 |

Aにも十分な目的・AC・安全条件を渡します。探索を禁止したり、わざと曖昧にしたりしません。
Bへ修正方法、答えの行、完成差分、片方だけのヒントを渡しません。既存の指示で道案内が足りていれば、差が出ない可能性もあります。
開始版から既にある別の不具合を見つけたときの扱いも、両条件の依頼に同じ文で書きます。書かないと、比較の途中で作業の範囲が広がり、人が止める必要が出ることがあります。

### 演習

1. 第8章用の同じ開始版から、コード・データを独立させたAとBを確認してください。
2. 上の表と共通の品質確認を使い、モデル、指示、担当、実効ツール、会話、停止条件を記録してください。
3. 両条件に同じ依頼を用意し、Bだけに、実習資料で指定された同じ開始版の関連ファイルを追記してください。
4. 変更点が参照パスの明示だけか、実行前に見比べてください。

### 両条件で共通にする依頼

```text
指定した比較教材で、検索結果とAPIのcountが一致しない問題を調べ、AC-08を満たすように修正してください。
検索結果の正しさ、単独・複合・0件、全体集計、UI/APIと既存操作を維持してください。
開始版から既にある別の不具合を見つけた場合は、その不具合の修正やテストの追加はせずに報告してください。
必要な調査は許可します。無関係な機能や依存を追加せず、確認を削除・弱体化しないでください。
両条件で決めた共通の品質確認を実行し、対象版・差分・実行結果・未確認を報告してください。
```

**Bにだけ加える一行の形式**

```text
関連ファイル：［この比較教材の同じ開始版で確定した参照パス］
```

角括弧の内容は、実習資料で指定された参照パスに置き換えてください。参照パスは、講師・準備担当者が比較教材の同じ開始版で確かめて示します。対象版に存在することを確認し、修正方法や完成差分は加えません。共通の品質手順への参照は、両条件に渡します。
VS Codeのチャット入力欄では、Enterキーを押すと送信されます。共通の依頼を貼り付けた後にBの一行を加えるときは、Shift+Enterで改行するか、同じ行の末尾に続けて書きます。送信する前に、入力欄に依頼の全文が入っていることを確かめてください。途中で送信されてしまった場合は、その会話を止めて予備試行として記録し、コピーが開始時のままかを確かめてから、新しい会話でやり直します。

### 結果を確かめる

Aの調査を禁止せず、Bへ解法を渡していないことを確認してください。コード・データ・指示・品質条件の対応が説明でき、残る条件差も記録されていれば、実行へ進めます。

<details>
<summary>ヒント1：見えにくい条件差も残す</summary>

開いているファイル、選択範囲、添付、上位フォルダー・ユーザー・組織の指示、解説を読んだかどうかも影響します。別の会話でも、人が前の試行で覚えたことやキャッシュの影響は完全には消えません。

</details>

<details>
<summary>ヒント2：品質を先に固定する</summary>

ID集合・内容・長さ・`count`、正常な0件と入力エラー、変わらない全体集計、必要な回帰を両条件で揃えます。安く済んだ方だけ簡単な確認にしてはいけません。

</details>

## 8-3｜A/Bを実行し、条件と結果を記録する

**この節のゴール:** A/Bを独立して実行し、品質・負担・条件差を比較できる形で記録できることです。

まず各条件を1回ずつ実行し、一組の結果を読みます。一度の比較だけで、どの仕事でも同じ効果が出るとは言えません。
順序と条件を先に記録し、Aのコードや会話の解法をBへ引き継がないようにします。結果が気に入らないからと勝つまで繰り返しません。

### 演習

1. 実行順、開始条件、記録する指標と範囲を決めてください。指標は、利用量、時間、人が追加した説明の回数など、比べるために記録する項目です。
2. AとBをそれぞれ新しい会話・独立コピーで実施し、同じ品質確認を行ってください。
3. 原記録を保存し、次の表へ結果をまとめてください。比較前の調査や比較後の分析は、本試行とは別に記録します。

| 記録項目 | A | B |
| --- | --- | --- |
| 開始版・データ・条件 | 実施時に記入 | 実施時に記入 |
| 結果 | 成功／失敗／未完了 | 成功／失敗／未完了 |
| 途中の失敗と回復 | 起動失敗・権限拒否・修正・再試行 | 起動失敗・権限拒否・修正・再試行 |
| 共通の品質確認の根拠 | Aの最終コードに対応する結果 | Bの最終コードに対応する結果 |
| 利用量 | 単位・取得元・対象範囲、または未取得 | 単位・取得元・対象範囲、または未取得 |
| 時間 | 開始・終了・待ち・打ち切りの範囲 | 開始・終了・待ち・打ち切りの範囲 |
| 人の介入 | 判断、通常承認、ヒント、追加説明 | 判断、通常承認、ヒント、追加説明 |
| 揃わなかった条件・未確認 | 何が揃わなかったか | 何が揃わなかったか |

準備の調査、定義作成、診断、A/B、分析、改善手順の作成は別の作業です。前工程や講師支援の利用量を本試行へ混ぜません。
品質の記録にも、対象版と「開始版の不具合を確認」「Aの修正後」「Bの修正後」などの段階を付けます。準備時に狙った不具合を検出した失敗を、修正後にも残っている失敗として数えないでください。
「同じ版の結果」とは、各条件の最終ソースと、その条件の確認記録が対応することです。AとBの最終コードや差分が、バイト単位で同じになることは求めません。
ファイルの場所を伝えたこと、そのファイルが実際に読まれたこと、内容を正しく使ったことも分けて記録します。
終了コード0や完了報告だけで、すべてのツール呼び出しが成功したとは扱いません。途中で回復した失敗も、本試行の探索・手戻りとして原記録へ残します。

利用量を比べるときは、どの作業の開始から終了までを数えたか、単位と取得元は何かを揃えます。時間も同じです。チャットに表示される作業時間と、許可を待った時間を含む開始から終了までの時間は一致しないことがあるため、どちらを使ったかを記録し、両条件でそろえます。必要な値を取得できないことを「欠測」と呼びます。欠測は0とは違い、その値では比較できません。
応答の途中で利用量の表示が変わる環境では、応答が終わった後の値を記録します。ステータスバーなどに出るアカウント全体の月間の利用量は、試行ごとの比較には使いません。
一つの試行で複数回依頼した場合は、その試行に含めた依頼を一覧にします。依頼ごとの値を使うなら、追加説明や再試行も含めて各依頼の最終値を一度ずつ合計します。会話全体の累積値を使うなら、対象範囲を確認し、依頼ごとの値を重ねて足さないでください。
試走で使ったVS Code 1.144と1.145では、依頼ごとのトークン数はチャットの画面に表示されませんでした（1.145の画面に出るトークン数は、コンテキストの使用状況です）。会話の保存データには値がありましたが、集計の範囲を確かめられないため比較には使っていません。このように範囲を確かめられない値は、未取得として扱います。
トークンを取得できる場合は、入力の総数にキャッシュ読み込み・書き込みが含まれるかを確認してください。入力総数へ内訳を重ねて足さず、入力、出力、キャッシュの定義と取得元をそろえます。別の実行環境で得た数値を、VS Codeで測定した結果として扱いません。

### 止める条件

対象版が違う、品質確認自体に不備がある、本来渡さない解法が混ざった、許可範囲を外れる、必須の情報を確認できない場合は、その事実を記録して止めます。
開始版の不具合を検出する失敗（準備のときに確かめた、想定どおりの失敗）は、品質確認の不備ではありません。
依頼の範囲を外れた作業（開始版にある別の不具合の修正など）が始まった場合は、止めて追加説明を送り、人の介入として記録します。もう一方の条件でも同じ基準で扱います。
品質確認を訂正したら、両条件を新しい共通条件で準備し直します。訂正前の結果を後から成功へ貼り替えません。

### 結果を確かめる

結果を、対象版、条件、同じ品質確認、原記録へたどれるか確認してください。未取得を0にせず、未完了を成功にしていないこと、前の試行の解法や変更を引き継いでいないことも確かめます。

<details>
<summary>ヒント：未取得の値があるとき</summary>

未取得を0にせず、その指標では比較できないと記します。品質・条件・探索・介入など、実際に取得できた範囲で評価します。
Previewの診断機能を有効にして穴を埋めたり、コンテキストの使用率から作業全体の消費量を計算したりしません。

</details>

<details>
<summary>解説：自習で記録だけ読む場合</summary>

出所のある実測記録が提供された場合は、その条件と限界を読んで評価できます。自分でA/Bを実行・測定したとは記録しません。
記録を読む場合も、対象版、条件、品質確認、取得範囲がそろっているかを確かめてください。

</details>

## 8-4｜条件、品質、負担の順に見て、採用するかを決める

**この節のゴール:** 利用量の大小だけで判断せず、条件と品質を確認してから、その方法を採用するかを根拠に基づいて決められることです。

「少ない利用量で終わった」場合でも、必要な品質に届いていなければ、少ない費用で成功したとは言えません。次の順序で結果を読んでください。

最初に与えた条件と、作業中にCopilotが何をどれだけ調べたかは分けます。今回は、その調べ方の変化も見たい結果の一つです。調べた範囲が違うことだけで比較条件が揃っていないとは判断しません。後からAの調査を制限したり、両方に同じファイルの場所を教えたりして、比較する問いを変えないようにします。

![比較条件が揃い、必要な品質を満たしたかを先に確認する。その後に記録できた利用量・時間・人の負担を比べ、分かったことと限界から、限定採用・追加評価・見送りを判断する。](assets/evaluation.svg)

図は結果を読む順序です。Bが必ず有利になる分岐や、実測の削減率を示しているわけではありません。

| 読む順序 | 判断すること |
| --- | --- |
| 1. 条件 | 同じ対象・要求で、違いを説明できるか |
| 2. 品質 | 必要な品質に到達したか。失敗・未完了は何か |
| 3. 負担 | 同じ作業範囲の利用量・時間・人の関わりを比べられるか |
| 4. 解釈 | 実際に起きたことと原因の考えを分け、一度の比較では分からないことを示せるか |
| 5. 採用するか | 限定して試す、追加評価する、見送るという判断に理由があるか |

### 演習

1. A/Bの原記録から、条件の対応と、必要な品質への到達を先に確認してください。
2. 同じ取得範囲で比べられる利用量・時間・介入だけを整理してください。
3. 観測と原因の仮説、まだ判断できないことを分け、限定採用・追加評価・見送りとその理由を決めてください。
4. 下の三つの仮定も使い、結果が期待と違った場合の判断を練習してください。

**Copilotへの依頼例**

```text
原記録は［置き場所］にあります。
A/Bの原記録から、まず比較条件、次に品質、その後に記録できた利用量・時間・人の関わりを整理してください。
観測した事実、原因の仮説、判断できないことを分けてください。
完了していないこと、取得できなかった値、揃わなかった条件を隠さず、限定採用・追加評価・見送りの選択肢と根拠を示してください。
Bの勝利や削減率を結論として先に決めないでください。
```

<div class="task" data-title="数値なしでも判断を練習する">

> 次の三つは説明用の仮定です。採用するかを判断する根拠と、足りない情報を考えてください。
> A/Bとも品質達成だが差が読み取れない場合、Bだけ未完了の場合、品質達成だが利用量が未取得の場合を、それぞれどう扱いますか。

</div>

<details>
<summary>解説：三つの仮定の読み方</summary>

差が読み取れないなら、改善効果を主張せず、準備・維持負担や追加評価の必要性を考えます。
Bが未完了なら、利用量が少なくても、少ない費用で成功したとは呼びません。完了できなかった条件や品質の不足を、次に改善する候補にできます。
利用量が未取得なら、その指標の優劣は保留です。取得できた品質・時間・介入などの範囲で言えることを限定します。

</details>

### 結果を確かめる

結論が、比較した「関連ファイルの明示」という条件と、観測できた範囲に収まっているか確認してください。単発結果からモデル・Agent・Skill全体の優劣へ広げず、追加評価が必要な条件を説明します。

## 8-5｜次に使う改善手順を一つにまとめる

**この節のゴール:** 比較の根拠と採否を、次に開始・確認・停止・再開できる具体的な手順へまとめられることです。

「文脈を最適化する」「レビューを強化する」だけでは、次に何をするか分かりません。
今回の件数が一致しない課題について、何を準備し、どう依頼し、どのファイルを渡すかを書きます。何を確かめ、人がどこで判断し、止めたら誰へ相談するかも決めます。改善案を作ったことと、その案を実行して測り直したことは別です。

### 演習

1. 比較の根拠、採否、その判断が成り立つ条件をシートに記入してください。
2. 次に同じ種類の作業を行うとき、依頼・指示・Agent・Skill・人の判断へ何を割り当てるか決めてください。
3. 開始に必要な情報、終了条件、停止と戻し先、再開条件を書いてください。新しい定義を追加しない判断も理由とともに残します。

| 置き場所 | 今回決めること |
| --- | --- |
| 今回の依頼 | 対象版、目的、AC、対象外、今回だけの参照 |
| 共通・条件付き指示 | 継続する規則、特定作業だけの規則 |
| Agent | 役割、入出力、必要な道具 |
| Skill・テストや確認用の資料 | 手順、失敗時の対応、再利用する確認 |
| 人の判断 | 必ず人を待つ場面、進み具合を知る情報、関わる条件、再開の条件 |

### 改善設計シート

```text
【比較の根拠】
共通課題・版・AC：
揃えた条件／変えた参照指定：
```

## 8-6｜自己確認・第三者確認と、実務への置き換え

**この節のゴール:** 改善設計シートだけで作業を説明できるかを確かめ、自分の仕事で調べ直すことを選べることです。

他の人や時間を置いた自分が読んでも使える手順になっているかを確認します。口頭で補足しないと分からない箇所があれば、シートへ戻って直しましょう。

### 演習

1. 講師付きでは講師または演習を支援するTAに、シートと参照だけから作業を説明してもらってください。自習では、時間を置いてから自分で説明し直します。
2. 開始、終了確認、停止と戻し先の説明が足りない箇所を訂正し、もう一度確認してください。
3. 自分の仕事を一つ選び、固有名や実際のデータを含まない形で説明してください。下の表から、その仕事で調べ直す情報と、次に試す一つの変更を決めます。

| 学び方 | 行うこと | 記録する状態 |
| --- | --- | --- |
| 講師付き | 講師／TAがシートと参照だけを読み、最初は作成者が口頭で補わずに説明してもらう | 実際の確認者、対象版、説明、指摘を採用したか、訂正後の再確認 |
| 自習 | 一度シートから離れ、記載した情報だけで自分が説明し直す。必要なヒント・解説で修正する | 自己確認した範囲、訂正、第三者確認は未実施 |

どの版・情報から何を始めるか、何を確認すれば終えてよいか、何が起きたら止めて誰へ戻すかを説明します。
自習は自己確認で先へ進めます。第三者がいないことだけで学習を止めません。ただし、自己確認やAIのコメントを実際の第三者確認として記録しないでください。AIに読ませて確かめた場合は、「AIによる確認」として、読ませた範囲と指摘を別に記録します。
第三者確認を含む評価は、その項目が未実施なら保留し、自習で確認できた学習を別に残します。

### 別の仕事へ移す

一つの一般化した作業を選びます。実顧客のコードや秘密情報を持ち込まず、業務が未定なら別のプロジェクトのAPI修正を想定して構いません。

| 再利用する考え方 | 別の仕事で調べ直すもの |
| --- | --- |
| 目的と品質から範囲を決める | AC、業務条件、対象版、対象外 |
| 必要な根拠を絞って渡す | 実際の構成・パス、必要なライブラリ、参照する資料やコードが最新か |
| 指示・役割・手順を分ける | 配置、適用条件、既存の仕組み、実効ツール |
| 同じ版の結果を見る | データ、コマンド、期待値、回帰範囲 |
| 人の判断と監督を設計する | 影響、権限、担当、停止・再開方法 |
| 一つずつ変えて評価する | 取得できる指標、集計範囲、採用・見直し条件 |

### 結果を確かめる

比較から何が分かり、その方法を採用するかを、根拠とともに説明してください。まだ判断できない範囲、機能の使い分け、次に使う具体的な手順も示します。誰がどこまで確認したか、別の仕事では何を調べ直すかも説明します。
本編の実装・品質確認、比較課題の成功・失敗、自分で行った実行・測定、記録を読んだ範囲や受けたヒント、改善手順を評価した結果は別々に残します。

<details>
<summary>解説：この章の到達点</summary>

削減率、Bの勝利、解答と同じ差分、全機能の利用は合格条件ではありません。
必要な品質を守り、根拠と限界を説明し、次の一つの試行を再開できる手順にすることが中心です。
自分で行った実行・測定と、読解・自己確認・第三者確認の範囲を説明できるようにしてください。机上で手順を確認したことを、実務での効果実証や運用承認とは区別します。

</details>
