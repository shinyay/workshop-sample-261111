## 5-1｜計画から、変更範囲を決めた実装依頼を作る

**この節のゴール:** 調査・実装計画と準備した指示・手順を、範囲と終了条件が明確な実装依頼に変えられることです。

この章から本編の絞り込みを実装します。まず依頼内容を確かめ、5-2で代表的なテストの失敗を確認してから実装を始めます。最終的な品質判断は、第6章でレビューと追加確認を通して行います。
5-2で先に編集するのはテストです。アプリ本体は、そのテストが狙った未実装を検出したと確認してから変更します。
操作する場所は、教材を表示するリポジトリではなく、実習アプリの作業コピーです。ターミナルの現在地と、対象の`pyproject.toml`、`tests`を確認してから始めてください。

第2章の計画と、第3章・第4章の指示・役割・手順を見直します。使うコードの版、既にある変更、データ、許可する操作、まだ決まっていないACを確認します。前の章で調べたことを、理由なく最初から調べ直す必要はありません。
新しい会話で依頼する場合、第2章の会話の内容は引き継がれません。まとめた計画を会話に貼るか、作業コピーに置いたメモの場所を依頼に書き添えてください。
未決の仕様を実装担当だけで決めさせません。また、今回の範囲にないライブラリ追加、DBの置き換え、公開も行いません。
ただし、既に決まっているACを未決事項へ戻さないでください。たとえば配色の維持は、フィルターのフォーム送信後や条件解除後も対象です。入力欄の配置や具体的な文言などの実装上の選択とは分けて扱います。
開始版であることを示す段階名や画面上部の案内、それを確かめる既存テストの期待も、2-4で人が決めた扱いに沿って変更単位ごとに見直します。講師用の完成例と区別できる扱いにします。

### 演習

1. 本編の作業コピーへ戻り、対象版、差分、指示・検証Skillの適用、使用するデータを確認してください。対象版と差分は、`git log -1 --oneline`や`git status`で自分で確かめます。
2. 最初の変更単位、対象AC、触れない範囲、確認方法、止めて相談する条件を依頼文にしてください。変更単位の分け方は5-3の表のとおりで、最初の単位は部署の条件と共通の取得処理、APIの一覧・件数です。ACは番号だけでなく、条件と期待する振る舞いも書き添えます。
3. Copilotに、実装を始める条件が揃っているか確認してもらってください。不明な仕様があれば、人が確認してから決めます。この節では依頼内容の確認までとします。

**Copilotへの依頼例**

```text
調査・実装計画と、準備した指示・検証手順を使って、絞り込みを実装する準備をします。
計画は［計画メモの場所］、ACは［ACメモの場所］にあります。
最初の変更単位は、部署の条件、共通の取得処理、APIの一覧と件数です。代表ACはAC-02（部署だけを指定すると、指定した部署の申請だけを返す）です。
状態・複合条件・画面のフォームは後の変更単位で扱うため、この単位で完成したとは報告しないでください。
まず対象版、この単位で変更する範囲、AC、変更しない範囲、確認方法を照合してください。
まだ編集・実行はせず、この単位で人が決めること（段階名や、開始版の動作を確かめる既存テストの扱いなど）を示してください。
未実装によるテスト失敗を確認してから実装する手順にします。不明な仕様や対象外変更が必要なら人へ戻し、同じ版の差分・結果・未確認を残してください。
```

### 開始条件の不足を見つけたら

指示・役割・手順の適用が未確認なら、その範囲を先に確認します。比較用コピーの成功を本編の成功へ転記しません。
用意された教材のコードや設定を使って再開した場合は、自分で達成していない部分と、提供を受けた部分を記録します。困ったときに、まず参加者の変更を捨てる手順にはしません。

対象AC、変更単位、既存の確認方法、止めて相談する条件を結びます。毎行の編集を人が指示することと、無制限に任せることの二択ではありません。

</details>

### 結果を確かめる

依頼文だけを読んで、何を変え、何を維持し、何を確認したら終えてよいかが分かるか確認してください。実装担当の完了報告と、人による品質判断は別であることも説明します。

## 5-2｜テストが失敗した理由を確かめる

**この節のゴール:** テストが狙った未実装を検出し、実装後には同じ入力条件と期待結果で成功することを確かめられることです。

最初は部署の絞り込みを扱います。必要な行、不要な行、返却件数を、ACと使用するテストデータから決めます。
テストの失敗を「赤」、成功を「緑」と呼ぶことがあります。ただし、失敗なら何でもよいわけではありません。狙った機能がまだないために失敗し、実装後に同じ条件と期待結果で成功することを確かめます。全ACを例外なくテスト先行にすることは求めません。

### 先に、使うデータを確かめる

テストに必要なデータや実行環境を用意する仕組みを、**fixture**（フィクスチャー）と呼びます。参照版の既存`client` fixtureは、テストごとの一時DBに初期12件を用意します。ブラウザーで申請を追加しても、このfixtureの件数は増えません。
「はじめに」のF1〜F6を使う場合は、別の新しい一時DBを`SEED_DEMO_DATA=False`で作り、6件だけを登録します。初期12件へ追加する方法ではありません。新しく作った申請は確認待ちになるため、承認済み・差し戻しの行は、作成後に既存の状態変更の手順で設定し、各行の状態を確かめます。

![ブラウザーのデモDBは操作後のデータを維持する。既存clientはテストごとに初期12件、F1〜F6の専用fixtureは別の一時DBに6件を用意し、それぞれのデータから期待値を決める。](assets/test-data.svg)

三つは別々のデータであり、順にコピーする図ではありません。同じ検索条件でも、使ったデータが違えば期待するIDや件数も変わります。

### 演習

1. 指定部署と別の部署を含むデータから、返るはずの申請IDと件数を決めてください。実装の条件式を使って答えを作るのではなく、ACとデータから判断します。
2. AC-02を確かめるテストを作り、実行してください。テストが起動し、対象が実行され、狙った機能がないために失敗したかを読み取ります。
3. 失敗の理由を確認してから、部署の絞り込みを最小限実装するようCopilotへ依頼してください。
4. 同じ確認と、既存の動作を壊していないかの回帰確認を実行してください。変更内容と、失敗・成功の結果を、それぞれ対象版と結び付けて記録します。

テストの中で「実際の結果が期待どおりか」を確かめる文を**アサーション**と呼びます。テストが起動しただけでなく、そのアサーションまで実行されたかを見ます。

| 順序 | 確かめること |
| --- | --- |
| データを決める | 指定部署とそれ以外を含め、返るはずの行をACとデータから説明できる |
| 確認を作る | 申請IDの集まり、重複・不足、各値、`count`を確かめる |
| 実際に走らせる | 起動し、対象テストが見つかり、狙ったアサーションまで実行される |
| 失敗理由を読む | 必要なライブラリやデータの不足ではなく、機能が未実装のために失敗したか |
| 実装後に戻る | 同じ入力条件と期待結果で成功し、必要な回帰確認も通るか |

不正な値や重複を400にする確認（負のテスト）は、実装前から成功することがあります。開始版は、どの検索条件も受け付けずに400を返すためです。この成功は、値を検査した証拠にはなりません。説明の文言が開始版と違うことを確かめるなど、狙った理由で拒否されたと分かる確認を加えてください。

### 確認の書き方の抜粋

次はテスト本文で使うアサーションの抜粋です。`assert`は、続く条件が成り立たなければテストを失敗させます。`actual_ids`は実際の結果、`expected_ids`は既知データから決めた期待値に置き換え、手元の実習アプリのfixtureへ組み込んでください。説明用のF1等を、そのまま実IDとして使いません。

```python
assert len(actual_ids) == len(expected_ids)
assert set(actual_ids) == set(expected_ids)
assert body["count"] == len(body["items"])
```

集合の一致だけでなく長さも見ることで、同じIDの重複を見逃さないようにします。期待値は変更対象の実装から自動的に計算せず、ACと既知データから決めます。

<details>
<summary>実行例：既存の初期12件fixtureから始める</summary>

次は、参照版`1a411cd`の`tests/conftest.py`にある`client`を使う例です。実習アプリの`tests/test_filtering.py`に保存します。初期12件では、開発部のIDは降順で9・5・1です。F1〜F6の期待値とは混ぜません。

```python
from flask.testing import FlaskClient


def test_department_filter(client: FlaskClient) -> None:
    response = client.get("/api/requests?department=engineering")
    assert response.status_code == 200
    body = response.get_json()
    actual_ids = [item["id"] for item in body["items"]]
    expected_ids = [9, 5, 1]
    assert actual_ids == expected_ids
    assert body["count"] == len(body["items"]) == 3
    assert all(item["department"] == "engineering" for item in body["items"])
```

依存の準備後、アプリのルートで実行します。パスの区切りは、PowerShellでもBashでも同じ意味になる`/`にしています。

```text
uv run --locked pytest tests/test_filtering.py -q
```

リストの一致は、IDの不足・余分・重複と順序をまとめて確認します。この例が未実装の開始版で`assert 400 == 200`と表示されて失敗したら、その入力を受け付けないことまで確認できています。起動や収集の失敗は別です。
Windowsで新しく作ったファイルは、改行の形式がCRLFになることがあります。この実習アプリの書式の確認（`ruff format --check .`）はLFを求めるため、内容が同じに見えるのに「would be reformatted」と表示されたら、`uv run --locked ruff format tests/test_filtering.py`のように、そのファイルを整えてから確認し直します。
手元の実習アプリのデータが参照版と異なる場合は、そのデータでIDと状態を確認して期待値を決めます。

</details>

<div class="task" data-title="判断してみる">

> テストが起動せず失敗した場合、「未実装だから赤になった」という証拠にできますか。
> また、検索実装後も「有効な検索キーは400」という開始版限定テストを維持すべきでしょうか。

</div>

### 結果を確かめる

失敗が依存不足やfixture不備ではなく、未実装の絞り込みによるものだったと説明してください。実装後は、期待するID集合と長さが一致し、`count`が`items`の実数と一致することを確かめます。
成功させるために、不正入力や回帰の確認を削除していないことも見直してください。

<details>
<summary>ヒント：テストを実行できない失敗と、仕様の変更を分ける</summary>

対象のアサーションまで実行されていなければ、その仕様を確かめていません。また、「検索がまだない開始版か」を識別する期待結果と、新機能を追加した後も保つべき期待結果は区別します。

</details>

<details>
<summary>解説：正当なテスト更新</summary>

検索対応を追加したら、その機能について開始版限定の400期待を更新します。不正値・重複キー・未知のキーを拒否する確認まで削除することは正当化されません。
完成例パッチの適用可否も、参加者独自の正しい実装を判断する基準にはしません。
参照版の`tests/test_reference_patch.py`は、講師用の完成例パッチを検品する確認です。本編の回帰確認では、5-3のとおり実行対象から外します。

`WORKSHOP_STAGE`や画面上の段階名も、機能の合格判定ではありません。演習版の分類を追加するときは、開始版と完成例の分岐を残し、演習版のラベルと機能のACを別々に確認します。
演習版の分岐へ「フォームがない」「複合条件は400」といった途中段階の期待を固定すると、次の正当な実装と衝突します。

</details>

## 5-3｜三つの変更単位で実装と検証を回す

**この節のゴール:** 変更を小さく区切り、実装・検証・必要な修正を同じ対象版で繰り返せることです。

5-2で行った部署の絞り込みとテスト先行は、次の最初の変更単位に含まれます。確認済みの部分をやり直すのではなく、残る条件と画面操作へ順に広げます。

| 変更単位 | 実装・確認の中心 | 途中で未実装と分かるようにするもの |
| --- | --- | --- |
| 1. 部署の絞り込みを通す | 部署、共通の取得処理、APIの一覧・件数、代表ACの失敗から成功 | 状態・複合条件・画面の完成 |
| 2. 条件を増やし、入力の扱いを確かめる | 状態、AND、未指定・空文字、0件、不正値・重複、集計の維持 | まだ作っていない画面操作 |
| 3. 画面操作と表示の完成 | 選択、解除、結果件数、0件案内、APIとの一致、開始版を説明する表示や文書（READMEなど）の見直し、回帰 | 残る未確認を明示する |

各単位で確認した範囲と、後の単位へ残すものを明示します。途中で全ACを満たしたと報告しないでください。

![合意した範囲を実装し、その版の検証結果を確定してから、人が次の行動を判断する。不一致があれば実装担当が修正し、同じ確認と必要な回帰確認へ戻る。](assets/implementation.svg)

図の戻り道は必要な修正と再確認です。成功するまで期待値を弱めるという意味ではありません。

### 演習

1. 今回取り組む変更単位と対象ACを選び、Copilotに範囲を示して実装を依頼してください。
2. 検証Skillを使って必要な確認を行い、結果を確定してください。検証中はコードや期待値を変更しません。
3. 不一致があれば実装担当へ根拠を返し、合意した修正の後に同じ確認を実行してください。
4. その単位の差分・結果・未確認を記録してから、次の単位へ進んでください。差分は`git diff --binary --output="［記録用フォルダー］/［単位名］.patch" HEAD`のように保存します。未追跡の新しいファイル（新しいテストなど）はこの差分に入らないため、写しも同じフォルダーへ置きます。次の単位の検証では、これらと比べて、その単位で変わった部分を確かめます。

**検証Skillを使う依頼例**

```text
今回の変更単位について、検証Skillの手順で必要な確認を選んで実行してください。
実装担当への依頼文、実装担当の確認結果（テストが先に失敗したことを含む）、人が決めた変更（文言・段階名など）を添えるので、意図した変更と依頼にない変更を区別してください。
対象版、実行場所、データ、コマンド、終了状態、確認結果と未実施を報告してください。
回帰確認では tests/test_reference_patch.py の2件を除外し、除外したことと理由も報告してください。
この検証中はコード・テスト・設定を修正しないでください。
修正が必要な場合は、根拠と対象を実装担当へ返してください。
```

検証結果を確定した後で、実装担当が修正します。同じエージェントが続けて作業する場合も、結果を確かめる段階と、修正する段階を区切ります。
実行コマンドは実習アプリのREADMEと設定から確かめます。講師用の完成例の検証や、存在しない手順を無断で本編へ持ち込みません。
本編の回帰確認では、3-2と同じく`tests/test_reference_patch.py`の2件を実行対象から外します。これらは、講師用の完成例パッチの適用・取り消しや、変更済みのファイルへ適用できない場合の動作を確かめる、配布物の確認用テストです。本編の変更内容によって、成功する場合も、パッチを当てられず失敗する場合も、段階名の確認で準備エラーになる場合もあります。どの結果も、それだけでは自分の実装の正しさを判断できません。除外は検証の依頼文で指定し、理由も書き添えます。除外したことと理由は、検証の記録に残します。
変更単位2ではAPIの条件・件数を確認し、フォームの選択値や0件の解除案内は変更単位3で確認します。APIと画面を一つのテストで確認する場合も、どのアサーションで失敗したかを分けて読んでください。
段階名と、それを確かめる既存テストも、変更単位ごとに見直します。例えば変更単位2で状態の条件を受け付けると、「開始版では部署と状態の組み合わせが400になる」という既存の期待と衝突します。2-4で決めた扱いに沿って、演習版の段階名をこの単位で加えるのか、その期待だけを更新するのかを、着手前に人が決めてください（5-2の解説を参照）。

### 結果を確かめる

変更した範囲、満たしたAC、まだ取り組んでいないACが分かるかを確認してください。変更対象の版に対する検証結果を見てから修正へ移り、修正後も同じ入力条件と期待結果で確かめます。

<details>
<summary>ヒント：途中の赤をどう扱うか</summary>

まだ作っていない機能によるテスト失敗と、今回も保つべき既存の動作を壊したことは別です。「途中だから全部無視」ではなく、今の変更で満たす仕様と、後の変更へ残すものを説明します。

</details>

## 5-4｜実際の結果から原因を絞り、必要な修正をする

**この節のゴール:** 失敗の事実と原因の仮説を分け、必要な追加確認から修正を判断できることです。

実際に見た結果を**観測**、その理由として考えた説明を**仮説**と分けます。例えば「APIが期待した行を返さない」は観測ですが、「SQLが原因だ」はまだ確かめていない仮説かもしれません。
入力を受け取る、値を検査する、DBから取得する、応答を返す、という処理を追います。テストデータも含め、どこで期待との差が生じたかを必要な追加確認で絞ります。

### 演習

1. 失敗した対象版、入力、データ、期待値、実際の結果を一組にしてください。
2. 原因の候補を挙げ、どの候補かを見分けるための最小限の確認を考えてください。その確認でDBやファイルが変わるなどの影響と、必要な許可も整理します。
3. 確認した根拠に対応する修正を行い、同じ確認と必要な回帰を再実行してください。
4. 次の表を使って、観測から再確認までを記録してください。

**Copilotへの依頼例**

```text
この失敗記録と同じ対象版を使って、観測した事実と原因候補を分けてください。
候補を見分ける最小限の追加確認を提案し、対象、実行によって変わるもの、必要な許可を示してください。
追加の許可が必要な確認は、実行する前に止まって私に確認してください。
確認後は、根拠に対応する修正と、同じ確認・回帰の再実行を行ってください。
期待値の不備を疑う場合も、ACとデータへ戻り、成功させるためだけに弱めないでください。
```

回帰の再実行は、5-3と同じ範囲で行います。講師用パッチの確認テスト2件は除き、`uv run --locked pytest --ignore=tests/test_reference_patch.py -q`のように実行します。

| 記録する段階 | 書くこと |
| --- | --- |
| 観測：実際に見たこと | どの版・条件で何が期待と違ったか |
| 仮説：原因として考えたこと | 原因の候補と、その裏付け、まだ確かめていないこと |
| 追加確認 | 候補を区別するため何を見るか |
| 修正 | 何をなぜ変えたか |
| 再確認 | 同じ確認、必要な回帰、残る不足 |

### 自然な不具合が出なかった場合

成功した本編を故意に壊しません。再現条件が示された講師の失敗記録を使い、観測・仮説・追加確認を整理してください。
記録の読解は、自分で再現・修正・再実行した経験とは分けて記録します。

実際に再現して切り分ける場合は、同じ版から**本編とは別のデバッグ用コピー**を作り、既存の`client` fixtureを使う次の検証例を`tests/test_diagnostic_error_contract.py`へ置いてください。アプリ本体を変更せずに失敗を採取し、期待値と既存のAPI契約を照合します。成功させるためだけにアプリやテストを変えず、必要な訂正と再確認を記録してください。

本編の変更はまだコミットしていないため、コミットからコピーを作ると開始版に戻ってしまいます。本編のフォルダーを、未コミットの変更と新しいファイルも含めてコピーしてください。`.venv`などの環境とキャッシュのフォルダーは除きます（環境は最初の`uv run`で作り直されます）。コピーで`git log -1 --oneline`と`git status`を実行し、本編と同じ対象版か確かめてから検証例を置きます。ACのメモもコピーに置き、新しいフォルダーは開くときに信頼の確認をします。

```python
from flask.testing import FlaskClient


def test_error_response_contract(client: FlaskClient) -> None:
    response = client.get("/api/requests?department=unknown")
    assert response.status_code == 400
    assert isinstance(response.get_json()["error"], str)
```

この検証例は診断用です。未解決のまま本編へ持ち込まず、確認後もデバッグ用コピーと本編を区別してください。

### 結果を確かめる

「この結果を見たので、この原因候補を採用した」と説明できるか確認してください。コードを変更しなかった場合も、環境・対象版・期待値のどこを訂正したかと、その後の確認を示します。

<details>
<summary>ヒント：DBや対象版も疑う</summary>

自動テストの一時DBと、手動で見ている画面のDBが違うことがあります。別のコピーや起動中サーバーを見ていないかも確認します。
ただし、原因を調べるために対象不明のDBを削除・初期化してはいけません。

</details>

<details>
<summary>解説：修正しない判断もある</summary>

起動環境の不備、古い結果の参照、期待値の誤りなら、製品コードの修正が適切とは限りません。
何を訂正したかと、その後にどの入力条件と期待結果で確かめたかを残します。アプリに不具合がなかった結果も、有効な記録です。

上の検証例では、`error`の型を決めつけていないかを確認します。本ワークショップの参照版は、`error`の中に`code`と`message`を持つオブジェクトを返します。既存の契約が維持されているなら、アプリを文字列返却へ変えるのではなく、検証側の期待値を訂正します。その際もHTTP 400、エラーコード、空ではない説明の確認は残します。

</details>

## 5-5｜画面・API・回帰を確認して引き継ぐ

**この節のゴール:** 画面・API・既存操作を確認し、レビューに必要な差分と結果をそろえられることです。

APIだけ成功しても、選択値の表示や解除、0件の説明が壊れているかもしれません。
画面とAPIを同じ条件・データで比べ、表示・返却された申請IDと件数が一致するかを確かめます。一覧の件数と、全申請の集計は別に確認します。

**回帰確認に含めるもの**

- 詳細、新規作成、状態変更、入力検証、並び順、表示、配色のうち、変更の影響を受けるもの
- 画面の案内文：途中段階の「状態の検索は後で追加する」といった説明を、実装後の画面へ残していないか

**デモDBの扱い**

- ブラウザーで新規作成・承認・差し戻しを確かめると、デモDBは変わります。実行前後の件数を残してください。初期12件を前提に確認し直す場合は、対象を確認した専用DBだけを所定の手順で戻します。サーバーの再起動だけでは初期化されません。
- 新しい作業コピーには、まだデモDBがない場合があります。初回の`seed`または起動によるDB作成と、既存データを削除して戻す`reset-demo`を区別してください。`seed`は既存の申請をリセットしません。

**ブラウザー確認スクリプトの扱い**

実習アプリの`tools/verify_browser.py`は、READMEにある任意のブラウザー確認で、開始版と講師用の完成例だけを対象にしています。完成例の画面の名前や件数を期待値として持つため、自分の実装の合否基準にはしません。画面の文言を、このスクリプトに合わせる必要もありません。画面は、ACと自分たちが決めた内容をもとに、ブラウザーを手で操作して確認します。

<details>
<summary>ヒント：APIへの直接アクセスだけでは分からないこと</summary>

`scoutTheme=dark`を付けたURLが正しく表示されても、フォーム送信で同じ値が保たれるとは限りません。
GETフォームの`action`へクエリを書くだけではなく、送信後のURLと画面を確認してください。必要な表示用パラメーターを送信する場合は、hidden入力など、フォームの送信項目として扱います。
選択値の保持、解除後の表示、明暗の配色を、ブラウザー上の一連の操作で確かめます。

</details>

### 演習

1. 同じ版・データで画面とAPIを確認し、検索結果のID集合と件数を照合してください。
2. 条件の選択・解除、正常な0件、不正入力、検索で変わらない全体集計を確認してください。
3. 明暗の配色をそれぞれ指定し、ブラウザー上で選択・フォーム送信・解除を行って、操作後のURLと配色を確認してください。既定の配色は、OSやブラウザーの明暗の設定で決まります。既定と同じ指定だけでは、値が失われても気づかない場合があるため、既定とは異なる指定も含めます。キーボードでの操作も確認してください。
4. 既存操作の回帰結果をそろえ、ACと差分・確認結果を結び付けて、レビュー用のメモを作成してください。

URLは、クエリの並び順や文字列の完全一致だけで判定しません。未選択の欄が`status=`のように送信される場合もあるため、値・重複・未指定と空文字の意味をACと照合してください。

| 確認の軸 | 代表的な問い |
| --- | --- |
| 条件 | 指定・未指定・空文字・AND・解除が仕様どおりか |
| 境界 | 正常な0件と400を区別しているか |
| 一覧 | 必要な行があり、余分・重複がなく、`count`と一致するか |
| 集計 | 検索だけで全体・状態別の総数が変わっていないか |
| 対象 | 同じ版、コピー、DB、起動中サーバーを見ているか |
| 回帰 | 既存操作と、AC-11で変更しないと決めた範囲を保ったか |

### レビューへ渡す記録

```text
対象版と差分：

画面/APIの確認と使用データ：

```

「支援／講師記録の読解／提供部分」には、人や講師に助けてもらった箇所、講師の記録を読んだだけで自分では再現していない箇所、用意されたコードや設定を使った箇所を書きます。

### 結果を確かめる

一つのACを選び、同じ版の差分と実行結果を指し示してください。テスト数や「全部成功した」という要約だけでなく、必要な画面操作も確かめたか、何がまだ未確認かを説明します。

<details>
<summary>つまずいたとき：確認が揃わない</summary>
