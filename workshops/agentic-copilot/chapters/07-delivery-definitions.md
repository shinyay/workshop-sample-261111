## 7-1｜アプリの事実と配備・自動化の要件を分ける

**この節のゴール:** アプリから分かる事実と、人が決める配備・自動化要件を分け、定義を作るための入力をそろえられることです。

第6章の品質確認を終えたら、次の担当がアプリを扱うために何が必要かを考えます。この章ではTerraformとAzure Pipelinesの定義を作成・レビューし、残る確認事項まで引き継ぎます。

アプリを動かす先へコードや設定を用意することを、**配備**（デプロイ）と呼びます。今回は実際に配備するのではなく、必要な構成や手順をコードで記した**定義ファイル**を作ります。

| 用語 | この章での役割 |
| --- | --- |
| Terraform | クラウドの資源（リソース）と設定を、コードで記述するための道具 |
| Azure Pipelines | テスト、成果物の作成、配備などの手順を自動化するサービス |
| CI | コードの変更を取り込み、ビルドやテストなどを行う継続的インテグレーション |
| CD | 確認した成果物を配備へ進める仕組み。この演習では実行せず、定義案だけを作る |
| 成果物 | 後の処理へ渡すファイル。この章ではアプリのソースなどをまとめたZIPを扱う |
| state | Terraformが管理する資源の状態を記録する情報。今回は操作せず、扱い方を決める |

<div class="important" data-title="クラウドへは接続・適用しません">

> この演習ではAzure・Azure DevOpsの実環境を使いません。リソースの作成・変更、Terraformのplan・apply・state操作、パイプライン実行は行いません。
> 作成するのは定義と引き継ぎメモです。定義を読んで確認したこと、許可されたローカル確認、実環境での配備を区別してください。

</div>

全員が行うのは、要件に対応する定義の作成・読解・レビューと、未設定・未検証事項の記録です。構文解析、確認スクリプトや補助CLIの実行、ZIPの作成・検査は、講師が許可し、環境を準備したローカル確認に含まれる場合だけ行います。以下のヒントにある実行例も同じ扱いです。実行しない場合も設計上の品質条件は省かず、読解した範囲と未検証の動作を分けて残してください。

### アプリの事実と配備要件

対象版、品質根拠、起動・依存・確認方法、残課題、人の関与方針を受け取ります。
アプリのコードからは、どのAzureサービスを採用すべきか、組織の接続や承認がどうなっているかまで決まりません。

| 区分 | 確かめること |
| --- | --- |
| アプリの事実 | 対象版、起動方法、設定、必要なライブラリ、DB、参加者版で使える確認方法 |
| 人が与える要件 | 環境の目的、管理する範囲、実行方法、渡すファイル、処理を始める・進める条件 |
| 演習の条件 | 想定する一つの構成、使う版、用意された最小限のひな形、許可するローカル確認 |
| 実環境で調べること | 資源を使えるか、権限、接続、承認、配備後の動作 |

この演習で想定する構成は、App Service（Linux）に一つのアプリを置く案です。7-2で検討し、適合を確かめるまでは採用を確定しません。

Python 3.14を既定とするアプリの説明は、選んだAzureランタイムの対応を保証しません。
SQLiteのデータをどう保持・初期化するか、複数のプロセスで使えるか、アプリをどこまで公開できるかも確認事項です。配備先へ合わせるために、DBを別の製品へ置き換えたり、認証や本番運用向けの機能を追加したりしません。

<details>
<summary>ヒント：参照版で先に調べる制約</summary>

参照版の`python -m request_portal serve`は、同じマシンから接続するための`127.0.0.1`でだけ待ち受けます。SQLiteは既定の`instance/portal-demo.sqlite3`を使い、`DATABASE`設定には`Path`が必要です。任意の環境変数名をTerraformへ書けば、アプリが読み取ってくれるわけではありません。
このローカル起動コマンドや保存先を、そのままApp Service向けの完成した設定として渡さないでください。待受、起動、Host制約、保存、認証・公開条件をアプリ側と照合し、適合不足は次の担当へ返します。

</details>

### 演習

1. アプリの起動方法、必要なライブラリ、設定、DB、品質確認の手順を、根拠となるファイルや記録とともに整理してください。
2. 次のDR要件について、アプリから分かること、人の判断が必要なこと、実環境で確かめることを分けてください。
3. DRごとに対応方針、確認方法、未決事項と判断する人を記録してください。

### 初期要件の対応表

DRは、この章の配備・自動化要件に付ける識別子です。アプリの機能を判断するACとは役割が違い、ACを置き換えません。

| ID | 要件 | 定義・記録で確かめること |
| --- | --- | --- |
| DR-01 | 同じ版を追跡する | 品質を確認したアプリ、生成入力、CIのソース、成果物の版 |
| DR-02 | 合意した仮想構成に限定する | 必要な資源と関係、追加しない機能 |
| DR-03 | 実行・依存・確認の条件を揃える | Python、uv、ロック、OS・シェル、作業場所 |
| DR-04 | データと秘密情報を持ち出さない | 実データ・資格情報・DB・stateの除外 |
| DR-05 | Terraformの入出力を説明する | 型、指定元、資源参照、出力と利用側 |
| DR-06 | 必要な品質確認を省かない | アプリと定義の確認を割り当てる |
| DR-07 | 不足する確認を成功扱いにしない | 失敗・中断・必須確認スキップを区別する |
| DR-08 | 確認した入力から成果物を作る | 内容、除外、版、確認、後続への受け渡し |
| DR-09 | CDは実行せず、定義案だけを作る | 既定では対象外。接続・適用・実行をしない |
| DR-10 | 未設定・未検証と判断者を残す | 接続・承認・保持・本番化の不足と次の確認 |
| DR-13 | CIを始めるきっかけと対象を示す | ソース連携、push・PR・手動、ブランチ・パス、サービス側設定 |

初期要件はDR-01〜DR-10とDR-13です。DR-11・DR-12は後の追加要件で扱います。

前章から受け取った版と、定義を追加して確認した版は、別々に記録します。受け取った版は、`git log -1 --oneline`と`git status`で自分で確かめます。最初に受け取ったコミットの識別子を、そのまま最新の版として使い続けないでください。追加後の確認記録、CIが取得するコード、成果物に記録する版が対応するかを確かめます。

### 結果を確かめる

アプリのコードだけでは決まらない、資源の選択・接続・権限・承認を挙げてください。ACとDRを混ぜず、未決の設定を架空の実値で埋めていないことを確認します。

<details>
<summary>ヒント：要件表に未決事項を残す</summary>

DR-ID、要件の出所、対応する定義箇所、確認方法、結果、未決事項・判断者を一組にします。生成前は対応方針を書き、生成後は実際の箇所を示します。
Azureの契約を識別するsubscription ID、外部サービスへ接続するための設定、承認者が不明なら、架空の値を実際に使える値として書きません。

</details>

## 7-2｜構成を考え、Terraformの入出力を作る

**この節のゴール:** 配備要件から必要な資源・入力・出力を考え、Terraform定義の各部分を説明できることです。

まず、AzureでWebアプリを動かすサービスであるApp Service（Linux）に、一つのアプリを置く構成を検討します。ただし、必要なPythonを使えるか、起動方法が合うか、SQLiteのデータを保持できるか、公開条件を守れるかを確かめる前には採用を確定しません。
資源の名前を並べるだけでなく、何を管理し、何を管理しないか、どの設定値を誰が渡すかを説明します。

![要件からTerraformとAzure Pipelinesの定義を作り、同じ版・設定・配備先・成果物を指しているか確かめる。CDは定義案だけとし、接続・適用・パイプライン実行は行わない。](assets/delivery.svg)

図は定義同士の対応です。矢印は実クラウドへの接続や配備の実行結果ではありません。

### 演習

1. 管理する資源、管理しない範囲、入力の指定元、利用側へ渡す出力を図または表にしてください。
2. アプリの事実と照合し、構成の適合が分からない部分を明示してください。
3. 最小骨組みから主要な定義をCopilotで作成し、各ブロックをDRへ対応付けてください。未確定の部分を実環境へ適用しません。最小骨組みは、準備担当者が用意するファイル（Terraformとプロバイダーの版を固定した`infra/versions.tf`など）です。置き場所は講師の案内に従います。

ACと同じく、DRも番号だけではCopilotに伝わりません。7-1の整理を置いた場所、最小骨組みの場所、講師が許可したローカル確認とその実行方法、変更してよい場所を依頼に書き添えます。7-3・7-4の依頼でも同じです。

**Copilotへの依頼例**

```text
合意した仮想構成と初期DR要件から、Terraform定義案を構成してください。
入力の型・意味・誰がどこで指定するか、必要な資源とその関係、出力とその使い道を説明してください。
Python・起動・SQLite保持・公開条件の適合が未確認なら明示してください。
実データ・資格情報・stateを埋め込まず、plan・apply・state操作、Azureへの接続は行わないでください。
主要な記述のまとまりをDRへ対応づけ、構成が未確定の部分を完成済みとして報告しないでください。
```

### HCLの読み方の小例

Terraformで構成を書くための言語を**HCL**と呼びます。次は、入力を`variable`で受け取り、利用側へ渡す値を`output`で示す例です。Azure資源を定義する完成例ではなく、実行もしていません。

```hcl
variable "environment_name" {
  type        = string
  description = "Logical name of the non-production environment"
}

output "environment_name" {
  value = var.environment_name
}
```

この例では、受け取った環境名を同じ意味の出力として渡しています。実際の資源名、命名規則、値の検査、設定元は要件に従って決めます。
作成した主要部について、必要な理由を自分で説明してください。完成例の名前だけを変えるのではなく、要件から入出力と依存関係を考えます。

### 結果を確かめる

入力の型・意味・指定元、資源間の参照、出力の利用側を一つずつ説明してください。Python・起動・保存・公開条件の適合が未確認なら、その確認事項が定義の完成報告に埋もれていないか見直します。

<details>
<summary>ヒント1：資源間の矢印を説明する</summary>

どの資源がどの設定・識別子を参照するかを追います。同じ文字列を別々に書くより、正しい参照関係になっているかを確認します。

</details>

<details>
<summary>ヒント2：アプリの事実に戻る</summary>

起動方法、設定名、保存先、必要な依存がアプリ側の根拠と合っているかを確認します。サービス名が正しそうでも、実行条件の対応がなければ配備できるとは言えません。

</details>

<details>
<summary>解説：生成と確認の段階</summary>

HCLの書式が整っていること、プロバイダーの仕様に合うこと、ローカルで`validate`を実行して定義を検査したこと、実環境で適用できたことは別です。プロバイダーは、TerraformからAzureなどのサービスを扱うためのプラグインです。
実際に行った確認だけを記録し、定義の生成を配備成功として扱わないでください。
`validate`には、固定した版のプロバイダーをローカルに用意する必要がある場合があります。準備担当者が通信・取得元・版を確認し、stateの保存先であるバックエンドへ接続しない方法でそろえます。必要な入力値が未設定でも構文の検査が成功することがあるため、成功しただけで値が確定した、構成を採用できるとは判断しません。

</details>

## 7-3｜CIの起動条件と、開始後の進行条件を分ける

**この節のゴール:** CIを始める条件と、品質を確認して次へ進む条件を分けて定義できることです。

DR-13は「何を契機に、どのソースを対象にCIを始めるか」です。DR-06・07は「始まった後、何を確認できれば次へ進むか」です。
次の工程へ進んでよいかを判断する確認を**品質ゲート**と呼びます。正しい品質ゲートがあっても、必要な変更でCIが起動しなければ確認は行われません。

Gitでは、変更を分けて進める履歴の枝を**ブランチ**、ローカルのコミットをGitHubなどへ送る操作を**push**と呼びます。GitHubなどで、変更内容のレビューや別のブランチへの取り込みを依頼するのが**プルリクエスト**（PR）です。どの操作をきっかけにCIを始めるかを、ここで設計します。この演習で実際にpushやPR作成を行うわけではありません。

| 設計する部分 | 問い |
| --- | --- |
| 起動 | どのリポジトリと連携し、push・PR・手動のどれで始めるか。対象ブランチやファイルは何か |
| 準備 | どの版・OS・シェル・Python・uv・ロックで作業するか |
| 確認 | 参加者版に実在する何を、どの順序で確認するか |
| 成果物 | 何を含め、何を除き、どの版と名前で渡すか |
| 進行 | 失敗・中断・必須確認のスキップ時に進まないか |
| CD | 通常のCIから使わない別の定義案にし、どの接続や承認を未設定として残すか |

Azure Pipelinesでは、一まとまりの処理を**job**（ジョブ）、複数のjobをまとめる大きな区切りを**stage**（ステージ）と呼びます。
準備を別のjobやstageに置いても、インストールしたツールや仮想環境が次の処理へ引き継がれるとは限りません。各jobで必要な実行環境を用意することと、確認記録を受け渡すことを分けて設計してください。
外部サービスへの接続先や認証を指定するサービス接続など、Azure DevOps側で設定するものもあります。YAMLファイルに書ける内容だけで完結するとは考えず、未設定のものを残します。

### 演習

1. 連携するリポジトリ、処理を始めるきっかけ、対象ブランチ・ファイルを整理してください。
2. 準備、品質確認、成果物作成、後続への受け渡しを定義し、失敗・中断・必須確認のスキップ時の扱いを示してください。
3. Terraformの出力と利用側、成果物の作成側と取得側が対応するか確認してください。
4. CDは通常のCIから参照しない別の定義案にし、実行しないことを明示してください。未設定の接続・承認を記録し、登録・接続・実行は行いません。

**Copilotへの依頼例**

```text
初期DR要件とアプリで必要な確認方法から、Azure Pipelines定義案を構成してください。
CIを始めるきっかけと対象範囲、開始後の準備・確認・成果物・次へ進む条件を分けてください。
ソース連携先とYAML外の設定、Terraformの出力と利用側の対応を明示してください。
CDは通常のCIから参照しない、実行しない別の定義案にしてください。接続・登録・実行はしないでください。
不明なタスク名・版・確認コマンドは推測で埋めず、確認事項として残してください。
```

### YAMLの条件を読む小例

次は、`Verify`という確認段階を仮定した後続段階の条件の抜粋です。単独で実行できるパイプラインではありません。

```yaml
dependsOn: Verify
condition: and(succeeded(), eq(dependencies.Verify.result, 'Succeeded'))
```

先行する確認段階が成功した場合に進む意図を表します。ただし、これだけでVerify内の必須テストが実際に走ったことまでは分かりません。
実行対象のテストが0件だった場合や、必須の処理を省略した場合を成功にしない設計も必要です。失敗の原因を調べる記録を保存することと、配備に使う候補ファイルを作ることは分けます。
定義に含める確認スクリプトは、正常、失敗、対象0件、スキップ、起動不能の入力を、それぞれ正しく判定できるように作ります。古い成功レポートを再利用したり、子プロセスが起動できなかった状態を「終了コードが0以外」とだけ判定したりしないようにしてください。
これらの入力でスクリプトを実際に動かすのは、講師が許可したローカル確認に含まれている場合だけです。含まれていない場合は、そのスクリプトを未検証として引き継ぎます。

成果物は作業フォルダー全体を圧縮せず、含めるファイルを決めて内容を検査します。アプリのソースと依存定義、版の情報に限定し、DB、秘密情報、state、仮想環境、キャッシュが混ざらないように定義します。
許可されたローカル確認として梱包を試す場合は、ダミーの禁止ファイル（`.env.local`や`.db`など、実際の秘密情報ではないもの）を置いた確認用のコピーで梱包し、実際のZIPの中身を調べます。試さない場合は、含めるファイルの指定を定義から読んで確かめ、梱包の結果は未検証として記録します。

<details>
<summary>ヒント：定義の構文が正しくても、処理は誤る</summary>

JUnitでは、最上位の`testsuites`に集計属性がなく、その下の`testsuite`に件数がある出力もあります。実際の正常レポートを読み、`testcase`と集計を照合してください。異常だけを拒否するテストでは、正常な結果まで拒否する不具合を見逃します。

ファイルが存在するだけでは、YAMLを解析できるとは言えません。実際のパーサーで字下げや重複キーも確認します。また、ツールのバージョン表示にはハッシュなどの補足が付く場合があるため、正常な出力を確かめ、比較する版の部分を決めてください。

Bashでは途中の確認コマンドが失敗しても、最後のコマンドが成功すると全体が成功になる書き方があります。`set -euo pipefail`等で停止条件を明示し、版の不一致で後続へ進まないことを、許可された範囲で実行して確かめます。

ソース用フォルダーにも、DBや`.env`、`__pycache__`が入る場合があります。フォルダー名だけを許可せず、含めるファイルと種類を限定します。梱包を試せる場合は、ダミーの禁止ファイルを置いた別の確認用コピーで、実際のZIPの中身を調べます。実際の秘密情報を検査用に使いません。

</details>

<details>
<summary>ヒント：確認した入力と、後続へ渡す証拠を結び付ける</summary>

別のjobやstageに、前の作業フォルダーがそのまま残るとは限りません。品質記録とJUnitを明示して受け渡し、ソース版・実行ID・検査対象が同じことを照合します。生成した診断ファイルと、未検証のソース変更は区別してください。

補助スクリプトだけでなく、アプリ・テスト・依存定義も確認対象の入力です。確認前後と梱包直前で入力が変わっていないか、未追跡のソースやテストが紛れ込んでいないかを確かめます。失敗したときは、以前の成功記録やZIPを今回の成果として使わないようにします。

定義と一緒に追加した補助スクリプトやテストも、アプリと同じ`ruff check .`と`ruff format --check .`の対象です。許可されたローカル確認で実行し、作ったCIが自分で追加したファイルで失敗しないかを確かめます。

</details>

<details>
<summary>ヒント：CDを実行しないことを明確にする</summary>

別のCD定義に`trigger: none`、`pr: none`と書くだけでは、手動起動や他からの参照まで禁止したことにはなりません。
通常のCIから参照しないこと、今回はパイプラインの登録・サービス接続・実行をしないことを、実施しない操作として併せて示します。
既定で無効にする条件や確認文言は補助であり、サービス側の権限・承認の代わりにはなりません。追加要件の変更時にも、非実行の境界が消えていないか確認してください。

</details>

<details>
<summary>解説：YAMLに書けない設定もある</summary>

起動やPRの扱いはソース連携先・提供形態に依存し、権限・サービス接続・環境の承認などはサービス側の設定も関わります。
「YAMLがあるのでCI/CDは完成」とせず、どこまで定義し、何を実環境で確認するかを引き継ぎます。

</details>

### 結果を確かめる

CIが起動しない問題と、必要な確認を省略して後続へ進む問題で、調べる箇所が違うことを説明してください。診断記録の保存を、未検証の配備候補を作成する理由にしていないことも確認します。Copilotが途中で「直します」と述べた変更も、最終的なファイルと実行結果で確かめます。

## 7-4｜追加要件へ、差分で対応する

**この節のゴール:** 追加要件の影響を両方の定義へ追い、整合する差分として反映できることです。

ここで二つの要件を追加します。初期要件を消したり、アプリのACを変更したりするものではありません。

| ID | 追加する要件 | 影響を調べる箇所 |
| --- | --- | --- |
| DR-11 | 環境ごとに資源と設定・stateを区別する | 論理環境名、命名、設定元、state分離方針 |
| DR-12 | 環境が変わっても同じ成果物を使う | 実行・成果物の識別、取得、再ビルドの有無、内容とdigestの照合 |

環境名だけ変えてstateが共有されたままでは、意図した分離になりません。今回は分離方針を定義し、stateの作成・移動・削除は行いません。
同じ名前の成果物でも中身が同じとは限りません。どの実行の何を取得するかを識別し、後続で作り直さない設計を考えます。
ファイルの内容から計算する識別用の値を**digest**（ダイジェスト）と呼びます。ここでは成果物の内容が同じかを照合するために使います。名前、どの実行で作られたか、digestを組み合わせて追跡します。
取得する側が選ぶ実行ID・ソース版・成果物名・digestを必須の照合項目として定義し、違えば後続へ進まないようにします。まだ作成・取得していない成果物に、測定済みの値を書いてはいけません。実物を使う照合は、7-1の許可されたローカル確認に含まれる場合だけ行います。

### 演習

1. DR-11とDR-12が、既存の入力、命名、設定、state方針、成果物の受け渡しへ与える影響を挙げてください。
2. TerraformとAzure Pipelinesの定義を差分で更新し、変更理由をDRへ対応付けてください。
3. 初期DRと、接続・適用・実行をしない条件を保ってください。そのうえで、環境が増えても同じ成果物を追跡できるかを確認します。

**Copilotへの依頼例**

```text
DR-11（環境ごとに資源と設定・stateを区別する）とDR-12（環境が変わっても同じ成果物を使う）を追加し、既存のTerraform・Azure Pipelines案への影響を調べてください。
環境別の資源・設定・state分離方針と、同じ成果物の識別・取得・照合を差分で反映してください。
初期DR要件と、接続・適用・実行をしない条件を維持し、変更理由と対応箇所を示してください。
実際のstate操作、成果物の配備、接続・実行は行わないでください。
```

### 変更を説明する

「何の要件で」「どの定義を」「なぜ変えたか」「どこが未検証か」を対応づけます。
命名変更、設定の受け渡し、成果物名・作成先・取得先など、片方だけ直すと壊れる組を探してください。

### 結果を確かめる

環境名だけでなく設定とstateの分離方針が対応し、成果物を同じ名前だけでなく版・内容で識別できるか説明してください。実際のstate操作や配備は行わず、未検証事項を残します。

<details>
<summary>ヒント1：同じ値を使う箇所を追う</summary>

Terraformの出力名を変えたら、利用側が参照する名前も確認します。環境を増やすなら、名前だけでなく設定とstateの境界も確認します。

</details>

<details>
<summary>ヒント2：成果物を追跡する</summary>

どの版を入力にし、どの実行で作り、どの成果物を次の処理が選ぶかを追います。まだ作っていない成果物に、測定済みのdigestを書きません。
実物を使う確認では、本文の照合項目に加え、ZIP内のファイルに欠落・余分・重複がないかを調べます。内容や版を記すmanifest（一覧・識別情報のファイル）がZIPの内外で一致するかも確認します。検査ツールを置いた作業コピーの版と、選んだ成果物のソース版は混同しません。
照合の基準には、成果物に書かれた値だけでなく、取得する側が選んだ値を使います。成果物と、その版や名前などの情報（metadata）を一式差し替えても、選んだ値と違えば拒否できるかを確かめます。補助CLIは実際に呼び出し、必要な引数、異常時の終了、正常時の結果出力まで確認してください。
環境を変えた確認では同じZIPを再利用し、再ビルドしていないことと、前後のdigestが同じことを確かめます。実行しない場合は、これらの確認を定義上で追い、動作は未検証として引き継ぎます。

</details>

<details>
<summary>解説：初回と追加作業の数値はA/Bではない</summary>

追加作業は、初回の定義や会話を使い、要求自体も違います。時間や利用量に差があっても、同条件の改善効果として扱いません。
ここで確かめるのは、要件変更の影響を調べ、関係する定義を矛盾なく変更する進め方です。

</details>

## 7-5｜定義を横断してレビューし、次の担当へ渡す

**この節のゴール:** アプリと二つの定義の対応を確認し、確認済み・未設定・未検証を分けて引き継げることです。

Terraform、Azure Pipelines、アプリの起動・確認方法を並べ、同じ版、設定、配備先、成果物を指しているかを確認します。
品質を確認した作業コピーに未コミットの変更がある場合、将来CIが取得するコミットには、その変更が含まれていないかもしれません。同じ状態だと決めつけずに確認します。

### 演習

1. アプリの起動・確認方法、Terraform、Azure Pipelinesを横断し、同じ版・設定・配備先・成果物を指しているかレビューしてください。
2. 許可されたローカル確認を行う場合は、必要なツール・ライブラリ、通信先、実行によって変わるものを先に確認し、実際の結果を記録してください。
3. DRごとの対応、未設定・未検証、次に判断する人と確認事項を、下の形式でまとめてください。

| 確認の段階 | 言えること | まだ言えないこと |
| --- | --- | --- |
| 要件と定義の照合 | 対応する記述がある、抜けがある | 実際に正しく動作する |
| 参照仕様の確認 | 採用した形式・版の仕様に合っている範囲 | 接続先の権限や、その資源を使えるか |
| 許可されたローカル確認 | 実際に実行したfmt（書式）・validate（定義の検査）・構文解析などの結果 | plan・apply・配備成功 |
| 実環境の確認 | 今回は未実施 | クラウド・パイプラインの成功 |

必要な環境や許可がない確認は「未実施」とします。コード読解だけで、ローカル確認やクラウドでの成功を記録しません。

**レビューAgentへの依頼例**

```text
第7章の定義を横断してレビューしてください。
対象は［Terraformとパイプラインの定義の場所］、要件とアプリの事実は［7-1の整理の場所］、版と実行した確認の結果は［記録の場所］にあります。
アプリの起動・確認方法、Terraform、Azure Pipelinesが、同じ版・設定・配備先・成果物を指しているかを確かめてください。
DRごとに、対応する記述、抜け、矛盾を挙げ、根拠（ファイルと行）と、上の表のどの確認の段階で言えることかを示してください。
読取・検索だけを使い、編集・任意実行・最終承認は行わないでください。実際に実行していない結果を確認済みとして扱わないでください。
```

```text
DR-ID：
対応する定義・箇所：
アプリ／Terraform／パイプラインの受け渡し：
確認の種類と実際の結果：
未設定・未検証：
次に判断する人と確認すること：
```

### 結果を確かめる

要件を満たす構成理由、追加要件の差分、定義間の対応、実際に確認した範囲を説明してください。次の担当が、何をそのまま使い、何を実環境で確かめる必要があるか分かることを確認します。

<details>
<summary>つまずいたとき：構成の適合が決まらない</summary>

Python、起動、SQLite保持、公開条件のどれが不足しているかを切り分けます。勝手なDB置換や本番機能の追加で解消しません。
適合を判断する根拠が足りなければ、その条件と次の確認を引き継ぎメモに残してください。

</details>

**第8章へ渡すもの:** 定義の生成・変更・レビューで観察した一場面と、その根拠です。初回と追加作業の数値を、次章のA/Bへ合算しません。
