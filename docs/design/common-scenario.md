## 1. シナリオの狙い

架空の社内申請ポータルに、担当部署と申請状態による絞り込みを追加する。
一つの変更要求を、要件整理、設計、エージェントのカスタマイズ、実装、検証、レビュー、運用への引き継ぎまで追う。

本編に先立つ[「はじめに」](../../workshops/agentic-copilot/chapters/00-start-here.md)で、ワークショップの目的、学べることと身に付ける力、共通シナリオの全体像を説明する。
到達目標を各章の成果・確認方法へ結び付け、参加者が何を学び、どのように自分の開発へ持ち帰るかを見通せるようにする。準備条件、教材と題材アプリのリポジトリ（どちらもPrivate）の閲覧権限と開始版の受け取り方、未準備の実習資産、ACも導入で確認する。
「はじめに」は本編とは別の導入章であり、SEC-01〜SEC-08のID・順序・必須学習やACを変更しない。導入を読んだことを、本編の実行・測定・到達の根拠にはしない。

教材は章と節に分け、本編の各ページを1節として「1-1」「1-2」「2-1」のような章番号-節番号を付ける。節番号は各章で1から始め、見出し・目次・ページ移動の表示をそろえる。
章全体への参照や図では「第1章」〜「第8章」を使い、「はじめに」と補足には番号を付けない。設計文書では追跡用にSEC-01〜SEC-08を使い、MOAWのページIDと原稿ファイル名も維持する。

D-040に基づき、本文は参加者が理解・操作・確認するための教材として記述する。各節のゴール、解説、演習、結果の確認を明示し、制作状況、S0〜S6の管理上の呼称、教材レビューの方針は本文から分離する。
制作方法は[制作・改訂ガイド](../../authoring/README.md)、未同梱の配布用資産と開催前の確認は[実習準備ガイド](workshop-preparation.md)にまとめる。本文の受講前確認には資産が未同梱であることを残し、提供済みとは誤認させない。

本編の全8セクションを、次の四つのまとまりで進める。四つのまとまりは章の統合や追加ではなく、参加者が現在の目的を見失わないための見取り図である。

| まとまり | セクション | 中心となる問い | 次へ渡す成果 |
| --- | --- | --- | --- |
| 理解と計画 | SEC-01・02 | 何を任せ、現状の何を根拠に、どこまで変えるか | 観察の観点、現状理解、ACとS1の計画 |
| 任せ方の準備 | SEC-03・04 | 継続的な規則、担当の役割、再利用手順をどう分けるか | 指示・Agent・Skillと、適用・試用を確認したS2 |
| 実装と品質判断 | SEC-05・06 | 何を実行し、どの根拠で修正・採否・完了を判断するか | S3の実装候補、レビュー・検証と人の判断によるS4 |
| 引き継ぎと改善 | SEC-07・08 | システムの定義と、自分の開発手順をどう次へ渡すか | S5の定義・残課題、S6の比較・改善手順・実務への再確認事項 |

SEC-03は継続的な規則、SEC-04は役割と手順を設計する。SEC-04でレビュー担当を作ることと、SEC-06で指摘の妥当性を判断することは別の学習である。
SEC-05では実装と確認の根拠を作り、SEC-06ではその根拠から品質を判断する。SEC-07はシステムの構成定義、SEC-08は開発の進め方を引き継ぐ。
各章の通常経路と受け渡しは第9節、観測と評価は第10節、復旧は第11節にまとめる。

参加者が学ぶのは、特定のプロンプトを再現することではない。
「何を満たすのか」「どの情報を渡すのか」「何を任せるのか」「どの結果を根拠に採用するのか」を説明できるようにする。
トークンエコノミーも、文章の短さではなく、品質を満たすまでの探索・生成・実行・手戻りを含めて扱う。

既存システムの改修、変更影響、レビュー、引き継ぎを重視する構成は、富士通向けのカスタマイズ案である。
富士通固有の開発標準や承認経路を確認したものではなく、架空の業務を「富士通の実運用」として説明しない。

### 2.1 今回の実施条件

2026-10-16のユーザー回答をD-028〜D-031で記録する。モデルの候補には、2026-11-07のオーナーの判断（D-051）でGPT-6.1 Terraを加えた。指定された条件と、その条件で実際に動作することを確認した状態は区別する。

| --- | --- | --- |

| ヒント | 十分に用意し、既定では非表示 | 第2.3節の段階的な支援案を使う。利用を減点せず、支援後に説明できたことと自力の操作を分ける |

最新Stable版であることだけで、Agent・Skill・診断・管理画面のすべてが非Previewとは判断しない。
定義ファイルの直接編集と、事前確認した非Previewの選択・呼び出し・観測経路を使う。Previewの管理画面やAgent Debug Logsを必須手順にも代替手順にも入れない。
必須機能や指定モデルを利用できなければ、提供条件と到達目標を見直す。別モデルへの無断変更や、通常の依頼をSkillの実利用と呼び替える方法で穴を埋めない。
Codespacesを使う場合も同じ条件を満たす必要があり、参加者の実行場所や権限が確定したことにはしない。

### 2.2 各章で共通に使う学習の進め方

1. 今回の問い、対象、維持する品質、任せない操作を確認する。
2. 参加者が依頼の目的を考え、Copilotへ調査・生成・確認を任せる。
3. 得られた参照・差分・実行結果を照合し、不足があれば追加確認またはヒントを選ぶ。
4. 参加者が採否と次の行動を判断し、要点と根拠への参照を既存の記録へ追記する。

この四つを毎回別のプロンプトとして送る必要はない。自分で考える時間は設けるが、行き詰まったまま待つことを自力学習の条件にしない。
講師は答えの一致より、判断の根拠と支援後の説明を確かめる。参加者の代わりに承認・完了を作らない。

### 2.3 必須情報とヒントの提示

| 提示するもの | 表示・配布の案 |
| --- | --- |
| 課題の目的、AC、対象外、実行権限、開始・終了条件 | 必要になる段階で全員へ明示する。ヒントの中へ隠さず、比較条件間でも品質基準を揃える |
| ヒント1 | 考える観点、問い直すこと。本人が必要時に開く |
| ヒント2 | 調べる場所、確認手段、進め方の候補。本人が必要時に開く |
| ヒント3 | 具体的な依頼例、部分的な実装・定義例。本人が必要時に開く |
| 解説・解答例 | 同じ共通教材でヒントと区別して折りたたみ、必要時に開く。実習アプリの完成コードを開始状態へ適用することとは別 |
| 復旧用の完成済み部分 | 本人の変更を保持し、提供部分と自力の成果を区別して必要時に使う。実ファイルは準備待ち |

ヒント・解説は講師と受講者が使う同じMOAW教材内で、既定を閉じた表示にする。別冊の講師用教材や、ヒントを作業コピー外へ置くことを必須にしない。
Markdownの折りたたみは表示上の非表示であり、同じファイルをCopilotが読めないという意味ではない。共通教材へのアクセスも比較条件の一部として確認する。
比較中にヒントを開いた・引用した・追加指示へ使った場合は、段階と提示内容を介入として残す。片方だけ支援した結果を、無介入の一変数比較として扱わない。
各章の開始プロンプトと追加プロンプトは設計上の案である。MOAWでは目的・行動・確認に沿って、共通依頼、必須情報、任意のヒントへ再構成する。48段階・96プロンプトをページ数や必須送信回数へ機械的に置き換えない。

## 4. 開始時のアプリ

参照元は `shinyay/python-portal-sample-app` のコミット `1a411cd13c02f28bb6f3ac30844af204f1f61d48`。
READMEではPython、Flask、SQLite、Jinja2を使い、Python 3.14を既定、3.13を互換対象とする。
依存関係はuvで管理され、pytest、Ruff、mypyが開発用の確認手段として記載されている。
当初は参照元の説明を確認し、D-041の補助試走では、この固定版の起動・86件のテスト・既存画面操作も独立コピーで確認した。固定参照版、試走で変更した版、配布用の開始版は分けて管理する。

| 面 | 開始状態として使うもの | 今回追加するもの |
| --- | --- | --- |
| 一覧 | 申請の表示、全申請の総数・状態別集計 | 部署・状態の検索条件、検索結果件数、0件の案内 |
| 詳細 | 個別申請の内容表示 | 機能追加なし。回帰確認の対象 |
| 新規申請 | 入力検証後に「確認待ち」で保存 | 機能追加なし。回帰確認の対象 |
| 状態変更 | 確認待ちから承認済み・差し戻しへ遷移 | 機能追加なし。処理済み申請を再変更しない |
| JSON API | 一覧・詳細の読み取り | 一覧に画面と同じ検索契約を追加 |
| 実行 | ローカル実行、架空データ、外部公開しない | Azureなどへの接続は追加しない |

初期アプリは絞り込み未実装であり、対応しない検索条件を400として扱う。
新しい機能を追加したら、その仕様変更に該当するテストは更新する。
不正入力を拒否する既存のテストを一律に削除する、という意味ではない。

参照元の初回データは12件と説明されているが、作成や状態変更後も常に12件とは限らない。
確認の前にデータの状態を揃える。「画面に12と出た」だけを合格条件にしない。
`/healthz`の`stage: starter`も教材の識別情報であり、参加者の実装の正しさを認定する値ではない。

## 5. 最初に渡す変更依頼

> 申請が増え、一覧から処理すべきものを探しにくくなっています。
>
> 担当部署と申請状態で絞り込めるようにしてください。
>
> 既存機能を維持し、画面とAPIの両方で正しく動作することを確認してください。

この依頼はSEC-01で提示し、その直後には実装を開始させない。
SEC-02では、依頼を知ったうえでアプリ全体を調べ、現状の機能・構造と幅広い改善候補を整理する。
その後、本編の共通課題としてこの依頼に戻り、依頼担当へ確認する項目を出して要件・変更計画へ進む。
資料に書かれた仕様、実装で確認できたこと、業務や設計意図の仮説、追加する要件を区別する。
講師は「仕様の答え」を最初から読み上げず、要件具体化の段階で次の論点を引き出す。

| 問い | 具体化する内容 |
| --- | --- |
| 二つの条件を指定したらどうするか | ANDかORか |
| 未指定と空文字はどう扱うか | 条件なしとの関係 |
| 対象が0件の場合はどうするか | 空状態の説明、条件解除、APIの返却 |
| 不正な値や同じキーの重複はどうするか | エラーと正常な0件を区別する |
| 件数は何を数えるか | 検索結果と全申請の集計を区別する |
| どの操作を維持するか | 作成・詳細・状態変更・表示などの回帰範囲 |
| 何を確認したら完成とするか | UI、API、テスト、差分の根拠 |

以下のACは参照元の条件を整理したドラフトの基準である。
演習中に参加者が仮説を出す余地は残すが、実装前に共通の品質条件へ揃える。

## 6. データとインターフェース

### 値の対応

| 対象 | コード | 画面上の名称 |
| --- | --- | --- |
| 部署 | `engineering` | 開発部 |
| 部署 | `sales` | 営業部 |
| 部署 | `corporate` | 管理部 |
| 部署 | `design` | デザイン部 |
| 状態 | `pending` | 確認待ち |
| 状態 | `approved` | 承認済み |
| 状態 | `rejected` | 差し戻し |

コードと表示名を混同しない。日本語画面を英語化したり、コード値を独自の略語へ置き換えたりする課題にはしない。
Q-004の推奨案は、下記ACを本編の契約とし、空白除去・大小文字補正などの新しい正規化を追加しないことである。
部署・状態の値は、上表のコードと完全に一致する場合だけ有効とする。大文字を含む値（例：`Pending`）、前後に空白がある値、空白だけの値はコードと一致しないため、AC-06の不正な値として400にする（D-045、完成例のテストと同じ）。
これらを受理する正規化や、URLエンコード等の追加仕様の検討は発展へ分ける。既存の挙動は参照コード・テストで確認し、未決の値を推測で受理・拒否する変更はしない。

### 一覧契約

一覧APIは `GET /api/requests`、画面の一覧は `/requests`。
絞り込み後の問い合わせ例は `GET /api/requests?department=engineering&status=pending`。
APIの外形は `{"items": [...], "count": N}` とし、`count`は返した一覧の件数を表す。
ここでの`N`は説明用の記号であり、実際のJSONでは数値になる。

検索処理を画面とAPIに別々に実装しない。
共通の取得処理を利用し、条件の解釈、結果、順序が食い違わないようにする。
既存の配色用パラメーター`scoutTheme=light`または`dark`は、検索条件へ混ぜない。

## 7. 受け入れ条件の正本

| ID | 条件 | 期待する振る舞い | 主な確認根拠 |
| --- | --- | --- | --- |
| AC-01 | 条件なし、または検索値が空文字 | 有効な絞り込み条件がなければ全件。片方だけ空なら、もう片方の条件は有効 | 未指定・空文字・混在のテスト |
| AC-02 | 部署だけ指定 | 指定部署の申請だけを返す | ID集合と部署値の照合 |
| AC-03 | 状態だけ指定 | 指定状態の申請だけを返す | ID集合と状態値の照合 |
| AC-04 | 部署と状態を指定 | 両方を満たす申請だけを返す | 片方だけ一致するデータを含む組み合わせテスト |
| AC-05 | 有効な条件だが該当なし | 正常な0件として扱う。APIは空の`items`と`count: 0`、画面は説明と解除手段を示す | APIと空状態の画面 |
| AC-06 | 不正な値、検索キーの重複、未対応の検索キー | 400と説明を返す。無視して全件や正常な0件を返さない | 負のテスト、HTTPステータス、画面・JSONの説明 |
| AC-07 | 画面とAPIへ同じ検索条件を渡す | 同じ取得処理に基づく同じ対象を表示・返却する | コードの参照関係と結果のID集合 |
| AC-08 | 一覧を絞り込む | APIの`count`と画面の結果件数は一覧の実数。全申請の総数・状態別集計は絞り込みで変えない | 絞り込み前後の件数と全体集計 |
| AC-09 | 条件指定後に表示・解除する | 選択条件を画面で確認でき、解除で条件なしの一覧へ戻る | 実画面の操作とリクエスト |
| AC-10 | 既存操作と表示 | 詳細、作成、状態変更、入力検証、既存の並び順・表示・配色を維持する。処理済み申請は再変更しない | 既存回帰テストと代表的な画面操作 |
| AC-11 | 変更全体 | SQLの値を文字列連結せず、パラメーター化を維持。実データ・秘密情報・外部公開・不要な依存を追加しない | 差分、既存の検証、実行設定 |

AC-06の重複は、同じ値の繰り返しも含む検索キーの重複を指す。片方の値が空でも重複として扱う。
AC-06の400と説明は、画面とAPIのどちらへの要求にも適用する。
AC-06の不正な値には、コードと完全に一致しない値（大文字を含む値、前後に空白がある値、空白だけの値）を含む。
配色パラメーターには既存の契約を適用し、既存の正常な指定を未知の検索キーとして拒否しない。AC-10の配色の維持には、絞り込みのフォーム送信や条件の解除の後も、指定された配色を保つことを含む。
AC-11は変更範囲の条件であり、完全なセキュリティ審査や本番適合を保証する合格証明ではない。

#### SEC-02: 現状の理解を、合意した変更計画へ変える

全体像、現状の機能・仕様、設計・アーキテクチャ、改善候補、要件具体化、変更計画の6段階で進める。

#### SEC-03: 一度きりの依頼と、繰り返し守る規則を分ける

#### SEC-04: 役割と手順を作り、同じ根拠を次の担当へ渡す

SEC-04のR0/R1はレビューAgentの有無、V0/V1は検証Skillの有無を扱う二組の比較である。
章内を「レビュー担当の設計・比較」「検証手順の設計・比較」「引き継ぎと本編への適用」の三つに区切る。題材は講師の共通小差分であり、SEC-03で各自が生成したコードを使い回さない。
読み取り中心のAgentと、検証・切り分け・報告までのSkillを定義ファイルから作り、実効ツールと利用の根拠を確かめる。最後に同じ版の検証結果をレビュー担当へ渡す。
本編では演習用に採用した定義を配置・試用し、S2へ進む。演習での設計・試用と、実務で常用するかの採否は別にする。実務での見送りを理由に後続の必須利用を省かない。
比較用コード・DB・診断変更は戻さない。必須の適用・利用が確認できなければS2未到達を残し、講師の確認済み定義で再開した場合も支援と自力を区別する。

#### SEC-05: 小さく実装し、失敗と成功の理由を確かめる

S1の計画とS2を受け取り、代表ACの部署絞り込みで、未実装による失敗から同じ契約の成功を確かめる案とする。
実装は「最小の絞り込み経路」「条件と入力境界の拡張」「画面操作と表示の完成」の3単位を基本案とし、代表ACのテスト先行は最初の単位で行う。各単位で実装・検証・修正を反復し、全ACの全面的なTDDは必須にしない。
検証Skillの報告を確定してから、実装担当が修正する。自然な不具合が出なければ、講師の再現済み記録から仮説と追加確認を考える。本編を故意に壊さない。
SEC-05の引き継ぎには、対象版と未コミット差分の識別、ACと変更・確認の対応、画面/APIと回帰の結果、計画との差、残課題を含める。
代表ACの失敗から成功までの確認、自分の不具合の再現・修正、講師記録の読解、講師の別コピーでの再開を分けて記録する。
講師記録を読んでも、本編の実行成功やS4の品質判断の代わりにはならない。S3の実装候補の状態と、個々の確認・学習の達成を区別する。

#### SEC-06: AIの指摘を評価し、人の関与を設計する

まず独立したAND/OR欠陥で期待集合と反例を説明し、指摘、追加検証、修正、同じ確認と回帰をつなぐ。
続いて、正しい指摘、もっともらしい誤指摘、根拠不足の成功報告、正常な進行を個人で判断する。必須判断点と、監督下で継続・介入・再開する条件を見直す。
SEC-06では、共通教材の検出・修正・回復と、本編の同じ版に対するレビュー・確認を分ける。
指摘の採否、修正範囲、未決仕様、最終品質判断は人が行い、合意範囲の調査・確認と監督の条件を方針にする。
本編S3へ戻り、同じ版の根拠をレビューAgentへ渡してS4を判断する。指摘や修正が不要という結論も認め、共通教材の成功を本編へ流用しない。
HOTLの方針と事例判断は必須、監督・停止・再開の実操作は発展である。発展も非Previewの範囲に限り、事例判断を実操作済みとしない。
SEC-07へは品質根拠・残課題に加え、関与方針と実際の判断、学習方法・支援を渡す。方針の記述を技術的な制御の実装済みとは扱わない。

#### SEC-07: アプリの根拠から、要件に合う配備・自動化の定義へ進む

章内を「要件とTerraform」「Azure Pipelines」「追加要件への横断変更とレビュー」に区切る。
App Service（Linux）の単一アプリを仮想構成の第一候補とするが、Python・起動方法・SQLiteの保存保持・公開制約への適合を確認するまで採用確定にしない。
最小骨組みと初期要件から主要部を生成する。CIを何で開始するかをDR-13、開始後に必要な品質確認を経て進む条件をDR-06・DR-07で分けて考える。
初期要件はDR-01〜DR-10とDR-13、追加要件は環境別設定・state分離のDR-11と同一成果物再利用のDR-12とする。アプリACを置き換えない。
SEC-07では、参加者版の起動・依存・確認方法を配備要件へ接続し、Terraformの入出力とパイプラインの設定・成果物・進行条件を対応づける。
CDは通常CIから参照しない別定義を第一候補とし、接続・適用・パイプライン実行は行わない。準備したローカル確認と要件・定義の照合からS5を判断し、配備成功とは呼ばない。
S4の未コミット差分と、将来CIが取得する版を同一視しない。生成・追加要件の差分・レビューと、実施したローカル確認、未設定・未検証を分けて記録する。
講師教材で学習を続けた場合は本編の未達を残し、生成・変更の自力の成果と支援を区別する。SEC-08へは観察を渡すが、初回生成と追加要件対応を同条件の比較実験にしない。

#### SEC-08: 比較の根拠を、自分の次の開発手順へ変える

SEC-08では、前工程の一場面を根拠から読み、比較材料と改善仮説を分ける。前工程、準備、A/B本試行、比較後の分析・手順作成、講師支援の数値を混ぜない。
AC-08の件数不整合を扱う独立教材で、関連ファイルの明示だけを変える。各条件1回のA/B一組を学習用の最小構成案とし、品質・時間・人の負担と、取得できたAI利用量を比較する。
試行の条件差、未完了、欠測、単発結果の限界を説明し、限定採用・追加評価・見送りを判断する。Bの勝利や削減率が出るまで繰り返さない。
本文内の改善設計シートへ「比較の根拠」「採否と理由」「次の手順」をまとめる。講師付きでは講師／TAがシートと参照だけから開始・終了確認・停止と戻し先を説明し、必要な訂正後に再確認する。
自習では本人がシートだけで説明し直し、ヒント・解説で不足を補って先へ進む。自己確認を第三者確認に読み替えず、実際の確認者がいなければその項目を未実施とする。
第三者確認は個人演習の成果への確認であり、ペア開発への変更ではない。講師付きの確認者・人数・枠はQ-001・Q-011で確保する。
比較中の条件と比較後に作った改善案を区別し、机上確認を再実行・再測定の成功にしない。
共通課題の手順を具体化してから、一つの一般化した自分の仕事について、調べ直す情報と次の一つの試行を考える。実顧客の情報や未確認の社内標準は持ち込まない。
本編S0〜S5、比較課題の修正成否、自力の実行・測定、記録読解・支援、自己確認、第三者確認、S6の評価学習を別々に残す。必要な材料・手順・第三者確認が不足するS6判定は保留しつつ、自習で確認できた学習を残して先へ進める。

引き継ぎには、合意した条件、確認済みの事実、未解決事項、次の担当が行うことを残す。
会話を切り替えたときに、前の履歴が自動共有されることを前提にしない。
長い全文履歴ではなく、必要な根拠と参照先を渡す。

### 9.3 SEC-01へ入る前の開始確認

講師は、参加者版で成立する起動・確認手順を事前に準備する。参加者は自分の対象で実際に確かめた範囲と、講師の画面・記録で確認した範囲を分ける。
S0はアプリの開始状態の確認であり、後続の新機能、独自Agent・Skillの完成、厳密な利用量計測を要求する状態ではない。

| 確認対象 | 開始前に具体化すること | 不足する場合 |
| --- | --- | --- |
| 教材の版 | 参加者版の識別、派生元と教材固有の変更、作業コピー、既存差分 | 版が不明なまま比較や実装へ進まず、講師へ戻す |
| 起動と依存 | 配布版に実在する手順、必要な依存、実行場所、許可する操作 | 環境準備へ戻す。当日の無断導入で穴を埋めない |
| データと実行対象 | 手動用DBとテスト用DB、初期化条件、サーバー・ポート、デモ操作後の変更 | 対象を識別できるまで更新・リセットせず、講師のデモ等へ切り替える |
| 開始時の確認 | 絞り込み未実装の開始契約と既存操作について、実行した確認と結果 | 起動・収集不備、既知の失敗、未実施を区別し、S0の不足を残す |
| Copilotの利用条件 | 最新Stable版とCopilot拡張、非Previewの実行基盤・機能、候補から指定した主モデル、既存指示、読取・検索と承認の範囲 | 講師記録で学べる範囲と必須の実操作を分ける。Previewや別モデルを無断で使わず、必須機能の不足は実施計画へ戻す |
| 観測と記録 | 対象版・行動・品質の記録方法、取得できる利用量と範囲、代替材料 | 数値は未取得として残す。アプリの起動成功や失敗とは別に扱う |
| 参照と配布 | 必要資料の閲覧、完成例への依存、解答・ヒントの提示範囲 | 参加者が使える資料へ整理し、権限の不足を推測で補わない |

開始版の「有効な検索を拒否する」という確認を、SEC-05の検索実装後にも無条件で要求しない。段階ごとの検証契約はQ-005で揃える。
参加者自身のS0が未達でも、講師デモで導入の観察は進められる。ただし本人の実行成功にはせず、自分の本編へ戻る前に不足する開始確認を行う。
環境・観測はQ-002・Q-003、参加者版と復旧はQ-005、資料へのアクセスと配布はQ-010で具体化する。

### 9.4 コピー・担当・会話を切り替える手順

これは切り替えの節目の確認であり、毎回同じ全体調査をやり直すことや、すべての要求で新しい会話を作ることを求めない。
各比較の本試行に新しい会話と独立した開始状態が必要な点は、個別セクションの条件に従う。

1. 移動前の作業について、対象版・差分・DBの状態、取得済みの根拠、未完了の処理を記録する。操作が止まったことだけで完了にしない。
2. 移動先のセクション・教材・試行ID、開始版、作業コピー、DB・サーバーを照合する。会話の切り替えをコードやデータの初期化とみなさない。
3. その対象で使う指示・担当・Skill・モデル・実効ツールを確認する。比較では固定条件を守り、定義変更や追加ヒントを同じ条件だったことにしない。
4. 次の仕事に必要な依頼・品質条件・根拠だけを渡す。本編では採用済み計画と最新の根拠を使い、比較の本試行には共通依頼と指定された入力だけを使う。準備会話、別条件の解法、講師の解説を混入させない。
5. 本編へ戻すときは、採用した指示・定義の差分と記録を確認し、既存の変更を上書きしない。比較用コード・DB・診断変更は戻さず、定義の配置・参照・適用を本編でも確かめる。
6. 必須の入力・権限・確認が足りなければ、該当セクションの準備・確認へ戻す。代替教材を使う場合は元の不足を残し、対象と支援内容を明記してから再開する。

独立した演習教材の開始版は本編の進み具合から都度作らず、講師が準備した版を使う。SEC-03は同じ開始版、SEC-04は同じ共通小差分、SEC-06はAND/ORの正常・欠陥・修正版、SEC-08は件数不整合の同じ欠陥版を、それぞれの用途に合わせて識別する。
定義や記録を引き継いでも、別の版で得た実行結果は移動先の成功の根拠にはならない。S3・S4・S5・S6の判定は、各セクションの対象と根拠へ戻って行う。

### 9.5 進行量と区切りの判断

SEC-02〜08には合計48段階、開始48本・追加48本のプロンプト案がある。これは設計上の案の数であり、必須の送信回数や所要時間ではない。
準備・分析の依頼と、比較の本試行で共通に使う依頼を分ける。追加プロンプトは不足に応じて選び、本試行中の介入はその試行へ記録する。
段階を送信回数で消化せず、成果・根拠・人の判断で区切る。必要な実装・追加検証の反復は残し、不足のない場面へ追加質問を機械的に送らない。
進行量だけを理由に、確認済みの必須学習を省略したり、講師デモへ置き換えたりしない。支援によって学べた範囲と、自力の実施を区別する。

実施枠と配分は未確定であり、段階数から時間を推定しない。
Q-011の試走では、説明・参加者の操作・切り替え・記録・確認・復旧の負荷を観察し、追加質問やヒント、記録の重複、発展範囲を調整する。必須範囲を変える判断は、既存のD-IDに対する変更として別途扱う。
実施時点の最新Stable版と指定モデルで直前確認し、開催中は版・モデル・設定を揃える案とする。直前の更新があれば影響箇所を再確認し、古い版での試走だけを最新環境の根拠にしない。
個人操作と講師／TAの確認待ちを含めて枠を調整する。収まらない場合は分割開催を優先する案とし、必須の実践を無断でデモへ置き換えない。

### 9.6 比較の目的を混ぜない

| 場面 | 主に変えるもの・学ぶこと | 結論にしないこと |
| --- | --- | --- |
| SEC-03 | A/Bで共通指示の改訂、B/Cで条件付き指示の追加 | 指示が常に有利、または個々の一文の効果を立証したという結論 |
| SEC-04 | R0/R1でレビューAgent、V0/V1で検証Skillの有無 | 四条件の要因実験、AgentとSkillのどちらが優れているかという順位 |
| SEC-06 | 欠陥の反例、指摘の採否、HITL／HOTLの関与判断 | 関与方式ごとの費用・欠陥検出能力を同条件で測定したという結論 |
| SEC-07 | 初期要件からの生成と、追加要件への差分対応 | 初回と追加作業の数値差を、そのまま改善効果とすること |
| SEC-08 | 関連ファイルの明示だけを変え、同じ品質で負担を評価する | モデル・指示・Agent・Skillの優劣や、業務全体の削減率 |

指示・定義の準備や結果の分析は、本試行の入力と記録から分ける。共通依頼・品質条件は全条件へ渡し、ヒントや他条件の解法を片方だけへ混ぜない。
新しい会話でも、人の学習効果やサービス側のキャッシュは完全には消えない。単発の比較は判断方法を学ぶ材料であり、再現性や一般的な効果の実証とは分ける。

## 10. 観察記録と到達判定

### 10.1 根拠を受け渡し、転記を増やさない

各記録に、セクション・教材・試行ID、対象版と未コミット差分、データ、出所を付ける。
本編、比較、共通品質演習、判断事例、講師記録の読解を区別し、同じ「成功」という語でまとめない。
S1のメモ、S3以降の引き継ぎ票、SEC-08のシートへ、必要な要点と原記録の参照先を追記する。毎回すべての項目を別の資料へ転記したり、会話全文を複製したりすることは求めない。

| 記録 | 残す内容 |
| --- | --- |
| 要件・計画 | AC-ID、変更対象、対象外、人が確定した判断 |
| 実行 | コマンド、対象の版・データ、成功・失敗・未実施、関連する出力 |
| レビュー | AC-ID、該当箇所、問題条件、根拠、採否、再確認 |
| 人の関与 | 委任範囲、必須判断点、監督情報、介入・継続・再開の理由。事例判断・実操作・支援を区別 |
| 効率 | 所要時間、利用量の取得範囲、探索、失敗、手戻り、未取得値 |
| 引き継ぎ | 残課題、危険な操作、未検証の環境条件、次の確認 |

### 10.2 非Previewで観測できる範囲を使う

| 観測 | 本編での扱い | 判断の限界 |
| --- | --- | --- |
| 品質と完了 | 必須。AC、対象版、差分、成功・失敗・未実施を残す | 品質未達の低利用量を優位としない |
| 経過時間 | 必須。同じ開始・終了点を使い、中断・承認待ちも記録する | 最初の回答の速さや未完了の短さを、完了までの時間としない |
| 人の負担 | 必須。追加情報、ヒント、修正依頼、判断を簡潔に記録する | 回数だけで無駄や必要性を決めない |
| AI利用量 | 非Previewの標準表示で、取得元・単位・範囲を揃えられる値を使う | 取得できない値は未取得。月間合計を一試行の消費としない |
| 詳細な要求・キャッシュ等の診断 | 今回はPreviewを使わず、必須の観測から外す | コンテキスト使用率・文字数・ツール回数から消費を作らない |

標準表示の対応は参加者の版・セッション・契約で事前確認する。Agent Debug Logsの有効化・インポートを代替経路にしない。
指示やSkillの適用についても、非Previewの表示・参照・ツール記録で確認できる層だけを確認済みとする。出力が指示に似ていることを、要求への組み込みの証拠にしない。
講師記録は版・条件・取得方法を示す読解用資料として別に扱う。生ログの全文共有を必須にせず、機微情報を確認した必要な抜粋と原記録の参照先を使う。
AI利用量が取れなければ、取得した品質・時間・行動について評価し、トークンや費用の削減は保留する。比較可能な材料があればS6の評価学習を進められるが、未取得指標の評価や自力測定を達成扱いにしない。

### 10.3 到達・支援・未確認を分ける

テストが起動しなかった場合は、アプリのテスト失敗と区別する。
AIが完了と回答した、操作が止まった、テストの件数だけが増えた、という理由では合格にしない。
講師のチェックポイントへ移った場合は、参加者自身が作成した成果と、提供された成果を分けて記録する。

## 11. 安全な復旧と対象外

途中参加・遅延に備えるチェックポイントは後続で準備する。
使用するときは参加者の変更を別途保持し、別の明示的な作業コピーから再開する。
コードの復元、デモDBのリセット、会話の切り替えは別の操作であり、一つの操作ですべて戻るとは説明しない。
完成例パッチを参加者の変更へ上書きしたり、未コミット変更を一括破棄したりしない。

| 講師が準備する復旧用教材の案 | 再開できる学習 | 消してはいけない未達 |
| --- | --- | --- |
| 開始版と起動・既存確認の記録 | 現状調査、指示設計 | 本人の環境準備・S0の不足 |
| 指示・Agent・Skillの準備済み版 | 本編での適用確認、実装 | 自力の定義・比較・適用で残った不足 |
| 絞り込みの実装候補と対象版の記録 | レビュー、追加検証 | 本人の実装・代表ACのテスト先行の不足 |
| 品質確認後の版と根拠 | 定義構成、評価と改善 | 本人のS3・S4の不足 |

これらは用意する教材の区分であり、S状態と同名のGitタグが存在するという意味ではない。完成済み部分は必要時だけ提供する。
比較演習には各条件の独立した開始コピーを別に用意し、復旧用の完成版を比較の開始状態へ混ぜない。
参加者は不足を残したまま後続の学習へ進めるが、前工程の到達記録まで講師の成功で埋めない。

本編で追加しないものは、実認証、利用者ごとの権限、監査証跡、通知、添付、金額処理、多段階承認、再申請、ページ分割、実クラウドへの配備。
アプリはローカル研修用であり、実業務データを登録せず、外部公開しない。
アプリのローカル動作と、Copilotのネットワーク利用は別である。
