## 1. このセクションの役割

以後の演習で「AIがどのように作業を進めたか」を観察するための共通言語を作る。
製品の全機能やモデル一覧を紹介する導入にはしない。
社内申請ポータルを題材に、指定した範囲の説明を得る依頼と、根拠を集めて次の判断材料を揃える依頼を対比する。
編集・実行を伴う反復は後続の学習へつなぎ、この導入では先取りしない。

開始状態は共通シナリオのS0。環境構築はこのセクションの演習に含めない。
開始前の確認と不足時の扱いは、[共通シナリオ](../common-scenario.md)第9.3節にまとめる。
終了時にもアプリの機能は変更せず、参加者が「何を任せ、どこで止め、何を見るか」を説明できることを目指す。

**今回の通常経路:** 題材と変更依頼を知る → 講師の調査を観察する → 一場面の根拠と人の判断を自分で説明する → SEC-02へ問いを渡す。
開発経験5年以上の個人参加を前提に、開発工程の一般論より実際の判断へ説明を絞る。操作や用語の経験差は、既定で非表示のヒントから補う。
環境・モデル・ヒント・観測の共通条件は[共通シナリオ](../common-scenario.md)第2・10節に従う。最新Stable版でもPreviewの機能を使わず、詳細診断の操作を導入へ追加しない。

## 2. 学習目標

| 目標 | 参加者が示せること |
| --- | --- |
| 協働の理解 | 調査、計画、編集、実行、確認を区別し、人の判断箇所を説明する |
| 行動の観察 | 最終回答だけでなく、読取・検索の成否、得た根拠、再試行・追加調査、人へ返した不明点を追う |
| 文脈の理解 | 入力欄の文章以外にも、履歴、指示、参照、ツール出力が使われると説明する |
| 利用量の理解 | コンテキスト容量、累積処理量、AIクレジット、所要時間を混同しない |

## 3. 講師の準備と参加者への入力

指定版の初期アプリ、架空データ、変更依頼、同じ環境で記録した短いデモを準備する。
デモは実行条件を明示し、再生した記録なのか、その場の実行なのかを区別する。
接続や観測機能に問題があったときは、準備済みの記録へ切り替えられるようにする。

参加者には、ポータルの一覧と基本操作、今回の変更依頼、対象外を渡す。
モデルはGPT 5.6 Luna、GPT 5.6 Terra、GPT-6.1 Terra（推論の度合いMax、Context Size 872K）の候補から、非Previewで利用できる一つを講師が指定する案とする。利用可否とメニュー表示は参加者環境で確認し、講師だけの機能を使わせない。
Copilotへの通信が必要なことと、アプリ本体がローカルで動くことを分けて説明する。

## 4. 進行案

| 段階 | 講師・参加者の行動 | 見るポイント |
| --- | --- | --- |
| 題材を確認 | 一覧、詳細、作成、状態変更を確認する | 今回直す機能と、維持する機能 |
| 質問への回答を見る | 一覧の画面・HTTP処理・データ取得について説明を依頼する | 示された構成が実在する参照先へ結び付くか |
| 調査を任せる | 絞り込みの変更依頼から、必要なファイル・既存テスト・未決仕様を調べてもらう | 得た根拠から追加の調査を選び、人の判断へ返す流れ |
| 委任の境界を決める | 実装前に人が確認する事項を挙げる | 仕様、依存追加、実行、公開などの判断 |
| 利用量を観察 | 取得できる表示と行動記録を確認する | 数字の単位、取得範囲、分からないこと |

二つのデモは質問の内容が異なるため、利用量の大小を公平なA/B比較として扱わない。
ここでは観察の方法を学ぶ。指示の定義前後を扱う比較体験はSEC-03、品質・利用量の評価方法を整理する別の比較はSEC-08で行う。

どちらの依頼でも読取・検索を使い得る。「質問への回答ならツールを使わず、エージェントなら必ず編集する」という区別ではない。
見せる違いは、指定範囲の説明を得ることと、目的に必要な根拠・不足を調べて次の判断へつなぐことにある。
講師は、実際のデモまたは出所を明示した準備済み記録から、次の対応を一つ示す。

| 観察するつながり | 確かめること |
| --- | --- |
| 読んだ根拠 → 追加調査 | どのファイル・記述を受けて、何を確かめるために次の参照先を選んだか |
| 調査結果 → 人の判断 | コードだけでは確定できない条件を、どの根拠と質問で人へ返したか |

この表は観察の設計であり、取得済みの実行記録ではない。ライブで該当場面が現れなければ、条件を明示した講師記録を使い、その場で起きた行動として説明しない。
ツールの回数や回答の長さを増やすために、不要な調査や架空の失敗を加えない。

## 5. デモ用プロンプト案

```text
このアプリの申請一覧は、どの画面・HTTP処理・データ取得処理で構成されていますか。
根拠となるファイルを示してください。
ファイル編集やコマンド実行はせず、読んだ事実と推測を分けて説明してください。
```

続いて、変更の判断材料を集める依頼に変える。

```text
部署と申請状態の絞り込みを追加する前に、関連するファイルと既存テストを調べてください。
読取・検索だけを使い、ファイル編集、コマンド実行、依存の追加、DB更新はしないでください。
得た根拠に応じて必要な追加調査を行い、まだ実装しないでください。
変更が必要そうな場所と、人に確認すべき仕様を分けて示してください。
```

この二つの例は依頼範囲を示すためのもの。文章での禁止だけを権限制御とみなさず、デモでも利用するツールを絞る。
モデルの非公開の内部思考を求めず、観察できる行動、根拠、結果について説明してもらう。

## 6. トークンエコノミーの説明

| 概念 | 演習での説明 | 避ける説明 |
| --- | --- | --- |
| 入力コンテキスト | 指示、履歴、参照、ツール出力を含む、その要求に必要な情報 | 「入力欄の文字数だけが入力コスト」 |
| コンテキストウィンドウ | 一回のモデル要求で扱える情報量の上限 | 「残量表示から累積の請求額が分かる」 |
| 累積利用量 | 繰り返した要求や生成に伴う利用量 | 「最後の回答が短ければ全体も安い」 |
| キャッシュ | 対応する環境で入力の一部が再利用される仕組み | 「過去の会話は常に無料」 |
| モデル選択 | 品質と再試行を含めたタスク単位で評価する | 「単価が低いモデルが常に最適」 |
| ツール | 調査・実行の能力。出力も文脈へ入る | 「ツールが多いほど必ず有利」 |

その要求に適用される指示は、モデルへの入力コンテキストに含まれる。
毎回入力欄へ書かなくて済むことと、入力トークンが不要になることは別である。
ユーザーの一つの依頼の中でも複数のモデル要求が発生し得るが、すべての指示ファイルの全文が毎回必ず入るとは限らない。
[SEC-03](03-custom-instructions.md)では常時適用と条件付き適用を使い分け、指示の負担と、探索・誤り・手戻りの変化を品質と合わせて観察する。

ワークスペースの意味検索は、毎回リポジトリ全文を入力することと同じではない。
必要な情報を絞ることと、根拠を不足させることは区別する。
手順をスクリプトへ移す、Skillへ分ける、担当を増やす、といった工夫も、それ自体で節約を保証しない。

## 7. 観察メモと終了条件

| 行動 | 目的 | 得られた根拠 | 次に必要な判断 |
| --- | --- | --- | --- |
| ファイルを読む | 一覧処理の所在を知る | 実際のファイル・関数 | 追加で読む場所 |
| テストを探す | 既存の契約を知る | テストの対象と期待 | 新しい条件との差 |
| 不明点を返す | 仕様を勝手に補わない | 未確定の条件 | 人が採用する仕様 |

参加者が、任せてよい調査、まだ始めない編集、確認が必要な操作を説明できれば次へ進む。
確認には、観察した一場面の根拠と、その後の追加調査または人への確認を使う。AIの回答の読み上げだけを理解の根拠にしない。
トークンの厳密な内訳を取得できることは、この導入の終了条件にはしない。
数値が見えない場合は未取得と記録し、行動の観察までを実施する。
Agent Debug Logs等のPreview診断へ切り替えず、標準表示で見える単位・範囲を説明する。コンテキスト占有率やツール回数を消費へ換算しない。

## 8. つまずきと代替進行

| 状況 | 対応 |
| --- | --- |
| アプリが起動しない | 事前環境の問題として切り分け、講師の画面で題材の説明を進める。参加者の実行成功とはしない |
| エージェントが即座に編集しようとする | 中止して変更の有無を確認し、調査専用の設定または利用可能な読み取り手段へ戻す |
| 説明が一般論だけになる | 対象ワークスペースと参照ファイルを確かめる |
| 数字だけに注目する | 品質を満たしていない低利用量は成功例ではないと示す |

発展課題は、同じ根拠を得るために不要だった探索を一つ説明すること。
モデルの順位付け、課金制度の網羅、複数エージェントの並列実行は扱わない。

## 引き継ぎ・未決事項・出典

モデル選択の詳しい説明は[補足ガイド](../../reference/model-selection.md)、
最適化の全体像は[Token Economy実践ガイド](../../reference/token-economy.md)を参照する。
演習では講師指定の主モデルを固定し、Auto／HydraFusionは解説のみとする。
ガイドの全文を導入デモへ詰め込まず、必要な節を講師の説明に使う。

次のSEC-02へ、初期状態の確認、変更依頼、人が確定すべき仕様の候補を渡す。
変更依頼はこの段階で提示済みとするが、SEC-02ではまずアプリ全体の機能・構造を調べ、改善候補を幅広く検討する。
その後、本編の共通課題である絞り込みの要件・計画へ戻る。候補ごとに別の機能を実装する構成にはしない。
SEC-08では、この導入で学ぶ観察を、共通小課題の比較・採否・改善手順へつなぐ。品質・利用量・人の負担を分け、使い分けと開始・確認・停止を他者へ説明できるかを確かめる。
導入や前工程の数値をそのA/Bへ合算せず、記録は仮説の材料として使う。改善設計シートと第三者の机上確認を、本編の未達を補う実行根拠にはしない。
参加者像・個人参加・ヒントの基本条件はD-028・D-029、環境制約とモデル候補はD-030・D-031で確認済み。残る支援はQ-001、利用可否・権限はQ-002、観測の可否はQ-003で管理する。
