## 1. 位置づけと学習目標

主目的は、必要な品質を守りながらCopilotと開発する進め方を、観測した根拠から選び、他の人が再試行できる形で説明できるようにすることである。
各演習の感想や便利だった機能を列挙するのではなく、共通小課題の比較、採否の判断、改善手順の作成、第三者の机上確認を通してS6へ進む。
自分の業務への応用は、共通課題の手順を具体化した後に行う。最初から異なる自由課題を持ち寄って数値を比べる構成にはしない。

**今回の通常経路:** 前工程の一場面を読む → 個人でA/B一組を実行する → 条件・品質・負担から採否を決める → 改善手順を書く → 講師／TAの机上確認を受ける → 実務の次の試行へ置き換える。
各条件1回を学習用の最小構成案とするが、単発結果を一般的な効果の実証にしない。必要な反復・実行枠は試走で判断する。
機能・モデル・段階的ヒントと観測は[共通シナリオ](../common-scenario.md)第2・10節に従う。講師付きでは第三者確認を行い、自習では自己確認で先へ進む。D-036に従い、自己確認やAIのコメントを第三者確認として記録しない。

| 学習目標 | 参加者が示す成果 | それだけでは達成としないもの |
| --- | --- | --- |
| 評価できる | 比較条件と品質を確かめ、利用量・時間・人の負担から言える範囲を説明する | 小さい数値やAIの自己評価だけで選ぶこと |
| 使い分けを決められる | 今回の依頼、指示、役割、手順、確認資産、人の判断を必要な理由で分担する | 習った機能をすべて追加すること |
| 再試行できる形にできる | 入力、作業範囲、確認方法、終了・停止条件、次の試行条件を具体化する | 「適切に指示する」「レビューを強化する」とだけ書くこと |

「短いプロンプト」「安いモデル」「多くの担当」のどれかを常に正解にしない。
トークン削減、Bの勝利、全機能の利用を合格条件にせず、差なし、追加評価、見送り、今回は新しい定義を作らないという判断も認める。
同じ開始条件と手順を再現できることと、同じ生成結果・利用量が必ず得られることは別である。

前工程からは、次の判断方法を受け取る。

| セクション | SEC-08で使う学び | 今回のA/Bへ混ぜないもの |
| --- | --- | --- |
| SEC-01 | コンテキスト、累積利用量、観測できる行動、人の判断を分ける | 内容の違う導入デモの数値 |
| SEC-02 | 対象、根拠、AC、維持条件、計画から依頼を作る | 改善候補ごとの別実装や本編の途中状態 |
| SEC-03 | 恒常的な情報と今回だけの要求、適用と遵守を分ける | A/B/Cのコード、指示変更と参照指定の同時比較 |
| SEC-04 | 担当の責務と、実行担当が使う再利用手順を分ける | R0/R1・V0/V1、診断・補助試行、定義作成の数値 |
| SEC-05 | 変更と確認を対応づけ、事実と仮説から修正する | 本編の途中コード・DB、失敗記録の読解を自分の実行とすること |
| SEC-06 | 根拠から指摘を判断し、委任・監督・介入を設計する | AND/OR演習、判断事例、発展実操作を費用・検出能力の同条件比較とすること |
| SEC-07 | 対応関係、確認できた範囲、未検証事項を引き継ぐ | 初回生成と追加要件の数値、定義や途中成果を比較入力に足すこと |

前工程の記録は仮説を考える材料であり、このA/Bの本試行と合算しない。
S5の定義案を実配備の成功へ置き換えず、本編の未達も残す。SEC-08で評価方法を学んだことが、前工程の実行根拠を補うわけではない。
以下の必須範囲は詳細DRAFTとしての提案であり、具体的な教材・試行数・進行の成立性はQ-009・Q-011で確かめる。

## 2. 共通課題、比較する問い、品質の正本

### 2.1 小さな件数不整合を扱う

AC-08の「結果件数と全体集計の区別」を使い、検索結果は正しいがAPIの`count`に全申請件数を返す小さな不整合を直す案とする。
絞り込み実装済みの比較教材を用意し、検索未実装の開始版が検索キーを拒否する状態や、SEC-06のAND/OR欠陥とは分ける。
共通シナリオの説明用データなら、複合条件の`items`はF1だけ、正しい`count`は1、全体集計は6となる。

本編にこの不具合があることは前提にしない。参加者が既に直した作業コピーを使い回さず、同じ開始状態から独立したA/B用コピーを作る。
説明用のF1等と実際のIDの対応、専用fixture、デモデータの初期投入の扱いは講師が揃える。参照元の初期データと混ぜて期待件数を変えない。
この比較用アプリは未実装であり、具体的な開始版、参照ファイル、確認方法はQ-009で教材化前に確定する。

### 2.2 一つの問いに限定する

> 関連ファイルを最初に明示すると、同じ品質に到達するまでの探索や手戻りはどう変わるか。

主仮説は「関連ファイルを明示すると、探索と手戻りを減らせる場合がある」。
Aも目的・AC・対象外・確認条件を十分に伝え、必要な調査を許す。曖昧な依頼、探索禁止、弱い品質条件を置いて不利にしない。
Bは同じ依頼に関連ファイルへの参照だけを追加し、修正方法、答えの行、解答差分、片方だけのヒントを渡さない。

既存指示が既に十分な道案内になっていれば、差が出ない可能性がある。
差を作るために、片方の有効な指示や安全条件を外さない。この結果から指示、Agent、Skill、モデルの有無・優劣まで結論を広げない。

### 2.3 品質条件を先に固定する

| 確認対象 | 共通の確認で確かめること |
| --- | --- |
| 検索結果と件数 | `items`のID集合・内容・長さと`count`が期待に合う。件数だけを合わせない |
| 単独・複合・0件 | 各条件とANDの意味を維持し、正常な0件をエラーへ変えない |
| 全体集計 | 検索結果を絞っても、データ変更のない全体集計を変えない |
| UI/APIと既存操作 | 比較課題に必要な共通の回帰を実行し、別経路を壊していない |
| 変更範囲 | 無関係な機能・依存を追加せず、条件を満たすために確認を削除・弱体化しない。開始版から既にある別の不具合は、修正もテストの追加もせずに報告する（D-050） |

講師は正常版で通り、欠陥版では意図した理由で失敗し、修正後に同じ確認で回復することを準備段階で確かめる。
期待集合は修正対象の処理から計算して自動的に追随させず、ACとデータから決める。起動不備、テスト未収集、未到達のアサーションは欠陥検出の成功にしない。
正本の確認、依存、作業ディレクトリ、データを両条件で揃える。完成例パッチの適用可否や、解答と同じ差分であることを正しさの基準にしない。

追加テストの扱いも共通方針にする。片方だけ簡単な確認へ切り替えたり、落ちるテストを消したりしない。
正本の確認自体に不備が見つかった場合は、結果を保持して比較を止める。訂正後の共通条件で新しい試行を準備し、以前の結果を訂正後の成功へ貼り替えない。
同じ品質に到達していない試行同士を、費用だけで優劣比較しない。

## 3. 開始条件と比較の分離

### 3.1 受け取る材料

| 入力 | 開始時に確認すること |
| --- | --- |
| 前工程の一場面 | 出所、対象版、何を行ったか、観測事実と未確認が分かる |
| 共通課題と条件票 | 目的、AC、対象外、確認手順、試行の開始・終了・打ち切りが決まっている |
| A/Bの開始コピー | コード・未コミット差分・DB・依存が同じ初期状態で、作業先を識別できる |
| 指示・担当・手順 | 採用済みのものを両条件で揃え、適用範囲と実効ツールを確認できる |
| 観測方法 | 取得元、単位、範囲、必要な事前設定、欠測時の代替が分かる |
| 本文内の記入形式 | 比較の根拠、採否、次に使う手順を一つのシートへ記入できる |

前工程を完了していない場合も、講師の版・記録を使って評価を学べる。
その際は本編の状態、講師提供部分、記録読解、自分の操作を区別する。記録がない場面を、もっともらしい成功談や架空ログで補わない。
本編で手戻りが起きていない場合は、問題なく進んだ場面とその根拠を選んでよい。

### 3.2 A/Bで揃える条件

| 条件 | A | B |
| --- | --- | --- |
| 目的・AC・対象外 | 同じ | 同じ |
| 初期コード・データ | 同じ開始スナップショット | 同じ開始スナップショット |
| モデル・推論設定 | 同じ固定設定 | 同じ固定設定 |
| セッション種別・担当・ツール | 同じ | 同じ |
| 共通・条件付き指示・Skills | 同じ | 同じ |
| 人の関与方針 | 同じ委任範囲・許可するコマンドの範囲・必須判断点・介入条件 | 同じ委任範囲・許可するコマンドの範囲・必須判断点・介入条件 |
| 会話 | 新しい会話 | 別の新しい会話 |
| 出力形式・品質確認・打ち切り | 同じ | 同じ |
| 変更する条件 | 関連ファイルを明示しない | 調査済みの関連ファイルを明示する |

演習では講師指定の主モデルを固定し、Auto／HydraFusionへ切り替えない。
担当や委譲先の設定も確認し、主モデルの選択だけで内部の全処理が同じと推測しない。取得できた実際の設定と、確認できなかった範囲を記録する。
人の関与方針を固定することと、実際の介入が同じ回数になることは別である。事前の介入基準と、その場で何を追加したかを残す。

開いているファイル、選択範囲、添付、親・ユーザー・組織の指示、解答資料へのアクセス等も確認する。
共通の品質手順への参照と、Bだけへ追加する実装関連ファイルの参照を区別する。参照の指定方法と対象版は講師が固定する。
参照を指定したこと、実際に読み込まれたこと、正しく利用したことは別であり、診断できない層を推測で補わない。

### 3.3 会話、コピー、記録を分ける

段階1・2の準備相談、段階3のA、段階3のB、段階4以降の分析を区別する。
準備相談の履歴や、先に得た解答・差分を、A/Bの開始会話へ引き継がない。Bには条件票で指定した関連ファイルへの参照だけを追加し、その一覧をAへ持ち込まない。
履歴を引き継ぐ分岐を、空の新規会話として扱わない。
第4節のプロンプトを、一つの会話で順番にすべて実行する設計ではない。

会話の切り替えは、コード・DB・指示・起動中のプロセスの初期化ではない。
既存の作業や他条件を一括で巻き戻さず、準備した独立コピーから開始する。講師の解答や比較条件を記載した設計資料が、試行側へ自動で入らない配布構成も確認する。
条件を揃えられなければ参考観察とし、一変数比較として扱わない。条件不成立を黙って除外せず、理由と支援への切り替えを記録する。

## 4. 6段階の進行とプロンプト

| 段階 | 作業 | 主な成果 |
| --- | --- | --- |
| 1 | 経験から根拠を取り出す | 一場面の事実・解釈・未確認と、改善の仮説 |
| 2 | 比較条件を確定する | 共通課題、A/Bの差分、固定条件、観測・介入の条件票 |
| 3 | A/Bを実行する | 独立した試行の品質・利用量・時間・介入・原記録 |
| 4 | 採否を判断する | 比較可能性、品質、負担、限定採用・追加評価・見送り |
| 5 | 改善手順を完成させる | 依頼・指示・役割・確認・人の判断を分担したシート |
| 6 | 引き継ぎと実務への置き換え | 机上確認による修正と、移植先の再確認・次の試行条件 |

開始・追加各6本、計12本のプロンプト案を示す。
段階3の開始プロンプトがA/Bで共通に使う実行依頼であり、他は準備・分析・手順作成を支援する依頼である。
段階3の追加プロンプトも、両試行の終了・打ち切り後の記録整理に使う。片方の試行を有利にする途中ヒントとして無条件に投入しない。
試行中の質問・修正依頼が必要な場合は共通の介入方針に従い、実際の内容と条件への影響を記録する。

### 段階1: 経験から根拠を取り出す

**目的と入力:** 前工程から一場面の記録を選び、感想を観測事実と仮説へ分ける。

**参加者の作業:** 何を依頼し、何を参照し、どの確認・判断をしたかを追う。
不要だった可能性のある反復と、必要だった再読・回帰確認を区別する。本編の記録と講師の記録を混ぜない。

**講師の介入:** 「どの記録から言えるか」「別の説明はあるか」を問う。
手戻りを探すために問題を創作させず、問題なく進んだ条件も整理させる。

**開始プロンプト:**

```text
指定した前工程の一場面について、依頼、参照、作業、確認、人の判断を整理してください。
記録で確認できる事実、私たちの解釈、まだ分からないことを分け、根拠の参照先を示してください。
必要な再読・再確認と、改善できる可能性のある反復を区別してください。
記録のない行動や利用量を補わず、ファイル編集・再実行はしないでください。
```

**追加プロンプト:**

```text
今の整理で、事実より強く言い切っている箇所はありませんか。
参照先を最初に示すことで変わりそうな行動と、変わらない品質条件を説明してください。
他の改善候補は次回用へ分け、今回の比較条件へ追加しないでください。
前工程の数値をSEC-08のA/Bの測定値には使わないでください。
```

**成果・人の判断・終了条件:** 一場面の出所と根拠を示し、観測と仮説を分けられる。
別の改善候補が見つかっても、共通の比較課題は変えない。記録が不足する場合は不足を残し、出所の分かる講師記録で学ぶ。

### 段階2: 比較条件を確定する

**目的と入力:** 共通課題、AC、品質確認、条件票、独立コピーの準備情報から、比較の成立条件を確認する。

**参加者の作業:** A/Bの依頼差分を読み、変えるのが参照指定だけであることを確認する。
モデル、指示、担当、ツール、人の関与、観測範囲、実行順と打ち切りを確認し、不足は実行前に講師へ戻す。

**講師の介入:** Aの目的や品質条件を弱くしていないか、Bだけに解法や追加ヒントが含まれていないかを確認する。
準備相談を試行会話へ持ち込まないこと、独立したDB・作業コピーを使うことを確かめる。

**開始プロンプト:**

```text
共通課題、品質確認、A/Bの条件票を読み、変える条件と揃える条件を整理してください。
A/Bの依頼差分に、参照指定以外の解法・ヒント・品質条件の差がないか指摘してください。
開始版、データ、会話、指示・担当、観測範囲、介入・打ち切りで未確定の項目を挙げてください。
この相談では実装・実行をせず、不足を推測で埋めないでください。
```

**追加プロンプト:**

```text
比較結果を歪める可能性のある入力や条件差を、条件票へ追記する案にしてください。
既存の有効な指示や安全条件をAだけから除かないでください。
何が起きたら参考観察へ切り替えるか、何を原記録に残すかを示してください。
準備相談の内容をA/Bへ渡さずに開始できるかも確認してください。
```

**成果・人の判断・終了条件:** 共通の開始・終了・確認・介入条件を人が採用し、違いを説明できる。
必要な条件が未確定なら実行を始めない。利用量を取得できない場合は、比較できる範囲と代替を先に明記する。

### 段階3: A/Bを実行する

**目的と入力:** 同じ開始状態と採用した条件票を使い、参照指定の違いによる作業を観測する。

**参加者の作業:** 実行順を記録し、独立した会話とコピーで共通依頼を実行する。
品質確認、差分、結果、利用量、経過時間、介入を保存する。先の解法を後の試行へ教えず、未完了や環境不備も残す。

**講師の介入:** コピー・DB・会話の取り違えを確かめ、共通の支援・停止方針に従う。
比較を成立させるために安全上必要な介入を控えない。停止した場合は理由と実際の変更・消費を記録する。

**開始プロンプト:**

```text
検索結果の件数が一覧の内容と一致しない問題を調べ、修正してください。
共通シナリオのAC-08を満たし、検索条件、結果の内容、全体集計は壊さないでください。
同じ品質確認を実行し、変更点、結果、未確認事項を示してください。
実装に必要な調査は行えますが、無関係な機能や依存は追加しません。
```

Bではこの共通依頼に、条件票で指定した関連ファイルへの参照だけを追加する。共通の課題票・AC・品質手順は両方に同じように渡す。
依頼文、参照の指定方法と対象、実際の追加介入を記録する。添付したことだけで、その全文が読み込まれ正しく使われたと扱わない。

**追加プロンプト:**

```text
両試行は終了または打ち切り済みです。指定した保存記録だけを読み、A/Bの結果欄を整理してください。
対象版、実行した品質確認、成功・失敗・未実施、介入、取得できた指標と原記録を対応づけてください。
不足を補う再実行や修正はせず、未取得・未完了・条件差をそのまま残してください。
この整理の利用量をA/B本試行へ合算しないでください。
```

**成果・人の判断・終了条件:** 両試行の開始・終了状態、実行結果、条件差が追える。
AIの完了宣言や動作停止を成功とせず、共通品質確認の実行と結果を読む。条件不成立は参考観察として記録し、第6節の代替へつなぐ。

### 段階4: 採否を判断する

**目的と入力:** 保存した条件票・差分・品質結果・指標を使い、何が比較でき、何を採用できるかを判断する。

**参加者の作業:** 条件、品質、負担の順に読み、観測事実と原因の仮説を分ける。
限定的に試す、追加評価、見送りから判断し、根拠・適用範囲・反証になり得る情報を残す。

**講師の介入:** 少ないトークンや短い回答だけで選んでいないかを問う。
不要な反復と必要な確認、AIの負担削減と人への負担移転、数値の欠測と0を区別させる。

**開始プロンプト:**

```text
A/Bの条件と保存記録を、比較条件の成立、品質への到達、利用量・時間・人の負担の順に評価してください。
観測した事実、原因の仮説、この記録だけでは判断できないことを分けてください。
品質未達や未取得値を補完せず、一般的な削減率へ広げないでください。
採否の候補と必要な追加確認を示し、最終判断は人へ返してください。
```

**追加プロンプト:**

```text
提示した採否について、反対の判断を支持し得る根拠や条件差を確認してください。
関連情報の準備・保守や、人の確認負担を無視していませんか。
この結果を使える範囲と、次に一つだけ変えて確かめる条件を示してください。
差なし・悪化・見送りも結果として残し、採用を前提に説明を作らないでください。
```

**成果・人の判断・終了条件:** 人が採否と理由を記入し、言える範囲と未確認を説明できる。
比較結果が弱ければ追加評価や見送りにする。代表的な実務課題での信頼性を、この小課題だけで認定しない。

### 段階5: 改善手順を完成させる

**目的と入力:** 共通課題の比較と採否、採用済みの指示・役割・確認資産を使い、次に依頼する具体的な手順へまとめる。

**参加者の作業:** 第8節のシートへ依頼文、参照、責務、確認、人の判断、停止・戻し先を記入する。
今回の要求と継続情報を分け、既存のものを使う・限定する・新規作成しない理由を説明する。

**講師の介入:** 「適切に確認する」といった記述を、対象・手段・判断へ具体化させる。
全機能の導入、長い履歴の複製、未知のコマンドの創作を解決策にさせない。

**開始プロンプト:**

```text
人が決めた採否と根拠から、この共通課題を次に依頼する作業手順を作ってください。
今回の依頼、共通・条件付き指示、担当、Skill、確認資産、人の判断の分担を示してください。
入力と参照先、作業範囲、実在する確認方法、終了・停止・戻し先を具体化してください。
既存のものを使う・限定する・今回は追加しない理由を残してください。
これは改善案の作成であり、定義ファイルの変更やアプリの再実行はしないでください。
```

**追加プロンプト:**

```text
改善設計シートのうち、他の人が推測しないと実施できない箇所を指摘してください。
対象版、依頼文、参照、確認結果の扱い、人の判断と戻し先がつながっていますか。
実測した比較結果と、まだ実行していない改善案を分けてください。
参照先やコマンドが不明なら創作せず、確認すべき項目として残してください。
```

**成果・人の判断・終了条件:** シートの三部分がつながり、共通課題で使う手順と採否の理由が具体的である。
共通課題の開始や必須確認に必要な情報が欠けていれば準備資料へ戻る。別の実務環境で調べる事項は未確認として分ける。

### 段階6: 引き継ぎと実務への置き換え

**目的と入力:** 改善設計シートを読み直して作業手順の不足を確かめ、別の業務へ移す際の条件を整理する。講師付きの第三者確認と、自習の自己確認を区別する。

**参加者の作業:** 講師付きでは第9節の三つの問いを講師／TAに説明してもらい、指摘の採否と修正を記録する。自習では本人がシートだけから説明し直し、自己確認の範囲と第三者未実施を残す。
その後、一つの一般化した業務について再利用する方法と調べ直す情報を分ける。業務が未定なら共通課題を使う。

**講師の介入:** 最初は口頭補足で穴を埋めず、シートとそこから参照できる資料で追えるかを見る。
指摘がなければ無理に欠陥を作らせず、開始・確認・停止を説明できた根拠を残す。機密情報を持ち込ませない。

**開始プロンプト:**

```text
改善設計シートについて、実際に行った確認の説明とコメントを整理してください。
講師付きの第三者確認と、自習で本人が行った自己確認を区別してください。
どの版・入力から何を始めるか、何を確認すれば終わるか、いつ止めて誰へ戻すかを対応づけてください。
不足、指摘の採否、人が採用した訂正案を分け、原コメントの参照先を残してください。
第三者がまだ確認していない項目を確認済みにせず、机上確認を実行成功と呼ばないでください。
```

**追加プロンプト:**

```text
修正後の手順を、指定した一つの一般化した業務へ移す場合を整理してください。
再利用できる判断方法と、パス・コマンド・適用範囲・権限・AC等を調べ直す事項を分けてください。
次に一つだけ変えて試す条件と、採用・追加評価・見直しの判断基準を示してください。
未知の組織ルールや実行結果は作らず、S6の根拠と残る不足を人へ返してください。
```

**成果・人の判断・終了条件:** 読み直した手順、確認者・確認範囲と修正の記録、実務の再確認事項がある。
人がS6を判断する。自習では第三者未実施を残して学習を進める。自己確認やAIのコメントを第三者確認へ言い換えず、未実施の改善案や移植先の作業を完了としない。

## 5. 比較の実施プロトコル

### 5.1 開始から記録の確定まで

1. 課題票、共通品質確認、開始スナップショット、依存、データ、設定、観測手段を確認する。
2. A/Bの独立コピーと新しい会話を準備し、準備相談・解答・他条件の差分が入っていないか確かめる。
3. 実行順と条件を記録する。可能なら参加者間でA→BとB→Aを入れ替える。
4. 共通依頼を実行し、調査・編集・確認、追加介入、エラー、設定変更を記録する。
5. 事前に決めた終了・打ち切り条件で止め、品質結果と対象版、差分、指標、原記録を保持する。
6. もう一方も独立した同じ開始状態から実行し、先の結果で依頼を改善せずに記録する。
7. 両試行の記録を確定してから、別の分析用会話や記入欄で整理・評価する。

本試行の範囲は、共通依頼の送信から、事前に定めた品質確認・結果報告の終了または打ち切りまでとする。
エージェント内の修正・再確認はその範囲に含める。結果の悪い要求だけを集計から外さない。
段階1・2の準備、段階3終了後の記録整理、段階4以降の比較分析・手順作成は分けて記録する。

今回の最小構成案は各条件1回のA/B一組。実行枠、具体的な打ち切り、必要な反復・支援はQ-009・Q-011の試走で事前に決める。本書で未測定の所要時間や削減率を置かない。
結果が好ましくないという理由だけでやり直さず、追加試行は目的・条件・識別を残す。支援や条件変更前の結果を消さない。
新しい会話でも、サービス側のキャッシュや人の学習効果は完全には消えない。実行順を入れ替えたことだけで厳密な因果評価が成立したと説明しない。
参加者ごとの環境差が残る記録をまとめ、集団全体の効果やモデルの順位へ一般化しない。

### 5.2 介入、停止、やり直し

| 状況 | 扱い |
| --- | --- |
| 合意範囲の調査・修正・再確認 | 共通方針の中で進め、実際の行動を記録する |
| AIが仕様・範囲の判断を求める | 人が判断し、与えた情報・理由・条件への影響を残す |
| 片方だけに解法のヒントを追加した | 元の試行は条件差付きで保持する。支援後の成果を無介入の結果にしない |
| 起動・依存・観測が準備不足 | 不備と未実施を記録し、その場の無断導入を前提にしない |
| 対象外編集、危険な実行、データの混入 | 安全を優先して停止し、変更と取得物を確認して講師へ戻す |
| 打ち切りに到達 | 未完了として実際の結果を残す。完了までの費用へ外挿しない |
| 設定・品質の正本を変更したい | 条件変更として採否を判断し、必要なら新しい試行IDと独立した開始状態でやり直す |

停止条件をプロンプトに書くことと、実行基盤が技術的に強制することは別である。観測・停止方法を事前に準備する。
停止は変更の取り消しではない。差分と記録を保持し、明示した別コピーで再開する。
接続不備、時間切れ、品質未達を隠すために、履歴・DB・未コミット差分を一括破棄しない。

## 6. 観測、集計範囲、代替学習

### 6.1 記録の中心は四つの軸

| 評価軸 | 記録すること | 単独では判断しないこと |
| --- | --- | --- |
| 品質・完了 | 共通AC、各確認の成功・失敗・未実施、対象版と差分 | AIの完了宣言やテスト件数だけ |
| AI利用量 | 取得できる入力・出力・キャッシュ等、AIクレジット、取得元・単位・範囲 | 文字数、現在のコンテキスト占有率からの累積消費の推定 |
| 所要時間 | 同じ開始・終了点の経過、打ち切り、中断・承認待ち | 最初の応答の速さだけ、未完了の短さ |
| 人の負担 | 追加情報、修正依頼、レビュー、判断、監督、通常の権限承認 | 介入回数の少なさだけ |

試行ID、A/B、順序、開始版、データ、環境、実際のモデル・設定、参照の渡し方、ツール利用、原記録を併記する。
深い診断を全員の必須操作にせず、利用可能な指標から始める。行動の読解では、公開された入出力・参照・実行結果を使い、非公開の内部思考を求めない。
今回の共通記録は品質・経過時間・人の介入とし、AI利用量は非Previewの標準表示から同じ範囲を取得できる場合に追加する。未取得ならトークン・費用の削減は評価しない。
結果欄は未記入から始める。説明用の架空の数値を、実測例に見える形で置かない。

### 6.2 二重計上と欠測を避ける

未取得は0ではない。片方だけ取得できた値で削減率を計算しない。
キャッシュが入力トークンの内訳なら入力へ再加算しない。推論等も表示上の定義を確かめ、包含する区分を重ねて足さない。
セッション合計と要求別の値を合算して同じ利用を二度数えない。子担当を使った場合は親の表示に含まれるかを確認し、計上漏れや重複を明記する。

トークン、AIクレジット、追加請求、経過時間、人の作業は同じ単位ではない。
契約や表示の違いを無視して換算せず、文字数から料金を作らない。単位の異なる軸を根拠のない総合点へまとめない。
同じ単位でも、集計範囲、開始・終了、取得方法が違う値は、そのまま比較可能とはしない。

| 作業の範囲 | 記録の扱い |
| --- | --- |
| A/Bの本試行 | 修正・再確認・失敗を含め、共通の範囲で集計する |
| 関連情報の準備・保守 | 人の調査、指示・参照の整備を別記し、実務の判断で無視しない |
| 比較後の分析・改善設計 | Copilotによる記録整理も別の利用として扱う |
| 講師記録・支援 | 出所と支援内容を示し、自分の実行・測定に置き換えない |
| SEC-03〜07等の観察 | 改善仮説の根拠に使い、このA/Bの数値へ合算しない |

既存の参照情報を再利用できる場合と、新たに調査して用意する場合では準備の負担が違う。
AIの探索が減ったという観測だけで、準備・保守を含む総負担が減ったと断定しない。償却回数や業務全体の費用も実測なしに作らない。

### 6.3 観測手段と代替

VS Codeの公開文書には要求・セッションの利用量表示がある。今回は非Previewの標準表示と、参照・ツールの実行記録を使う案とする。
Agent Debug Logs等のPreview／Experimental機能は使用せず、講師ログのインポートも代替操作にしない。セッション種別・版・契約で見える範囲をQ-002・Q-003で事前確認する。未記録の過去の詳細を復元できる前提にしない。
モデル名、メニュー、ログの保存先を講師の環境から参加者全員へ推定しない。未準備の設定変更や権限拡大を必須にしない。

| 利用できる材料 | 学習での扱い |
| --- | --- |
| 条件・品質結果と、同じ範囲の利用量 | 取得した指標で比較し、単位と範囲を付ける |
| 条件・品質結果と、行動・所要時間 | その範囲で評価し、トークンや費用の削減は未評価とする |
| 参加者の観測が使えない | 条件・版・品質根拠のある講師の実測記録を読む |
| 条件が崩れた自分の記録 | 参考観察として原因を説明し、必要なら比較可能な講師記録へ切り替える |
| 比較可能な材料がない | 準備と手順の設計は進められるが、比較評価の達成は保留する |

講師記録にも条件、対象版、元の品質確認、介入、取得範囲、未実施を付ける。成功した例だけを選んでBの有利さを演出しない。
記録読解は参加者自身の測定ではない。説明用の状況や机上の想定を実測ログへ加工しない。
ログにはプロンプト、コード、パス、ツール入出力が含まれ得る。架空データだけの教材を使い、共有前に内容と共有先を確認する。
本リポジトリへ未確認の生ログ、秘密情報、実顧客データを追加しない。

## 7. 結果から採否を判断する

### 7.1 判断の順番を固定する

| 順番 | 問い | 不足がある場合 |
| --- | --- | --- |
| 条件 | 開始状態と方針は同じか。違いは参照指定だけか | 条件差付きの参考観察とし、単一要因の効果と断定しない |
| 品質 | 両方で同じ必須確認を実行し、必要な品質へ到達したか | 未達・未実施を残し、完了費用だけの優劣をつけない |
| 負担 | 比較可能な利用量・時間・人の負担に何が起きたか | 指標ごとに言える範囲を限定し、欠測を補わない |
| 適用 | この条件を別の作業へ使うために何を確認するか | 限定試行、追加評価、見送りを理由付きで選ぶ |

品質未達の原因や未完了までの観測も学習材料になるが、「安く完了した」という評価には使わない。
条件が揃っていても、一回ずつの比較から統計的な優位性や一般的な削減率を主張しない。
実務へ広く採用する前に、代表的な課題で複数回確かめ、品質・信頼性・所要時間・利用量・人の負担を併せて見る。

### 7.2 数字の違いを行動へ戻す

| 観測したこと | 調べる仮説・根拠 | 避ける結論 |
| --- | --- | --- |
| Bが同じ品質で少ない利用量 | 不要な探索や再説明が減ったか、条件差や準備負担はないか | 常に一定割合で削減できる |
| 差がない | 対象が小さい、既存指示が十分、試行のばらつき等を確認する | 指示や参照は無意味 |
| Bの入力や総利用量が増えた | 参照内容、重複読取、追加確認、他の指標の変化を調べる | 明示的な参照は常に悪い |
| 検証回数が減った | 手戻りが減ったのか、必要な確認を省いたのか | 少ない検証が無条件に効率的 |
| 人の介入が減った | 前提が整ったのか、必要な判断を飛ばしたのか | 人が入らないほど優秀 |
| 片方が未完了・計測欠落 | どの条件・確認・指標が不足したかを示す | 欠けた値を推定して精密な比較に見せる |

同じファイルを再読していても、編集後の差分確認なら必要な場合がある。
修正後の同じテスト、原因を確かめる再現、必要な追加調査を、回数の多さだけで無駄としない。
改善候補は、新しい根拠や必要な確認につながらない反復として、実際の記録から説明する。
Copilotの「原因はこれ」という説明も仮説である。説明のもっともらしさより、記録と別の説明の可能性を見る。

### 7.3 採否の範囲を残す

| 判断 | 記入する内容 |
| --- | --- |
| 限定的に試す | どの作業・条件で試すか、根拠、守る品質、人の判断、残る不確実性 |
| 追加評価 | 不足する記録や条件、次に一つだけ変えるもの、採用・見直しの基準 |
| 見送り | 効果が説明できない、準備負担が大きい等の理由と、再検討する条件 |

採否の基準は結果に合わせて都合よく変更せず、条件票で決めた品質と評価軸へ戻る。
利用量が減っても品質が落ちた案は採用しない。時間が短く利用量が増えた場合等は、何を重視して判断したかを明示する。
今回の採否は作業方法の評価であり、本番利用、顧客データの利用、組織標準、予算・権限の承認ではない。
モデル変更、担当数、指示やSkillの変更を試すなら次の別実験とし、このA/Bの途中へ混ぜない。

## 8. 改善設計シートと使い分け

### 8.1 一つのシートに三部分をまとめる

比較の根拠、採否と理由、次に使う作業手順を同じシートへまとめる。
長いログや会話全文を複製せず、必要な内容と原記録への参照を残す。本文内の記入形式は設計例であり、記入済みの実測資料ではない。

```text
【比較の根拠】
課題・対象AC・対象外:
記録の出所: 自分の実行 / 講師の実測記録の読解 / 支援あり
A/Bの試行ID、順序、開始版・差分・データ:
環境、モデル・設定、指示・担当・ツール・Skills、人の関与方針:
共通依頼と、Bだけに追加した参照・指定方法:
共通品質確認と各結果、実行時と修正後の対象版:
指標ごとの取得元・単位・範囲・値、未取得:
介入・中断・条件差・未完了、原記録の参照先:
本試行とは別の準備・分析・支援の記録:

【採否と理由】
観測した事実と根拠:
原因の仮説、別の説明、この記録だけでは言えないこと:
比較可能な範囲、品質到達、各負担の関係:
人の判断: 限定的に試す / 追加評価 / 見送り
適用する条件、判断理由、残る不足、見直すきっかけ:

【次に使う作業手順】
対象の作業、開始版、入力と参照先:
次に使う依頼文:
今回の要求と、共通・条件付き指示の分担:
担当の責務・ツール、再利用するSkill・確認資産:
既存のものを使う・限定する・追加しない理由:
作業範囲、実在する確認手順・期待する結果:
人の必須判断点、監督する情報、介入・停止・戻し先:
終了条件、未完了の場合に残す記録:
机上確認者・対象シートの版・説明内容・指摘採否・訂正後の再確認と残る不足:
移植先で再確認するAC・パス・コマンド・適用範囲・権限:
次に一つだけ変えて試す条件、固定条件、採用・見直しの基準:

```

まだ結果がない欄を、説明用の数値や架空の確認者で埋めない。
共通課題の必須入力・確認方法が欠けていれば、その手順は完成とはしない。別の実務環境で調べる情報は、対象と確認する人を未決事項として分ける。
改善手順を文章にしただけでは、変更後の利用量・品質を測ったことにならない。比較済みの条件と、新しい案を区別する。

### 8.2 情報と責務の置き場所を選ぶ

| 判断対象 | 共通課題で考えること | 避けること |
| --- | --- | --- |
| 今回の依頼 | 件数不整合の修正、対象版・AC・維持条件・対象外 | 一回限りの要求を恒常的な指示へ積み上げる |
| 共通指示 | 採用済みの品質・実行・報告ルールを参照する | 同じ規則を依頼・AGENTS.md・他の形式へ重複コピーする |
| 条件付き指示 | 対象ファイルに必要な規則と適用範囲を確認する | すべての言語・文書へ無条件に適用する |
| Agentの役割 | 修正担当と、根拠から指摘するレビュー担当の責務を分ける | 小さな作業を分担のためだけに細分化する |
| Skillの手順 | 実行担当が検証・切り分け・報告の既存手順を使う | Skillを常に独立した作業者と扱う、新しいSkillを数で増やす |
| 確認資産 | AC・データに基づく期待値と実在する確認手段を使う | 指示の文章だけでテストや実行結果を代替する |
| 人の判断 | 範囲、指摘採否、確認不足、終了・停止・再開を決める | AIの自信や承認回数だけで判断する |

SEC-03・04で作ったものを無条件に増設するのではなく、採用済みの定義の対象と役割を読む。
検証Skillが十分なら新しく作らない。一回限りの補足なら今回の依頼に置き、適用対象外の情報は分ける。
レビューAgentは読取・検索・指摘・追加確認の提案まで、検証の役割は確認・切り分け・報告までとし、修正は実装担当へ戻す。
この役割分担を文章化することと、実効ツールで制限できていることは別である。既存の権限を広げることを総合演習の条件にしない。

### 8.3 曖昧な記述を具体化する

| 曖昧な記述 | 共通課題で具体化すること |
| --- | --- |
| 関連情報を十分に渡す | どの開始版の何を参照として指定するか。不足時に追加調査を許す範囲 |
| テストを実行する | 正本の手順、対象、作業ディレクトリ、データ、結果集合・件数・集計の確認 |
| 人がレビューする | 誰が、どの差分と同じ版の結果を見て、何を採否判断するか |
| エラー時には止める | 起動不備、品質不合格、仕様不足、対象外操作をどう分け、誰へ何を戻すか |
| 効率が良ければ採用する | 品質を守ったうえで、どの指標・範囲を比較し、何が不足なら追加評価にするか |
| 別の案件でも使う | 共通の判断方法と、移植先で再確認するAC・パス・コマンド・権限を分ける |

入力を最小化するために必要な制約や未確認事項を落とさない。
参照が正しく準備できていない仕事へ、ファイル指定だけを機械的に持ち込むことも避ける。
「全ファイルを毎回添付する」「すべての編集を止める」「常に新しい会話へ分ける」といった一律の規則を結論にしない。

## 9. 人の関与、机上確認、実務への置き換え

### 9.1 HITL／HOTLを評価へつなぐ

SEC-06で学んだ、必須の人の判断と、合意範囲を観測しながら任せる方針を使う。
比較中は方針を共通にし、実際の判断・監督の負担を記録する。方針を途中で変えて介入が減っても、参照指定だけの効果とはしない。
通常のツール承認と、仕様・範囲・品質に関する判断を分ける。指示で安全境界を外すことは効率化ではない。

| 判断場面 | 人が確認すること |
| --- | --- |
| 比較前 | 公平な条件、実行対象、許可する操作、品質・打ち切り、観測と共有範囲 |
| 比較中 | 合意範囲からの逸脱、未決仕様、危険な操作、介入・停止と記録 |
| 分析後 | 原記録と説明の一致、採否、過度な一般化、未完了・欠測の扱い |
| 改善手順の作成後 | 責務、必須判断点、開始・終了・停止条件、実務へ移す前の確認 |

介入が減った理由を、前提の整理、必要な確認の欠落、人への負担移転などに分けて調べる。
HITLからHOTLへ一律に進むことや、無人化を最終目標にすることは求めない。

### 9.2 シートだけで開始・確認・停止を説明する

講師付きの回では、講師／TAへ個人で作成したシートとそこから参照できる資料を渡す。最初は作成者が口頭で不足を補わない。
確認担当と枠は参加人数に応じて事前に確保し、訂正後の再確認も含める。ペア開発へ変更する手順ではない。
確認者は、次の三つを自分の言葉で説明する。

1. どの版・情報から、何を始めるか。
2. 何を確認できれば、終えてよいか。
3. 何が起きたら止め、誰へ何を戻すか。

推測しないと答えられない箇所を記録し、作成者が指摘の採否と訂正理由を残す。
採用した訂正後の版を確認者に読み直してもらい、解消した点と残る不足を分ける。指摘がなければ三つの説明と根拠を記録する。
Copilotはコメント整理を補助できるが、存在しない第三者の確認を作らず、AIだけの自己確認を人の確認として記載しない。

これは手順の不足を見つける机上確認であり、改善案を実行・再測定したことではない。
自習では、本人がシートから離れた後に上の三つを説明し直し、共通教材のヒント・解説で不足を補う。確認者がいないことだけで学習を止めず、自己確認で次の学習へ進める。
第三者確認は未実施のまま残し、自己確認だけで完了にしない。本人が説明した範囲、訂正、必要な第三者確認を区別する。
講師コメントの例を読む学習も、本人のシートが実際に確認された成果とは分ける。

### 9.3 別の仕事へ移すときに調べ直す

対象は一つの一般化した作業に絞る。例えば既存APIの小さな不具合修正を取り上げ、実顧客のコードや秘密情報は持ち込まない。
業務が未定なら、共通課題を別のプロジェクトで行う場合として考えてよい。

| 再利用する判断方法 | 移植先で調べ直す情報 |
| --- | --- |
| 目的・品質から作業範囲を決める | 業務AC、維持する仕様、対象版、対象外 |
| 根拠と参照を絞って渡す | 実際の構成、ファイル、依存、参照の鮮度 |
| 継続情報・今回の要求・役割・手順を分ける | 指示の配置・適用範囲、既存Agent・Skill、実効ツール |
| 同じ版の結果で品質を判断する | コマンド、fixture、期待値、回帰範囲、実行環境 |
| 人の判断と監督を設計する | 影響、権限、担当者、承認経路、停止・再開の方法 |
| 一つずつ条件を変えて評価する | 取得できる指標、集計範囲、試行条件、採用・見直しの基準 |

知らないプロジェクトのコマンド、組織の標準、富士通の承認経路を作らない。
共通課題で使えた指示・手順を、そのまま移植先へコピーして適用済みとも説明しない。
次の試行には一つの変更条件と維持する品質を記す。モデル比較や新しいカスタマイズを選ぶ場合も、今回実行済みの成果には含めない。

## 10. S6と学習の達成を判定する

| 判定材料 | 必要な状態 | 不足する場合 |
| --- | --- | --- |
| 比較の根拠 | 条件、対象版、品質結果、原記録、取得範囲が対応する | 条件差・欠測を残し、比較可能な材料を用意する |
| 解釈と採否 | 観測・仮説・限界を分け、採否と理由を説明できる | 数字やAIの結論だけで決めず、根拠へ戻る |
| 使い分け | 依頼・指示・役割・手順・確認・人の判断を理由付きで分担している | 全機能の追加や重複を見直す |
| 作業手順 | 共通課題の開始、確認、終了・停止・戻し先を具体的に追える | 必須入力・確認方法の不足を修正する |
| 第三者の机上確認 | 実際の確認者・版・説明・指摘採否と、必要な訂正後の再確認がある | 未実施・不足を残す。自習は自己確認で継続し、この項目の完了とはしない |
| 実務への適用 | 再確認する情報、次の一つの試行条件、採用・見直しの基準がある | 抽象的な抱負ではなく対象と判断へ具体化する |

削減率の達成、Bの勝利、比較課題の解答との一致、全機能の利用はS6の条件にしない。
片方が未完了でも、その事実と比較の限界を説明することは評価できる。品質未達を安い成功とせず、改善案の実行を済ませたとも扱わない。
利用量が未取得ならその指標の評価は未達として残し、取得できた条件・品質・行動等で評価する範囲を明示する。
比較可能な材料そのものがない場合や、必要な手順・第三者確認が不足する場合はS6の判定を保留し、達成できた学習を別に記録する。自習では自己確認をもとに学習を続け、保留を学習継続の禁止にしない。

| 別々に残す状態 | 区別すること |
| --- | --- |
| 本編S0〜S5 | 実装、品質、定義と引き継ぎの到達・未達 |
| 比較課題の修正 | A/Bそれぞれの成功・失敗・未完了、対象版 |
| 実行と測定 | 自分で実施した範囲、取得した指標、条件差 |
| 読解と支援 | 講師記録の出所、ヒント・提供部分、自分で説明した範囲 |
| 確認者と範囲 | 自習の自己確認、実際の第三者確認、訂正、未実施の項目 |
| S6の評価学習 | 比較、採否、改善手順、机上確認、実務への再確認事項 |

講師記録を使ってS6の評価方法を学んだ場合は、その出所と支援を付ける。自力の測定や本編の未達を達成済みにしない。
学習上の到達を、業務全体の効果実証、実運用の承認、顧客への配布準備完了に読み替えない。

## 11. 講師準備、つまずき、復旧

### 11.1 教材化前に準備するもの

| 準備対象 | 配布・実施前に確かめること |
| --- | --- |
| 共通課題 | AC-08の小課題と対象外、説明用データと実IDの対応が明確 |
| 正常・欠陥・修正の版 | 同じ品質確認で成立・欠陥検出・回復を確かめ、完成例の差分を合格条件にしない |
| A/Bのコピーと依頼 | 初期状態を独立させ、違いを参照指定だけにし、解法・準備会話を混入させない |
| 指示・担当・ツール | 共通設定と実効範囲、適用・利用の確認方法を揃える |
| 観測と条件票 | 単位・範囲、事前設定、順序、介入、打ち切り、条件差と欠測の扱いを決める |
| 記録と代替 | 出所・版・品質根拠付きの実測記録を用意し、読解・支援を区別する |
| 改善設計シート | 本文の三部分と記入基準から、根拠・判断・具体的手順を追える |
| 机上確認とS6 | 確認者、三つの問い、訂正後の確認、保留と支援の判定を準備する |
| 配布と復旧 | 講師の解答・設計意図・生ログの公開範囲を確認し、差分を保持して別コピーで再開できる |

これらの準備物は今回の文書改訂では作成しない。比較教材・記録・観測環境の成立性はQ-003・Q-005・Q-009、進行はQ-011で確認する。
モデル・指標・試行数・打ち切り・役割分担は、参加者環境と教材に合わせて事前に固定する。未測定の効果や所要時間を保証しない。
解説・ヒントは同じ共通教材で利用する。折りたたみをCopilotからのアクセス制御とは扱わず、[テンプレート方針](../template-strategy.md)に沿って履歴・権限・比較への混入を確認する。

### 11.2 つまずきへの対応

| 状況 | 講師の対応 |
| --- | --- |
| 振り返りが感想になる | 一場面の記録へ戻し、依頼・行動・結果と解釈を分ける |
| Aを曖昧にしてBを良く見せる | 目的・品質・調査権限を共通に戻し、参照以外の差を除く |
| 参照を増やすこと自体が目的になる | 必要な入口と追加調査の範囲、準備・保守の負担を問う |
| Bが勝たず、結果を取り直したがる | 元の結果を保持し、差なし・悪化・ばらつきを解釈する。勝つまでの選別をしない |
| 数字が取れない | 未取得とし、取得可能な指標または講師の実測記録へ切り替える |
| 片方が未完了 | 打ち切り時の状態を残し、少ない利用量を成功と評価しない |
| 設定・ヒントが片方だけ変わった | 条件差として残し、必要なら別の条件票と試行IDで再開する |
| 改善案が抽象的 | 開始版・参照・確認手順・期待結果・戻し先へ具体化する |
| 全機能を新規作成したがる | 既存の定義と正本を読み、使う・限定する・追加しない理由を説明させる |
| シートだけでは第三者が開始できない | 推測が必要な箇所を記録し、採否・訂正・読み直しを行う |
| 自分の業務を決められない | 共通課題を別の環境へ移す場合として再確認事項を整理する |
| 比較材料がない | 読解・設計で学べる範囲を残し、実行・測定は未実施とする。形式だけのS6認定をしない |
| 自習で第三者の確認者がいない | 三つの問いを本人が説明し直して学習を進める。第三者確認の未実施と、自己確認した範囲を分ける |

ヒントは、目的の問い、根拠の参照先、記入の構造の3段階で深め、提供した範囲を記録する。完成例とその解説は比較後の別資料として扱う。
比較の途中に必要な支援と、終了後の解説を区別する。講師の完成シートを読むだけでは、参加者自身の判断・手順作成・机上確認の代わりにならない。
復旧では対象コピー、DB、指示、会話、観測記録を分け、参加者の差分を保持する。安全条件を外した再試行や、他の作業を巻き込むリセットを行わない。
