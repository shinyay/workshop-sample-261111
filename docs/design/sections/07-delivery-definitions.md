## 1. 位置づけと学習目標

このセクションでは、アプリと配備の要件を、TerraformとAzure Pipelinesの定義へ落とし込む過程をGitHub Copilotで実践する。
S4の実装・品質根拠を受け取り、要件整理、構成設計、両定義の生成、追加要件への差分対応、横断レビューを通して、S5の引き継ぎ案を作る。

Terraformでは必要な環境を資源と設定として宣言し、Azure Pipelinesでは準備・確認・成果物・配備の順序と条件を定義する。
Terraformで環境を記述することと、その適用をパイプラインから実行することは別の範囲として扱う。

AzureとAzure DevOpsの実環境はない。したがって、クラウド配備やパイプライン成功は終了条件にしない。
一方、読解だけに限定せず、参加者自身が目的と制約を伝え、主要な定義を生成・変更し、その理由を説明することを本編の中心にする。
「ファイルができた」「AIが問題ないと答えた」ではなく、何を満たし、何を確認でき、何が残るかを評価する。

**今回の通常経路:** 要件とTerraform → Azure Pipelines → 追加要件への横断変更とレビュー、という三つのまとまりで進める。
個人で構成理由と採否を説明し、Terraform・YAMLの構文や参照の経験差は骨組みと既定で非表示のヒントで補う。完成済みの主要部を名前だけ変える演習にはしない。
Copilotの機能・モデル・観測は[共通シナリオ](../common-scenario.md)第2・10節に従い、Previewの機能や実サービスへの接続で不足を埋めない。

| 学習目標 | 参加者が示す成果 |
| --- | --- |
| 要件を分ける | コードから確認した事実、人が決める配備・自動化の要件、未決事項を分ける |
| 役割を説明する | Terraformが管理する環境と、Azure Pipelinesが扱う作業の順序・条件を説明する |
| 定義を構成する | 合意した要件をCopilotへ渡し、主要ブロックを生成して必要な理由を説明する |
| 二つの定義をつなぐ | 配備先、設定、入力・出力、成果物、品質条件の対応を示す |
| 変更に対応する | 追加要件の影響を調べ、必要な定義と記録を差分で変更する |
| 確認の限界を説明する | 静的な照合、ローカル確認、実環境での実行を区別する |
| 人へ引き継ぐ | 採否、残課題、危険な操作、次に人が確認・判断することを整理する |

前後のセクションとは、次のようにつなぐ。

| 接続先 | このセクションで受け継ぐこと・渡すこと |
| --- | --- |
| SEC-02 | 事実・仮説・要件を分ける進め方を再利用する。アプリの機能要件だけで配備方式が決まるとはしない |
| SEC-03・04 | 採用した指示と役割を使う。新しいAgentやSkillを増やすこと自体を課題にしない |
| SEC-05・06 | 対象版、実際の確認手順と結果、品質判断、未実施事項、人の関与方針を受け取る |
| SEC-08 | 生成・修正・レビューでの探索や手戻りを渡す。独立したA/Bの測定値とは分ける |

以下の「必須」は、この詳細DRAFTで提案する本編の範囲である。
6段階・12プロンプトの成立性、具体的な配置先と確認手段はQ-008・Q-011で教材化・試走する。
ユーザーが明示した「要件から両定義を構成する体験」と、個々の教材案の最終確定は区別する。

## 2. 要件から始める共通シナリオ

### 2.1 最初に渡す依頼

> SEC-06で品質を確認した申請ポータルについて、将来の検証環境と、自動検証・配備に向けた定義案を準備してください。
>
> アプリの起動・設定・確認方法を読み取り、講師が提示する配備要件に基づいてTerraformとAzure Pipelinesを構成してください。
> どの要件がどの定義に対応し、二つの定義が何を受け渡すか説明してください。
>
> 今回はAzure・Azure DevOpsへ接続せず、リソースの作成・変更、パイプライン実行、配備は行いません。実環境で確認すべき事項を残してください。

架空の研修シナリオであり、富士通の実環境・標準・承認経路を表すものではない。
本編S4が未達の場合の代替学習は第3節で扱い、未達の実装を品質確認済みと呼び替えない。

### 2.2 アプリの事実、与える要件、未決事項

| 区分 | 材料 | 扱い |
| --- | --- | --- |
| アプリから確認する事実 | 対象版、起動方法、依存管理、設定の読み込み、DBの扱い、参加者版の検証コマンド | ファイル・箇所と実行記録を示す。未読・未実行を補わない |
| 人が与える要件 | 仮想の配置先、環境の区分、命名、必須の確認、成果物形式、失敗時の進行条件 | 要件票として合意し、定義との対応を残す |
| 教材上の前提 | 単一の構成案、最小の骨組み、使うツール・タスクの版、許可済みローカル確認 | 講師が事前に選び、参加者間の無制限な分岐を避ける |
| 実環境が必要な事項 | 実際の権限、サービス接続、環境の承認設定、利用できる資源、配備後の挙動 | 未設定・未検証として引き継ぐ。架空の実値を入れない |

固定参照版はPython・Flask・SQLite・Jinja2、uvによる依存管理を使う。
Python 3.14を既定、3.13を互換対象とする説明は、採用するAzureランタイムがそのまま対応するという根拠にはならない。
実際の参加者版で起動・確認コマンドを読み直す。完成例パッチの検証など、配布から分離した資産をCIへ戻さない。

SQLiteの保存先、初期化、再起動後の保持、複数プロセス・複数インスタンスでの扱いは、クラウドでの追加検討になる。
認証・利用者ごとの権限・監査・バックアップ等の不足を隠さず、外部公開可能な本番アプリへ暗黙に格上げしない。
基盤へ合わせるためのPython変更、DB置換、コンテナー化、認証実装を、このセクションで勝手に追加しない。

### 2.3 講師が固定する「仮想構成の要件票」

本編は、一つの仮想構成と最小骨組みから始める。
Azureのサービス選定を無制限に任せる演習でも、完成例の値だけを置換する演習でもない。
次の項目を講師が教材化前に具体化し、そのうち要件が表れる主要ブロックを参加者がCopilotで生成する。

| 要件票の項目 | 固定する内容 |
| --- | --- |
| 環境の目的と配置先 | 非本番の検証用途、一つのAzureサービス構成、管理する資源と管理しないもの |
| 実行方式 | OS、Python、起動方法、設定の渡し方、作成する成果物の形式 |
| データと公開範囲 | 架空データのみ、DBの配置・保持に関する条件、実際には外部公開しない境界 |
| ツールと依存 | Terraform・プロバイダー・uv等の選定版、ロックの扱い、事前取得と許可する通信 |
| CIの対象 | 利用するAzure DevOpsの提供形態、エージェントOS・シェル、正本の確認手順、採用タスクと参照仕様 |
| CIの起動契機と範囲 | ソース連携先、push・PR・手動等の契機、対象ブランチ・必要なパス条件、YAML外の設定 |
| 成果物の契約 | 内容、除外対象、名前、作成先と取得先、対象版の識別、確認方法 |
| CDの範囲 | 定義する配備の流れ、既定で実行対象外にする方法、環境側へ残す設定 |
| 人の判断 | 構成・追加要件の採否、公開・権限・state等を人へ戻す条件、未決事項の扱い |

検討候補は、リソースグループ、実行基盤、Webアプリ、設定という対応を追いやすい小さな構成とする。
App Service（Linux）の単一アプリを第一候補とし、Python・起動方法・SQLiteの保存保持・公開制御との適合を先に確認する。ここで採用サービスを確定したとはしない。
複数インスタンスや本番運用の構成は本編へ広げない。適合しなければ仮想構成を見直し、教材のPython変更やDB置換で無断に解消しない。
整合する構成をまだ用意できない段階では、完成した生成演習として配らず、何が不足しているかをQ-008へ残す。

### 2.4 定義を評価する要件例

次のDR-IDはSEC-07内の配備・自動化要件の設計例であり、共通シナリオのAC-01〜AC-11を置き換えない。
DR-01〜DR-10とDR-13を初期要件、DR-11・DR-12を段階5で追加する要件として扱う。
DR-13は起動契機の論点を今回補ったIDであり、既存のDR-11・DR-12を付け替えない。
具体的な値や確認手段は要件票で固定し、初期要件は生成前、追加要件は段階5の変更前に提示する。

| ID | 要件例 | 定義・記録で確かめること |
| --- | --- | --- |
| DR-01 | 同じ版を追跡する | S4、生成の入力、CIが取得するソース、成果物の版が対応する |
| DR-02 | 合意した仮想構成に限定する | 必要な資源と関係があり、無関係なサービスや本番機能を増やしていない |
| DR-03 | 実行・依存・確認の条件を揃える | Python、uv、ロック、作業ディレクトリ、OS・シェルと確認コマンドが対応する |
| DR-04 | データと秘密情報を持ち出さない | 実データ・資格情報・DB・stateを成果物へ含めず、非本番・非公開の境界を残す |
| DR-05 | Terraformの入出力を説明する | 入力の型・意味・指定元、資源間の参照、出力と利用側の対応がある |
| DR-06 | 必要な品質確認を省かない | 参加者版に存在するアプリの確認と、教材で選んだ定義の確認を段階へ割り当てる |
| DR-07 | 不足する確認を成功扱いにしない | 失敗・中断・必須確認のスキップで配備候補や配備へ進まず、診断記録を別に扱う |
| DR-08 | 確認した入力から成果物を作る | 必要ファイル、除外、依存、対象版、成果物の内容確認と後続への受け渡しが対応する |
| DR-09 | CDは非実行の定義案にする | 配備段階の主要部を定義しつつ既定では対象外にし、接続・適用・実行を行わない |
| DR-10 | 未設定・未検証と判断者を残す | 環境側の権限・接続・承認、データ保持、本番化の不足、次の確認を引き継ぐ |
| DR-13 | CIを開始する契機と対象を明示する | ソース連携先、push・PR・手動等の起動、ブランチ・必要なパス条件、YAMLとサービス側設定の分担が対応する |
| DR-11 | 環境ごとに資源と設定・stateを区別する | 論理環境名、命名、設定、stateの分離方針が対応し、他環境を変更しない設計になる |
| DR-12 | 環境が変わっても同じ成果物を使う | 特定の実行・成果物を選び、作り直さず、識別情報と必要な内容・digestを照合する設計になる |

「対応する記述がある」「仕様に照らして確認した」「ローカルで実行した」「実環境で確認した」は別の状態である。
例えばDR-12のdigest確認を定義しても、未作成の成果物の実測digestを記入してよいわけではない。
要件対応表には、DR-ID、出所、対応する定義箇所、確認方法と結果、未決事項・判断者を記入する。生成前は対応方針とし、生成後に実際の箇所へ更新する。

## 3. 開始条件、教材、役割

### 3.1 S4から受け取るもの

| 入力 | 開始時に見ること |
| --- | --- |
| 対象版 | 本編のコミット、未コミット差分の識別、作業コピーが特定できる |
| 品質根拠 | 同じ版のACごとの結果、指摘の採否、修正後の確認、残課題がある |
| 起動・確認契約 | 参加者版の実在する手順、依存、DB初期化の条件、実行済みの範囲が分かる |
| 指示と役割 | 採用済みの指示・Agent・Skillが何を対象とし、どのツールを持つか分かる |
| 人の関与 | 委任範囲、必須判断点、監督・介入条件、実際の判断が残っている |
| 教材側の入力 | 仮想構成の要件票、骨組み、参照仕様、追加要件、記入欄が準備されている |

未コミット差分を含むS4を、コミットSHAだけでCIの取得対象と同一視しない。
ローカルで識別した対象と、将来CIがcheckoutする版を分け、実行前に確定すべき事項を残す。
このセクションのためだけに、参加者へ実サービス接続や公開を求めない。

S4未達でも、講師が用意した版と根拠を使ってSEC-07の定義構成を学べる。
その場合は対象を講師教材と明示し、本編の未達、講師提供部分、自分が構成・説明した部分を分ける。
SEC-06の判断事例の読解や発展実操作の記録を、アプリの品質根拠として流用しない。

### 3.2 最小骨組みと参加者の作成範囲

| 講師が渡すもの | 参加者がCopilotで構成するもの |
| --- | --- |
| 仮想構成と管理範囲、参照する仕様 | 要件に必要なリソース・設定・依存関係 |
| Terraformのファイル区分、必要な版の方針 | 入力変数、主要な構成、利用側へ渡す出力 |
| パイプラインの枠、OS・シェル、実在する確認手順 | 準備・品質確認・成果物作成と受け渡しの主要部 |
| CDの非実行境界と未設定情報の記入欄 | 配備先・成果物・設定・進行条件の対応を示す定義案 |
| 記録と支援のひな型 | 要件対応表、追加要件の変更理由、確認範囲、引き継ぎ |

配置候補は`infra\versions.tf`、`infra\variables.tf`、`infra\main.tf`、`infra\outputs.tf`、`azure-pipelines.yml`。
非実行CDは通常CIから参照しない別定義を第一候補にする。サービス側の起動登録は行わず、ファイル数を増やすことを学習目標にはしない。
これらは将来の教材配置候補であり、本リポジトリに実行用ファイルがあるという意味ではない。

初めから完成した主要部を配り、名前だけを変えた場合は「構成を生成した」という達成にしない。
逆に、TerraformやYAMLの全構文を暗記させる課題にもせず、公式仕様と骨組みを参照できるようにする。

### 3.3 担当の責務

| 担当 | 任せること | 任せないこと |
| --- | --- | --- |
| 構成・実装担当 | 要件の整理、構成提案、合意範囲の定義生成・修正 | 未決の配備先・権限の独断決定、無断のアプリ変更、実配備 |
| レビューAgent | 要件と定義の読取・検索・照合、指摘、追加確認の提案 | 編集、任意のコマンド実行、最終承認 |
| 検証を行う担当 | 許可済みローカル確認、結果と原因候補の報告 | 確認中の無断修正、認証・クラウド接続、成功の創作 |
| 参加者・人 | 構成と変更範囲の採否、実行可否、指摘の採否、S5判断 | AIの自信や指摘数だけによる合格判定 |
| 講師 | 要件・仕様・骨組み・依存の準備、ヒント、確認範囲の説明 | 不足する実行結果を架空ログで補うこと |

Python向けの条件付き指示をTerraformやYAMLへ適用済みとせず、共通指示と今回の明示的な依頼の役割を分ける。
検証SkillにTerraformやAzure Pipelinesの確認手順があるとは限らない。本文と対象範囲を確認し、存在しない手順を実行済みとしない。
必要な補足は今回の明示的な依頼や講師の手順で渡す。SEC-04の役割を壊すような権限拡大や、Skillの恒久的な書き換えを必須にしない。

## 4. 6段階の進行とプロンプト

| 段階 | 作業 | 主な成果 |
| --- | --- | --- |
| 1 | 前提と要件を整理する | 事実・要件・未決事項の区分、DR-01〜DR-10とDR-13の対応方針 |
| 2 | 構成を設計する | 管理範囲、工程、入出力・成果物の契約、人の採否 |
| 3 | Terraformを構成する | 主要な定義と要件対応、依存・出力・未設定の説明 |
| 4 | Azure Pipelinesを構成する | 起動契機、確認・成果物・非実行CDの定義と進行条件 |
| 5 | 追加要件に対応する | DR-11・DR-12の影響、差分、両定義の対応更新 |
| 6 | 横断レビューと引き継ぎ | 採否、確認範囲、S5または不足、次の担当への記録 |

以下は開始・追加各6本、計12本のプロンプト案。
開始依頼で必要な前提を渡し、追加依頼は出力を見て不足や不整合を確かめるために使う。全員が同じ生成結果を得ることは前提にしない。
実行が必要になったら、許可する対象・手段・副作用を別途確認する。文章中にコマンドが出たことを実行の承認にしない。

### 段階1: 前提と要件を整理する

**目的と入力:** S4の引き継ぎ、参加者版、仮想構成の要件票を使い、定義へ落とす情報と人が決める情報を分ける。

**参加者の作業:** 対象版を特定し、起動・依存・設定・DB・品質確認の根拠を抽出する。
機能ACと配備要件を分け、要件票の不足を質問候補にする。コードに書かれていない組織方針を推測で埋めない。

**講師の介入:** 「この情報はコードから分かるか」「誰が決めるべきか」を問う。

## 5. Terraformで具体的に学ぶこと

### 5.1 要件と主要ブロックを対応づける

| 面 | 参加者が説明すること | 避けること |
| --- | --- | --- |
| 管理範囲 | どの資源をTerraformで管理し、どれを外部の前提にするか | 見栄えのために不要なサービスを足す |
| 版と依存 | Terraform・プロバイダーの制約、ロック、採用した属性の仕様 | 未確認の最新版や存在しない属性を使う |
| 入力 | 型、意味、許容値、指定元、必須と既定値の理由 | すべて文字列にする、架空のID・秘密値を埋める |
| 資源の関係 | 一方の資源の属性を他方が使う関係と変更影響 | 名前の手入力を各所へ複製する、依存を推測する |
| 設定とデータ | アプリ設定、保存先、公開制約、本番化の不足 | DB変更や外部公開を暗黙に追加する |
| 出力 | 利用側が必要とする識別情報と、その取得・受け渡し方針 | 出力宣言だけで実値が取得・転送済みと扱う |
| state | 対象環境を識別する方針、保存・アクセス・復旧の未決事項 | 同じstateの環境名だけを変えて安全な環境分離と呼ぶ |

配備先の名前などをTerraformとパイプラインの両方で独立に組み立てると、規則の変更で不一致が生じやすい。
正本にする情報、そこから参照・受け渡す情報を決める。ただし、参照関係を説明しただけで実際の連携が完成したとはしない。

### 5.2 宣言、実値、受け渡しを分ける

| 情報 | 定義段階で決めること | 実環境で必要になること |
| --- | --- | --- |
| 環境識別 | 論理名、許容値、命名規則、設定・stateとの対応 | 対象環境と権限の確認 |
| 配備先 | 必要な出力の名前・型・意味、利用する箇所 | 正しい環境からの取得、受け渡し、存在と権限の確認 |
| アプリ設定 | キーと用途、非秘密値と秘密情報の参照の区別 | 保存先、権限、実値の設定、動作確認 |
| 成果物 | 形式、識別、配備先との対応 | 実際の登録・取得・配備、内容の照合 |

stateや出力を、資格情報の配布手段にしない。実state、保存済みplan、秘密値を教材・ログ・成果物へ含めない。
未設定項目は一覧へ残し、型に合わない`TODO`や本物らしい接続先をコードへ埋めて構成を完成したように見せない。
必須の入力は必須のまま表現できる。validateで内部整合性を確認しても、その値の実環境での妥当性は別の確認になる。

## 6. Azure Pipelinesで具体的に学ぶこと

### 6.1 起動契機と工程の品質条件

DR-13は「いつ、どの変更に対してCIを開始するか」、DR-06・DR-07は「開始した後に何を確認し、どの条件で次へ進むか」を扱う。
講師は仮想のソース連携先と起動要件を一つに揃え、参加者は定義とサービス側設定の対応を説明する。実PR作成やクラウド上の試行は求めない。

| 起動について決めること | 読み解く例 |
| --- | --- |
| push・PR・手動の扱い | どの契機を対象にし、何を自動起動の対象外にするか |
| 対象ブランチと必要なパス条件 | 対象の変更で必要な確認が走り、除外によって必須確認を落とさないか |
| 設定する場所 | 採用するソース連携でYAMLに書ける条件と、サービス側へ残す設定は何か |
| 品質条件との関係 | 起動しただけで品質確認済みにせず、手動実行でも必須確認を省かないか |

ソース連携先によってPR等の設定方法は異なるため、未確認の`trigger`や`pr`をすべての環境へ共通の完成形として転記しない。
この対応は定義の机上確認であり、対象の変更をサービスが検出した実績ではない。

次は工程の設計例であり、実行済みのパイプラインではない。
Terraformの環境作成とアプリ配備を一つの無条件な処理にまとめず、初期化・環境準備・アプリの確認・成果物・配備の責務を分ける。

| 工程 | 定義する内容 | 次へ進む条件 |
| --- | --- | --- |
| 準備 | 対象ソース、OS・シェル、Python・uv・必要なツール、ロックに沿う依存 | 準備が成立し、対象と作業ディレクトリが正しい |
| 品質確認 | 参加者版のテスト・静的確認、教材で選んだ定義の確認 | 必須の確認が実際に実行され、合格している |
| 成果物作成・内容確認 | 必要ファイル、除外、版の識別、形式、内容の照合 | 対象版と内容が対応し、欠落や混入がない |
| 配備候補の登録 | 合格した成果物の登録先・名前・実行の識別 | 配備候補として必要な確認がすべて済んでいる |
| 非実行CD | 対象環境、取得する成果物、設定、配備と配備後確認の定義 | 本ワークショップでは進めない。実環境側の準備・承認・確認は未実施 |
| 診断記録 | 失敗理由、関連するログやテスト結果の保存方針 | 配備候補と区別し、機微情報・存在有無を確認する |

パイプライン内での「成果物の登録」は、インターネットへの一般公開を意味しない。
今回はAzure Pipelines上の登録自体も実行しない。ローカルで作成した候補がある場合も、サービス上の登録・取得の成功へ置き換えない。

DR-06に使うコマンドは、参加者版の正本と対象ファイルから採る。
開始版の教材状態テストや完成例パッチへの依存を、そのまま機能追加後の品質条件にしない。
コマンド名が存在するだけでなく、対象テストが収集・実行され、必要な失敗が終了状態へ反映される設計かを見る。
品質条件を減らす、失敗を無視する、最後の成功メッセージで終了コードを上書きすることを、移植の解決策にしない。

### 6.2 失敗時の流れを読む

Azure Pipelinesでは、独自の`condition`を指定すると既定の条件を上書きする。
対象ブランチやフラグだけを見る条件にして、依存する確認の成功条件を落とさない。
`always()`などを使う場合は、何を失敗・中断時にも行うのかを限定し、配備候補や配備と診断を区別する。
stage・job・stepの依存と条件を併せて読み、単一行だけで全体の進行を判定しない。

| 説明用の状況 | 定義から確かめること |
| --- | --- |
| 必須確認がすべて成功 | 正しい版の成果物を作成・確認し、配備候補として渡す設計になっているか |
| テストが失敗 | 配備候補・配備を止め、必要な診断情報を別に残せるか |
| 依存の取得やテスト起動が失敗 | アプリのテスト不合格と区別しつつ、後続の品質到達として扱わないか |
| 必須の確認をスキップ | 必須確認を任意に外せる分岐がなく、不足を成功として後続へ渡さないか |
| 実行が中断 | 条件の上書きによって、後続の資源変更や配備が残らないか |
| 成果物がない・版が違う | 空や別の「最新」の成果物を黙って使わず、配備候補としての扱いを止めるか |
| CDの接続や承認が未設定 | 本編では実行対象外のままにし、実配備を許す根拠にしないか |

これは定義に対する机上の確認であり、Azure Pipelinesの実行結果ではない。
説明用の状況を成功・失敗の架空ログに加工しない。実環境での条件評価や中断時の挙動は、後続の確認項目へ残す。

### 6.3 成果物の契約

成果物には、必要なアプリのファイルと、その起動・依存に必要な情報を含める。
ローカルDB、秘密情報、実state、不要なログ、環境固有の仮想環境、講師用の解答を丸ごと固めて渡さない。
除外しすぎて必要なテンプレート・静的ファイル・設定仕様が欠けていないかも見る。

登録元と取得側で、名前だけでなく、実行の識別、保存先・取得先、形式、ディレクトリ構造を揃える。
同じコミットから作ったという説明と、同じ成果物のバイト列を再利用したという説明を区別する。
依存やツールの版、生成時の条件も記録し、必要なdigestは実際に生成・取得した対象から測る方針を定義する。

ソースに対するテストの成功だけでは、パッケージ内の欠落や配備先での起動を確認したことにはならない。
内容確認と、必要なら講師が準備したローカルの起動確認を分ける。用意していないスクリプトを実在する検証手順として呼び出さない。
採用する成果物機能とタスクはAzure DevOpsの提供形態・版に合わせ、YAML構文とタスク個別の仕様の両方を確認する。

### 6.4 CDを定義するが、実行しない

CDを「省略」の一言だけで済ませず、何をどこへ渡し、どんな確認・判断を経るかを定義する。
配備先の入力、成果物の取得、設定の適用、選定した配備タスクの主要な入力、配備後確認の位置を説明できるようにする。
実サービス接続、権限、環境の承認設定は別項目として残す。

本編ではCDを既定で実行対象外にし、接続・適用のコマンドを手元でも実行しない。
未設定の接続を参照するCDは、通常CIから参照しない別定義を第一候補とする。別定義もサービス側へ起動登録せず、配置・参照関係を教材化時に確認する。
実行時のスキップ条件だけで、サービス側の構文・資源参照の確認まで回避できるとは仮定しない。
無効化フラグやトリガの設定を書いたことも、誤実行が技術的に防止できると実証した根拠にはしない。

実行していない配備を成功に見せるダミー処理や、接続不備を無視して成功で終える代替は置かない。
`plan`・`apply`・state操作・Azure CLIの資源操作を、ローカル検証の一部として紛れ込ませない。
将来実行するには、要件と権限の再確認、環境側の設定、独立したレビューと実環境での検証が必要になる。

## 7. 追加要件と、両定義をまたぐ変更

### 7.1 段階5で提示する変更依頼

> 検証環境を二つの論理環境として扱えるようにしてください。環境ごとにリソース名と設定を分け、他環境の資源やstateを取り違えない構成にします。
>
> 一方、環境が変わるたびにアプリを作り直すのではなく、必要な確認を済ませた同じ成果物を使ってください。環境固有の設定は成果物と分けてください。
>
> 実際の環境作成・切り替え・配備は行いません。定義と受け渡し、確認方法を更新してください。

二つの論理環境は教材上の区分であり、実在の開発・本番環境や、富士通の運用段階を表さない。
追加要件の全体は講師設計として事前に用意し、参加者には初期定義ができた段階で提示する。
初期要件を隠して失敗させるのではなく、要求が増えたときの影響調査と保守を学ぶ。

### 7.2 期待する変更の対応

| 面 | 変更・確認すること | 維持すること |
| --- | --- | --- |
| Terraformの入力と命名 | 論理環境の識別と許容値、資源名・設定との対応 | 必要な資源の役割、非本番の境界 |
| stateの扱い | 環境ごとの識別・分離方針、誤った対象を選ばない確認 | 実stateへ接続・作成・移行・削除しないこと |
| Terraformの出力 | どの環境の配備先かを利用側が識別できる契約 | 出力宣言を実値・実行結果としないこと |
| パイプラインの設定 | 対象環境と設定の選択、配備先との対応 | 必須の品質確認と失敗時の停止条件 |
| 成果物 | 特定の実行・成果物を選び、同じ内容を再利用する契約 | 環境ごとに再生成しないこと、秘密情報を含めないこと |
| 引き継ぎ | DR-11・DR-12、差分、確認範囲、未決事項を追加する | 元のAC、対象版の追跡、人の判断 |

Terraform workspace、別ディレクトリ、backendのキー等のどれで分離するかは、教材の構成に合わせてQ-008で決める。
一つの方式をあらゆる案件の正解として教えず、論理名だけを変えて安全な分離が成立したとも説明しない。
実資源が既にある場合の命名変更・移行・置換の影響は別の確認であり、今回は未適用の定義案の変更に限定する。

### 7.3 横断レビューで使う問い

| 問い | 見つけたい不整合 |
| --- | --- |
| 同じ環境を指しているか | Terraformの環境名と、パイプラインの配備先・設定・stateの対応が異なる |
| 出力はどこへ渡るか | 出力名だけ合っていて、取得元や変換・受け渡しの手順がない |
| 同じ成果物を使うか | 配備時に再ビルドする、「最新」を取得し直す、環境値を埋めて別物にする |
| 何を確認してから渡すか | 必須確認の対象版と成果物がずれる、未実施を合格扱いにする |
| 構成を増やしすぎていないか | 環境追加を理由にDB置換、認証、監視基盤などを無断で追加する |
| 実行しない境界は残るか | 追加テンプレートに接続・適用が入り、既定の非実行設計をすり抜ける |

これらはレビュー観点であり、参加者の出力に必ず欠陥があるという前提ではない。
不整合がなければ、対応と根拠を説明した結果を認める。講師が補助用の不整合例を作る場合は、実際の生成結果や本編から分離して提示する。

## 8. 確認手段と、言えることの範囲

### 8.1 実行しなくても確認すること

必須なのは、要件と定義の対応、構成の理由、両定義の整合性、追加要件の差分、未設定・未検証の区別である。
要件から定義を追うだけでなく、定義の各部分から必要な理由へ戻ることで、不要な追加も確かめる。
Copilotの説明だけを根拠にせず、該当ファイルと採用版の仕様を参加者が照合する。

ローカル検証を全員の必須操作にするかは、ツール・依存・通信の準備条件をQ-008で確認して決める。
実行できない場合も構成・変更・レビューの学習は進められるが、ローカル確認の欄は未実施として残す。

| 手段 | 準備と確認する範囲 | 保証しないこと |
| --- | --- | --- |
| 要件・仕様との照合 | DR-ID、定義の箇所、採用版の仕様、入出力の契約を読む | 実サービスでの構成・運用の成立 |
| `terraform fmt -check` | 準備済みのTerraformで、指定した対象の整形を確認する | 要件、リソース属性全体、権限、配備の正しさ |
| `terraform validate` | 必要なプロバイダー・モジュールを初期化済みにし、構文と内部整合性を確認する | リモートstateやプロバイダーAPI、実際の資源・接続の妥当性 |
| YAMLのパーサー・仕様照合 | 準備済みの手段で構文を確認し、Azure Pipelinesの構造と採用タスクの仕様を別に照合する | サービス上のテンプレート展開、変数評価、タスク実行 |
| アプリのローカル確認 | 同じ版・条件・対象で、許可済みの確認を実行する | Azure Pipelines上の成功、クラウドでの起動 |
| 成果物候補の内容確認 | 作成した場合だけ、版・含有ファイル・除外・形式・digest等を確かめる | サービス上の登録・取得・配備、実環境での動作 |
| Terraformの`plan`・`apply`、パイプライン実行 | 本ワークショップでは行わず、必要な準備と後続の確認を記録する | 未実施を成功と扱うこと |

`terraform validate`に必要な初期化では、`terraform init -backend=false`により設定済みbackendへのアクセスを避ける方法がある。
ただし、プロバイダーやモジュールの取得まで不要になるわけではない。ネットワーク、取得元、選定版、ロック、ローカルへの書き込みを事前に確認する。
インストール済みのTerraformだけで、必ず認証も通信もなくvalidateできるとは説明しない。
講師が準備していない追加のツール・拡張・依存取得を、当日その場で必須にしない。

Azure PipelinesのYAMLスキーマは構造の参照であり、個々のタスクの仕様をすべて含むわけではない。
YAMLパーサーの成功をAzure Pipelines全体の検証と呼ばず、外部サービスの検証APIにも接続しない。
架空のサービス接続や成功を返すスクリプトで、未検証の箇所を検証済みに変えない。

### 8.2 確認記録の形式

```text
確認IDと対象DR-ID:
対象ファイル・版・差分:
手段: 読取照合 / 整形 / 内部整合性 / ローカルのアプリ / 成果物候補
ツールと版、作業ディレクトリ、依存、データ、許可した通信:
実際に行った確認、コマンドと原記録の参照先:
結果: 成功 / 失敗 / 未実施 / 準備不備で確認できず
この結果から言えること:
この結果だけでは言えないこと:
訂正、再確認、残る未決事項:
```

ツールの起動不備や依存未取得を、定義の意味上の不合格と混同しない。ただし、確認できなかったことも合格にはしない。
静的な照合と実行結果を別欄で残し、講師の記録には出所・版・条件を付ける。
定義を修正した後は、変更の影響を受ける確認を同じ手段でやり直す。古い結果を更新後の版へ貼り替えない。

## 9. 人の関与、S5の判定、引き継ぎ

### 9.1 SEC-06の関与方針を適用する

| 判断場面 | 人が決めること | 条件内でCopilotへ任せること |
| --- | --- | --- |
| 生成前 | 要件、仮想構成、管理範囲、編集対象 | 根拠の抽出、構成案と対応表 |
| 生成・変更中 | 範囲変更、未決仕様、依存・通信・実行の可否 | 合意範囲の定義作成、差分、説明 |
| 追加要件 | 環境の区分、state分離方針、成果物の再利用契約 | 影響調査、必要な差分、整合性の照合 |
| レビュー後 | 指摘採否、訂正範囲、未設定事項の扱い、S5 | 根拠の整理、許可済みの再確認、引き継ぎ案 |

HITLの必須判断点を残し、合意範囲の作業は観測しながら任せる。すべてのファイル編集を毎回止めることも、すべてを無条件に任せることも目的にしない。
実接続、資格情報の探索、state操作、アプリ変更、対象外の資源追加が提案・開始されたら、その作業を止めて人へ戻す。
停止は変更の取り消しではない。差分と取得済みファイル等を確認し、成果を保持したうえで、範囲と再開条件を決め直す。

Copilotの作業を人が監督することと、将来のパイプラインに承認制御を設けることは別である。
Azure PipelinesのEnvironment等の資源に設定する承認・チェックは、パイプラインYAMLとは別に管理される。
YAML内の待機処理やコメントだけを、それらの制御と同じものとして扱わない。
誰が何を確認して承認するかを引き継ぎに残し、実際の権限・設定・実行確認は未実施とする。

### 9.2 S5の到達条件

| 判定材料 | 必要な状態 |
| --- | --- |
| 対象と要件 | 対象版、講師教材の利用有無、要件票と採用した構成が特定できる |
| 定義案 | Terraform・Azure Pipelinesの主要部を構成し、DR-IDと対応づけて説明できる |
| 追加要件 | DR-11・DR-12の差分と、維持した条件を説明できる |
| 横断レビュー | 入出力、環境、state、設定、成果物、品質・進行条件を照合し、指摘の採否を残している |
| 確認範囲 | 実施した確認に根拠があり、未実施・未設定・未決と実環境での確認を区別している |
| 引き継ぎ | 残課題、非実行の境界、人が次に判断することが具体的に分かる |

今回定義化する主要要件の欠落、矛盾、採用した指摘への未対応が残ればS5は保留し、構成・修正へ戻る。
実接続情報や実環境での検証が未完了でも、その扱いと次の確認を合意して引き継げれば、定義と引き継ぎ案としてのS5は評価できる。
S5は配備成功・本番適合・運用準備完了を意味しない。S4未達の本編を、講師教材でのS5相当の学習によって達成済みにもしない。

### 9.3 学習の達成と支援を分ける

| 評価するもの | 確かめる説明・操作 | それだけでは達成としないもの |
| --- | --- | --- |
| 要件整理 | 事実・要件・未決を区別する | AIの一覧をそのまま受け取ること |
| 生成 | 主要部を依頼して構成し、必要な理由を説明する | 完成例の名前だけを置換すること |
| 変更 | 影響を考え、両定義の差分と維持条件を説明する | 全文を再生成して差分を読まないこと |
| レビュー | 根拠と要件から採否を判断する | AIの「問題なし」や指摘数だけ |
| 確認の理解 | 手段、結果、限界、次の確認を説明する | YAMLが読めたことやfmtの成功だけ |
| 引き継ぎ | 他の担当が対象と残課題を追える | 「あとでAzureへ適用する」とだけ書くこと |

自分で生成・変更した部分、講師の骨組み・完成例を使った部分、実行、記録読解、支援利用を分けて記録する。
ローカル確認を実行できなくても、理解した範囲は評価する。ただし未実施を成功にせず、読解のみを生成体験の達成に置き換えない。
成果物が同じ形でも、要件や受け渡しを説明できない場合は、必要な箇所へ戻って確認する。

### 9.4 引き継ぎメモ

```text
対象版・差分、S4の状態、講師教材を使った場合の識別:
要件票の版、採用した仮想構成、管理する範囲:
DR-IDと定義箇所の対応、追加要件で変更・維持したこと:
Terraformの入力・出力・stateと、パイプライン側の受け渡し:
起動・依存・確認の契約、成果物の形式・内容・版の識別:
レビュー指摘の採否、訂正、更新後の確認と原記録:
実施済みの確認と限界、未実施・未設定・未決事項:
実行対象外の段階と、接続・適用・配備を行わない境界:
環境側で必要な権限・接続・承認、実環境での確認:
データ保持、公開制御、認証・監査・バックアップ等の本番化の不足:
人の関与方針、実際の判断、次に人へ戻す条件:
S5の判定と不足、学習の達成、自力・記録読解・講師支援:
次の担当が判断すること:
```

運用メモには、既知のローカル起動・確認方法と、将来の環境で確認するログ・障害調査・復旧の論点を分けて残す。
未実行のクラウド起動・ロールバック・DB復旧を、確認済みの運用手順として記載しない。
SEC-08へは、この引き継ぎと、探索・生成・修正・レビューで観察した手戻りを渡す。
SEC-08では一場面の根拠として読み、独立した共通課題の比較から採否・使い分け・改善手順へつなぐ。今回の定義や初回生成・追加要件の数値を、そのA/Bへ流用しない。
改善設計シートの机上確認は開始・確認・停止の説明を確かめるものであり、SEC-07の未実施の検証や実配備を完了にするものではない。

## 10. トークンエコノミーと実務への応用

必要な入力は、要件票、対象版、起動・確認の正本、採用した構成、関係する定義、確認結果である。
全履歴やすべてのAzureサービスの資料を毎回渡すのではなく、対象と根拠を絞る。ただし、条件や未確認事項を削って短くすることを効率と呼ばない。

| 観察すること | 実務へ持ち帰る問い |
| --- | --- |
| 生成前の前提整理 | 配備先や確認手順が不足して、不要な質問・探索・生成が増えなかったか |
| 要件対応表 | どの要件を直すかが分かり、同じ説明を繰り返さずに済んだか |
| 追加要件への差分 | 全文再生成より変更を追いやすかったか。必要な関連箇所を落としていないか |
| 両定義の受け渡し | 名前や設定の重複・不一致による手戻りがどこで起きたか |
| 人の判断と確認 | 決めるべき前提を先に決めたか。未検証を成功とするための無駄な試行を避けたか |
| 再利用する情報 | 恒常的な指示、再利用する手順、案件ごとの要件を分けられるか |

取得できる利用量は単位と集計範囲を付け、未取得を0にしない。改善率・費用・時間の見積もりを作らない。
SEC-07の初回生成と追加要件対応は、入力・目的・出力が異なる学習過程であり、同条件の比較実験ではない。
これらの数値をSEC-08のA/Bへ合算せず、既存の比較条件・課題・コピーを維持する。

別の開発へ応用する際も、生成されたTerraformやYAMLをそのまま移すのではなく、要件、対応版、データ、権限、成果物、確認方法を調べ直す。
持ち帰るのは、目的を定義へ対応づけ、根拠と限界を説明して変更・引き継ぎを進める方法である。

## 11. 講師準備、ヒント、停止と代替進行

### 11.1 教材化前に準備するもの

| 準備対象 | 確認すること |
| --- | --- |
| 仮想構成と要件票 | 一つの構成と実行・成果物の契約が整合し、実顧客の環境を模していない |
| 骨組みと生成箇所 | 足場を渡しつつ、両定義の主要部を参加者が生成する余地がある |
| 仕様と版 | Terraform・プロバイダー・Azure Pipelinesのタスク・実行環境の参照が揃う |
| ローカル確認 | ツール、依存、取得元・通信、ロック、対象範囲、副作用、結果の見方を準備する |
| 非実行CD | 未設定の資源参照、既定の除外、手元で行わない操作を明示する。制御の実証とは分ける |
| 追加要件 | DR-11・DR-12の提示順、期待する影響、維持条件、異なる妥当な解への評価を用意する |
| 確認・支援用資料 | 実記録と説明用の状況を分け、対象版・条件・出所・未実施を示す |
| 評価と引き継ぎ | S5、生成・変更の学習、ローカル確認、支援利用を別に記録できる |

骨組み、講師用の完成例、追加要件の解説は、[テンプレート方針](../template-strategy.md)に沿って公開範囲と提示時点を決める。
別フォルダーに置くだけで解答を隠せるとは考えない。講師が使える外部サービスや権限を、参加者にもあるものとして準備しない。

### 11.2 ヒントとつまずきへの対応

| 状況 | 講師の対応 |
| --- | --- |
| 何を入力すればよいか分からない | 要件票と起動・確認の正本を示し、事実・要件・未決を分ける問いへ戻す |
| 大きな構成が生成される | 管理範囲とDR-02へ戻し、各資源の必要な理由を説明させる |
| 主要部を完成例からコピーしただけ | 要件から自分で一部を再構成し、理由を説明する支援へ切り替える。元の成果を消さない |
| 属性やタスクが存在しない | 採用版の仕様へ戻す。見かけを合わせる架空の設定で補わない |
| validateの依存がない | 準備不備として記録し、照合・記録読解へ切り替える。当日の無断導入を前提にしない |
| 生成と成果物の関係が分からない | 作成元・登録・取得・利用先を一つずつたどり、契約表へ戻す |
| 環境名の置換だけで終わる | 資源・設定・state・成果物の対応を問い、DR-11・DR-12を分けて確認する |
| Azureへの認証や適用を求められる | 範囲外として実行せず、未設定事項と非実行定義の整理へ戻す |
| 実行していないのに成功報告になる | 根拠と確認範囲へ戻し、説明・ローカル実行・実環境実行を分ける |
| 実行なしでは不安が残る | 具体的な未検証事項と次の確認にする。成功扱いにも、無断の実接続にも進めない |
| 前工程や本編が未達 | 講師の版と骨組みで学習を続け、自力・支援・本編の未達を別に残す |

ヒントは、目的の問い、参照先、必要な構造の3段階で深め、渡した範囲を記録する。完成例とその解説は振り返り用の別資料として扱う。
講師デモ・完成例の読解へ切り替えた場合は、その理解を評価しつつ、参加者自身の生成・変更が未実施であることを残す。
原則として両定義の生成と追加要件への対応を残し、全体の試走で負荷を調整する。説明や演習の時間・回数は未測定のまま固定しない。

停止・復旧では、定義、アプリ、DB、ツールの取得物、会話を別に扱う。
参加者の差分を保存し、必要なら講師の別コピーへ切り替える。一括破棄、無断のロック更新、stateの削除・移行を復旧策にしない。

## 12. 未決事項、対象外、出典

### 未決事項の接続

| ID | ここで具体化すること |
| --- | --- |
| Q-001 | Terraform・YAML・CI/CDの経験差、要件の読解、生成・説明・変更に必要な支援 |

| Q-005・Q-006 | 参加者版の検証契約、代替用の版、既存Agent・Skillの対象範囲と役割 |
| Q-008 | 仮想構成、DR要件例の具体化、骨組み、版・タスク、成果物・stateの契約、ローカル確認、追加要件、S5の評価 |
| Q-010・Q-012 | 要件・骨組み・解説・記録の配布範囲、参照元と再利用条件 |
| Q-011 | 6段階・12プロンプト、生成・変更・照合・支援の進行と試走 |

旧案の「短いひな型の読解・一部変更を中心にする」方針は、主要部の生成と追加要件への対応を中心とする案へ更新する。
骨組み・読解・記録による支援は残すが、それだけを本編の生成体験の代わりにはしない。変更理由はP-006・P-013で追跡する。

今回の文書改訂では、Terraform・パイプラインの実習ファイル、ローカル検証環境、成果物、講師記録を作成しない。
Azure・Azure DevOpsの契約や接続、権限変更、実リソース・state操作、アプリの本番化、パイプライン実行、配備、利用量測定、教材の試走も行わない。
定義のレビューにセキュリティ上の観点を含めても、実環境のセキュリティ審査や本番利用の承認を終えたことにはしない。
