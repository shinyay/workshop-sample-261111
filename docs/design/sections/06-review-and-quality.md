## 1. 位置づけと学習目標

S3の実装候補を受け取り、レビューと追加検証を通じてS4の品質判断へ進む。
中心の問いは、**「AIの指摘を何で確かめ、何を任せ、どの地点で人が判断するか」**である。
AIにレビューさせる操作だけでなく、その結果を評価する人の関与まで設計する。

**今回の通常経路:** 共通AND/OR教材で指摘と追加検証を結ぶ → 四事例を個人で判断する → 関与方針を見直す → 本編S3へ適用してS4を判断する。
本人が採否・監督・介入を考え、講師／TAは根拠の問い返しと段階的ヒントで支援する。ペアの監督担当は設けない。
機能・モデル・観測は[共通シナリオ](../common-scenario.md)第2・10節に従う。HITL／HOTLは開発プロセスの概念であり、Previewの自動進行機能を使うことは学習の前提ではない。

| 学習の柱 | 参加者ができるようになること | 示す根拠 |
| --- | --- | --- |
| レビューの妥当性 | 正しい指摘、誤指摘、確認不足を見分け、採用・見送り・保留を判断する | AC、対象コード、問題条件、影響、採否理由 |
| 検証の妥当性 | 反例と追加確認を考え、必要な修正と回復を確かめる | 期待値の根拠、修正前後の同じ確認、回帰、未確認事項 |
| 人の関与の妥当性 | HITL／HOTLを説明し、必須判断点と委任・監督・介入条件を組み合わせる | 関与方針、事例への判断と理由、本編への適用、振り返り |

受講者のHITL／HOTLの理解を明確な学習目標にする方針はD-023で確認済み。
HOTLの監督方針と介入・継続・再開の判断を必須にし、自動進行を監督して停止・再開する実操作は発展扱いとする方針はD-024で確認済み。
以下の8段階・16本のプロンプト、四つの判断場面、評価方法はP-012の設計案であり、教材の成立性は試走で確かめる。

| 前後の学習 | SEC-06への接続 |
| --- | --- |
| SEC-01・02 | 人が目的と品質条件を判断する考え方、調査した根拠、AC、計画を使う |
| SEC-03・04 | 採用した指示、読み取り中心のレビューAgent、検証Skill、役割と権限を使う |
| SEC-05 | 同じ版の差分・実行結果・残課題と、人へ戻した判断を受け取る |
| SEC-07 | 対象版、品質根拠、起動・確認方法、残課題、関与方針を、要件に基づく定義構成へ引き継ぐ |
| SEC-08 | 判断・監督・手戻りの観察を渡す。独立したA/Bの測定値とは分ける |

参加者自身の実装に不具合があることは前提にしない。
共通の品質演習で判断方法を学んでから本編へ適用し、修正不要という結論も根拠付きで認める。
レビューに指摘がないこと、テストが成功したこと、人が承認したことのどれか一つで、残りを代替しない。

## 2. HITL／HOTLを作業の進め方として理解する

### 2.1 人が判断を待たせる地点と、監督する範囲

本研修では、Human in the Loop（HITL）とHuman on the Loop（HOTL）を、開発プロセスに人をどう組み込むかを考える概念として扱う。
学習の順序は、**人の判断を言語化する → 事前方針に移せる部分を考える → 作業ごとに組み合わせる**とする。

| 観点 | HITL中心の設計 | HOTLで監督する設計 |
| --- | --- | --- |
| 進み方 | 定めた地点では、人の判断がなければ次へ進まない | 合意範囲では作業を進め、人が観測して必要時に介入する |
| 人の仕事 | 根拠を読み、採否や次に許可する範囲を決める | 継続条件と実際の進行を照合し、介入・停止・再開を判断する |
| 事前に必要なもの | 判断点、判断材料、判断する人、待っている間の扱い | 委任範囲、観測情報、監督者、介入条件、停止・再開方法 |
| この課題の例 | AND/ORの指摘を評価してから修正を認める | 許可済みの対象確認と回帰確認を進め、別版・範囲逸脱等を検知して介入する |
| 形だけになる例 | 根拠を読まず、確認ボタンだけを押す | 状況を把握できないまま任せ、終了後の要約だけを見る |

HITLを初級、HOTLを上級とする序列にはしない。
判断の不確実性、変更の影響、観測のしやすさ、戻しやすさ、人の負担に応じて使い分ける。
同じレビュー工程でも、調査・許可済み確認の反復は監督下で進め、指摘の採否・修正範囲・未決仕様・最終品質判断では人を待つ、という組み合わせができる。

「レビュー工程全体がHOTL」と名付けるより、何の作業ループを任せているかを特定する。
各調査・確認のたびに人の内容判断を待つなら、その部分はHITLとして説明する。
条件内で進む作業を監督することと、毎回の確認を省略して放置することは異なる。

### 2.2 判断、操作上の承認、学習支援を分ける

| 人の行為 | この演習で残す内容 | それだけでは示せないこと |
| --- | --- | --- |
| 指摘の採否・仕様の判断 | どのACと根拠から、何を採用・見送り・保留にしたか | ツールが実行できるという許可 |
| 通常のツール承認 | 何の操作を、どの対象・権限で許可したか | 実装や指摘の正しさ |
| 監督・介入 | 何を観測し、どの条件で継続・停止・再開を判断したか | 全ACの最終判断 |
| 講師のヒント | 渡された情報、提示時点、自分で説明できた範囲 | ヒントなしで到達したこと |

通常の承認要求を解除してHOTLを体験させる構成にはしない。
実行基盤の許可と、学習上の品質判断の両方を守る。人の判断が必要な地点で、AIの「承認します」を人の判断の代わりにしない。

### 2.3 既存の役割と権限を維持する

| 担当・仕組み | 任せる仕事 | 人へ戻すこと・持たせないもの |
| --- | --- | --- |
| レビューAgent | 読み取り・検索、ACとの照合、指摘、追加確認の提案、再レビュー | 編集、任意のコマンド実行、無制限な委譲、最終承認 |
| 検証Skillを使う実行担当 | 合意した確認の選択・実行、失敗の切り分け、報告 | 検証中にコードや期待値を書き換えること、無断の設定・依存変更 |
| 実装担当 | 合意範囲のテスト追加・正当な訂正、採用された指摘の修正 | 未決仕様の独断確定、無関係な改修、権限拡大 |
| 人 | 指摘の採否、修正範囲、未決仕様、監督・介入、最終品質判断 | 根拠のない成功認定、未確認の事項の補完 |

SEC-04で採用した定義の配置・適用・実効ツールを、共通教材と本編それぞれで確認する。
Skillは独立した作業者でも権限付与の仕組みでもない。検証結果を確定し、その報告を受けて実装担当が修正する。
同じエージェントが担当を続ける場合も、この責務の切り替えを明確にする。
HOTLを理由にレビューAgentの権限を広げたり、検証Skillや別担当への委譲で実行制限を迂回したりしない。
別Agent・別会話であることを、客観性や作業環境の分離の保証にはしない。

### 2.4 必須と発展の境界

| 区分 | 参加者が行うこと | 到達の記録 |
| --- | --- | --- |
| 必須: HITLの理解と適用 | 共通教材と本編で、指摘・根拠を評価し、人の必須判断点を説明する | 自分の判断と理由、講師支援の有無 |
| 必須: HOTLの理解 | 監督方針を作り、四つの共通事例で介入・継続・再開条件を判断する | 方針、提示情報、判断理由、見直し |
| 必須: 品質確認 | 共通教材で追加検証・修正・再レビューを行い、本編も必要な確認へ進める | 対象別の実行根拠、指摘の状態、S4の判定 |
| 発展: HOTLの実操作 | 準備済み環境で自動進行を監督し、必要時の停止・再開を操作する | 実際に観測・操作した対象と結果、未実施の操作 |

事例判断を行っただけで、自動進行の監督・停止・再開を操作した成果とは記録しない。
発展実操作も非Previewの機能で事前に成立を確認できる場合に限る。Previewの監督・診断機能や、安全条件の解除を代替にしない。
逆に、発展実操作が未実施という理由だけで、必須のHOTL学習を未達にはしない。
必須の事例判断や関与方針だけで、本編のS4へ到達したことにもならない。

## 3. 開始条件と教材の分離

### 3.1 S3から受け取るもの

SEC-05の引き継ぎ票を使い、対象版と未コミット差分、ACと変更・確認の対応、実行コマンドと結果、画面/API・回帰、計画との差、残課題を揃える。
既に決めた委任範囲、人へ戻した仕様・範囲の判断、通常の承認、講師支援も振り返る。
過去に人へ相談したことだけを根拠に、SEC-05でHOTLの実操作まで学習済みとはしない。

| 確認するもの | 開始時に区別すること |
| --- | --- |
| 作業対象 | 本編のコピー・差分・データと、共通教材のコピー・差分・データ |
| 品質の根拠 | 現在の版の結果と、変更前・別コピー・未実行の説明 |
| AC | 共通シナリオ第7節の正本と、未決の追加仕様 |
| 設定 | 講師指定の固定モデル、採用した指示・役割・Skill、実効ツール |
| 人の関与 | 内容を判断した地点、操作を許可した地点、支援を受けた地点 |
| 不足 | 未実施・未確認、修正後に再確認していない結果、未解決の失敗 |

代表ACのテスト先行やS3の引き継ぎ票だけで、全ACのレビューが済んだとはしない。
不足があればその範囲を明示し、本編の到達状況を保留したまま共通教材で学ぶこともできる。
講師の教材で進めた成果を、自分の実装の確認済み範囲へ足し込まない。

### 3.2 二つの作業と判断用事例

| 対象 | 用途 | 混ぜないもの |
| --- | --- | --- |
| 自分の実装 | S3の差分をレビューし、必要な確認・修正をしてS4を判断する | 共通教材の修正・実行結果 |
| 共通の品質演習 | 独立したAND/OR欠陥を使い、指摘・反例・追加検証・修正を学ぶ | 本編のコード・DB、SEC-03・04の比較コード |
| 判断用事例 | 正しい指摘、誤指摘、根拠不足、正常進行への人の関与を考える | 実際のCopilotの出力や実操作の記録という扱い |

最初に共通教材で判断方法を揃え、その後に本編へ戻る。
HITL／HOTLで改修全体を二重に実行することは必須にせず、同じ品質課題の判断場面を対比する。
先に学んだ知識、ヒント、事例の提示順が影響するため、検出能力や費用の独立した比較実験とは扱わない。

SEC-05で講師の失敗記録を読解した場合も、この節の共通演習と本編レビューは省略しない。
SEC-05の読解記録、SEC-06の判断事例、SEC-08のA/Bは別の教材・根拠である。

### 3.3 講師が準備するもの

| 準備物 | 成立させる条件 |
| --- | --- |
| 正常版・欠陥版・修正版 | 絞り込み実装済みの正常版を基準に、複合条件の結合だけを変え、同じ確認で回復を示せる |
| 課題票 | 目的、AC、維持条件、対象外、既知の情報を示し、修正方法を先に教えすぎない |
| データと確認資産 | 期待集合を独立に説明でき、正常・欠陥・修正版へ同じ確認を適用できる |
| 作業コピーと実行環境 | 本編と独立し、DB、サーバー、ポート、版、復旧対象を識別できる |
| レビュー用の資料 | 対象差分と実際の確認結果を対応づけ、未確認・未実施を明記する |
| 四つの判断用事例 | 提示情報、追加情報、判断理由の解説を分け、事例の出所を表示する |
| 関与方針と記録欄 | 委任・必須判断・監督・介入・再開を、既存の引き継ぎ票へ追記できる |
| 支援と評価 | ヒント、代替記録、独立コピーでの再開、品質と学習の別判定を準備する |
| 発展実操作 | 実際の観測・停止・再開と副作用を確認できる場合だけ用意する |

実出力を教材化するときは原記録を確認し、対象版・実行条件・提示範囲を残す。
説明用に作る事例はその旨を明記し、架空のテストログ、利用量、時刻等を実測風に補わない。
講師用の解説をいつ提示するかは、リポジトリの履歴・閲覧権限も含めてQ-010で判断する。
欠陥と追加確認の一時的な補助試走は行ったが、配布用資産や発展の実操作環境は未提供であり、以下をそのまま実行可能な参加者手順とはしない。

## 4. 8段階の進行案

| 段階 | 対象と作業 | 残す成果 |
| --- | --- | --- |
| 1 | S3と判断点を整理する | レビュー対象、根拠の不足、人の判断点 |
| 2 | 人の関与を具体例から理解する | HITL／HOTLの説明、関与方針の初案 |
| 3 | 共通教材をHITL中心でレビューする | 指摘の評価、期待結果、追加確認の方針 |
| 4 | HOTLでの監督を設計・判断する | 監督方針、事例への判断、見直し |
| 5 | 共通教材で追加検証・修正・再レビューを行う | 問題の検出と回復、指摘の解消状態 |
| 6 | 自分の実装へ適用する | 本編のレビュー・確認・採否・関与の記録 |
| 7 | 人が品質を判断する | S4の根拠、または未達・保留の理由 |
| 8 | 関与方針を振り返り、引き継ぐ | SEC-07への引き継ぎ、別の開発への適用案 |

以下は開始・追加各8本、計16本のプロンプト案。
追加プロンプトは必要に応じて使い、全件を機械的に投入することは求めない。
段階5・6は確認と修正を反復し、段階7で不足が見つかったら該当する作業へ戻る。
各依頼の前に対象と担当を確認し、読み取り担当へ実行や編集を要求しない。

### 段階1: S3と判断点を整理する

**目的・入力:** 本編S3の引き継ぎ票、差分、AC、実行記録から、何をレビューでき、何が不足しているかを明らかにする。

**参加者の作業:** 現在の版に使える根拠を選び、修正前・別コピーの結果を分ける。
SEC-05で任せた範囲と人へ戻した判断を挙げ、今回の必須判断点の候補を記入する。

**講師の介入:** 成功という要約だけ、別版の実行結果、対象のないログを見分ける問いを出す。全体調査を最初からやり直させない。

**開始プロンプト案（読み取り担当）**

```text
本編S3の引き継ぎ票、差分、AC、実行記録を整理してください。
現在の版の判断に使える根拠、別版の結果、未実施・未確認を分けてください。
ACと変更・確認の対応、残課題、レビューへ渡すべき参照先を示してください。
編集や実行はせず、不足する根拠を取得するための次の作業を提案してください。
```

**追加プロンプト案**

```text
SEC-05で任せた範囲と、人へ戻した判断を提示します。
内容に関する判断、通常のツール承認、講師の支援を分けてください。
今回のレビューで人の判断を待つべき地点と、事前方針内で進められる作業の候補を挙げてください。
過去に行ったことが記録にない場合は、実施済みと補わないでください。
```

| 成果 | 人の判断 | 終了条件 |
| --- | --- | --- |
| 対象・根拠・不足の一覧、判断点の候補 | どの版をレビューし、何を先に補うか | 本編と共通教材、現在の根拠と不足を説明できる |

### 段階2: 人の関与を具体例から理解する

**目的・入力:** 第2節の進行例と、段階1の判断点からHITL／HOTLを自分の言葉で説明する。

**参加者の作業:** 指摘の採否、許可済みの調査、検証の反復、期待値の変更、最終判断を分類し、理由を先に書く。
第7節の方針票へ初案を記入する。用語を当てるだけでなく、誰が何を見て判断するかを考える。

## 5. AND/OR欠陥から検証の妥当性を学ぶ

### 5.1 正常版、欠陥版、修正版

P-004を維持し、絞り込みが正しく動く講師用正常版から、複合条件の結合だけをANDからORへ変えた欠陥版を用意する案とする。
絞り込み未実装の開始アプリが有効な検索に400を返すことは、別の状態であり、この欠陥の検出ではない。
単独条件は正しく、複合条件だけが間違う形を準備時に確かめる。

| 版 | 講師が示す対応 | 参加者の結果と分けること |
| --- | --- | --- |
| 正常版 | 同じ品質確認が成立する、絞り込み実装済みの基準 | 開始版や参加者自身の実装ではない |
| 欠陥版 | 狙った結合だけが変わり、追加確認が仕様不一致で失敗する | 起動・fixture不備や、関係のない故障ではない |
| 修正版 | 原因に対応する差分で同じ確認と回帰が成立する | 期待値を誤実装へ合わせた成功ではない |

パッチを使う場合は、適用後のコードの形まで調べる。
文字列やバイトが変わったこと、パッチが適用できたことだけで、狙ったANDからORへの変更が成立したとはしない。
参加者の修正は講師と同じ差分である必要はなく、ACと変更範囲で評価する。

### 5.2 期待集合を先に説明する

データの正本は[共通シナリオ第8節](../common-scenario.md)の6行を使う。
次の表は説明用の期待値であり、実行結果ではない。F1〜F6は実DBのIDでもない。

| 問い合わせ | 正しいANDでの集合 | 複合条件だけをORにした場合 |
| --- | --- | --- |
| `department=engineering` | F1、F2 | F1、F2。単独条件では違いが出ない |
| `status=pending` | F1、F3、F5 | F1、F3、F5。単独条件では違いが出ない |
| `department=engineering&status=pending` | F1 | F1、F2、F3、F5 |
| `department=design&status=approved` | 空集合 | F2、F5、F6 |

実テストへ使う際は専用fixtureと実際のIDの対応を準備する。
参照元の初期デモデータを混入させず、テスト用DBと手動用DB、実行中のコピーを揃える。
期待集合はACと既知データから独立に作り、製品コードと同じ絞り込み関数だけから生成しない。

| 弱い確認 | 見逃し得ること | 補う確認 |
| --- | --- | --- |
| 単独条件が成功する | 複合条件の結合だけが誤っている | 両方一致・片方だけ一致・どちらも不一致を含むデータ |
| F1が含まれる | F1以外の不要な行も返っている | 期待するID集合との一致 |
| 件数だけが一致する | 同数の別の行へ入れ替わっている | ID集合と各行の値 |
| 返った行がすべて条件を満たす | 必要な行が欠ける。空一覧なら条件判定が一度も行われない場合もある | 期待集合の完全性、非空の条件、正常な0件を別々に確認 |
| IDを集合に変換して一致する | 同じIDの重複が消える | 元の一覧の長さ、重複の有無、APIの`count` |
| APIの対象集合だけが正しい | UI、並び順、全体集計、条件解除が違う | AC-07〜AC-10に対応するコード・実画面・回帰 |

集合の列挙順を、そのままアプリの正しい並び順とはしない。順序は既存契約に基づいて別に確認する。
全体集計はこの説明用データなら6件、確認待ち3件、承認済み2件、差し戻し1件。
データを変えていなければ、一覧がF1の1件になっても、この集計は変わらない。

### 5.3 失敗と回復の根拠を揃える

追加した確認が実際に起動・収集・実行され、対象の不一致で失敗したかを見る。
インポートエラー、fixture不備、別DB、古いサーバー、テスト未収集を、AC-04を検出した結果とはしない。
途中のアサーションで停止した場合、後続の集合・件数・値の確認まで実行済みと数えない。

修正後には、欠陥を検出したのと同じ確認を実行する。
テスト自体を正当に訂正した場合も、訂正後の同じ確認を欠陥版と修正版で確かめる。
すでに修正した本編を巻き戻すのではなく、保持した修正前の独立コピーを使う。確かめられない場合は検出能力が未確認と残す。

修正後の確認は複合条件だけで終えない。
単独、未指定・空文字・片方だけ空、正常な0件、不正値・検索キーの重複・未対応キー、UI/API、結果件数と全体集計、既存操作への回帰を、ACとの対応で選ぶ。
すべてを一つのテストへ詰め込まず、失敗時にどの契約を確かめられたか分かる構成にする。

## 6. 人の判断を学ぶ四つの場面

以下は講師向けの事例設計であり、実際のAI出力を報告するものではない。
参加者への最初の提示では「正しい」「誤り」といった解説用ラベルを伏せ、事例として与える情報と出所を明示する。
参加者の判断後に追加情報と解説を示す。実際のCopilotが四種類すべてを出すことに依存しない。

### 場面A: 正しい指摘を、根拠から採用する

| 項目 | 設計する内容 |
| --- | --- |
| 提示する情報 | AC-04、既知データ、単独条件の確認資料、複合条件をORで結ぶコードと、それを問題候補とする指摘 |
| 最初に考えること | 指摘のどこがACと矛盾し、どの入力・期待集合なら違いが出るか |
| HITLでの判断 | 反例と確認方針を評価し、必要な根拠を得てから指摘の採用と修正範囲を決める |
| HOTLでの判断 | 許可済みの追加調査・確認は進められるが、確認結果から修正へ移る地点では人の判断を待つ |
| 追加情報と見直し | 準備済み教材で得た実際の複合条件の結果を提示する。期待集合との不一致か、環境不備かで次の作業を変える |
| 説明する理由 | AIの自信ではなく、AC、コード、データ、結果の対応から判断する |

コードの矛盾を説明できたことと、実行で再現したことは分ける。
この共通演習では反例の実行まで学ぶが、一般の構造・範囲の指摘すべてへ失敗テストを要求するものではない。

### 場面B: もっともらしい誤指摘を見送る

| 項目 | 設計する内容 |
| --- | --- |
| 提示する情報 | AC-08、一覧と全体集計の定義、「絞り込み後は全体集計も一覧と同じ件数に合わせるべき」という説明用の提案 |
| 最初に考えること | APIの`count`、画面の結果件数、全申請の総数・状態別集計のどれを指しているか |
| HITLでの判断 | 全体集計を変える提案は、現行AC-08と矛盾するため見送る |
| HOTLでの判断 | ACと矛盾する変更へ進もうとしていたら介入する。提案を読むだけなら、その場でコードを変更させない |
| 追加情報と見直し | 対象が全体集計ではなくAPIの`count`だと分かった場合は、別の指摘として実際の`items`との対応を調べる |
| 説明する理由 | すべての数値を揃えることが正しさではない。集計対象を仕様から区別する |

誤提案に従って一度壊す操作は必須にしない。
AC-08の新しい欠陥を直す演習も必須にせず、SEC-08の件数不整合の小課題を前倒ししない。
仕様そのものを変えたい場合は別の要件判断であり、レビューの提案だけでACを更新しない。

### 場面C: 根拠不足の成功報告を保留する

| 項目 | 設計する内容 |
| --- | --- |
| 提示する情報 | 「確認は成功した」という説明用の要約に対し、対象版・コマンド・出力の一部がない、または記録が修正前の版を指す状況 |
| 最初に考えること | 実行されたか、どの版か、何を確認したか、修正後も使える根拠か |
| HITLでの判断 | 品質判断を保留し、足りない根拠の取得を依頼する。成功にも失敗にも決め付けない |
| HOTLでの判断 | 根拠が必要な次の工程へ進むことには介入し、許可範囲の記録確認や再実行へ戻す |
| 追加情報と見直し | 現在の版・データ・実行対象と結果が揃えば、その範囲の判断に使う。別版なら必要な確認をやり直す |
| 説明する理由 | 要約の確信度ではなく、再参照できる実行根拠が必要である |

不足する原記録をAIに作らせない。事例の中で情報が未提示なら、追加情報を求める判断自体が成果になる。
判断保留のために、無関係な作業まで一律に取り消す必要はない。何がその根拠に依存するかを示す。

### 場面D: 正常な進行を継続させる

| 項目 | 設計する内容 |
| --- | --- |
| 提示する情報 | 対象版と一時DB、許可済みの確認範囲、現在の作業と結果、次の回帰確認、人の最終判断点が対応した説明用の進行事例 |
| 最初に考えること | 次の作業が委任範囲内か、観測できるか、介入条件に当たっていないか |
| HITLとの対比 | 確認単位ごとに人を待つ方針なら判断を行う。監督下で進める方針なら毎回同じ承認を追加する必要はない |
| HOTLでの判断 | 条件内の回帰確認を継続させる。最終品質判断を自動で通過させるわけではない |
| 追加情報と見直し | 新しい権限、別コピーの結果、範囲外の変更が判明したら、継続判断を見直して介入する |
| 説明する理由 | 止めること自体を目的にせず、委任範囲と観測結果から必要性を判断する |

正常な事例でも観測と理由が必要であり、「AIを信頼しているから」だけでは継続の根拠にならない。
停止回数や承認回数を増やすことを、監督能力の評価指標にはしない。

## 7. 人の関与方針を記入し、見直す

S3の引き継ぎ票へ次の項目を追加し、大きな別冊報告書を作ることを目的にしない。
初案、事例後の見直し、本編で使った方針を識別し、変えた理由を短く残す。
次の例は方針の記入例であり、既に設定・稼働している制御ではない。

| 項目 | 本編レビューでの記入例 |
| --- | --- |
| 対象と作業ループ | 指定した本編の版・差分について、読み取り調査と許可済み確認を進める範囲 |
| 委任する作業 | レビュー担当は根拠の調査・指摘まで。実行担当は準備済みの対象確認・回帰・報告まで |
| 必須の人の判断点 | 指摘の採否、修正範囲、未決仕様、最終品質判断。必要な通常のツール承認も別に守る |
| 監督する人 | 参加者本人。講師／TAが支援した場合は、現在の対象・結果・未決と支援内容を残す |
| 観測する情報 | 対象版、現在の作業、変更範囲、AC、実行結果と参照先、失敗・未確認事項 |
| 観測する節目 | 確認単位の終了、失敗・対象変更・範囲変更の発生時、次の人の判断点へ進む前 |
| 継続条件 | 次の作業が委任範囲と権限内で、根拠・対象が対応し、停止条件に当たらない |
| 介入条件 | ACとの矛盾、判断に必要な証拠の不足、対象版・DBの取り違え、範囲逸脱、新しい権限、根拠の増えない反復 |
| 停止対象と保持するもの | 条件に抵触した作業と、それに依存する進行を止める。差分・記録を保持する |
| 再開条件 | 人が停止理由の解消、対象と差分、残る確認、委任範囲・権限を確認する |
| 終了と引き継ぎ | 最終版の必要な根拠を人へ渡す。自動承認・マージ・配備まで含めない |

監督者が状況を観測できず、必要時に介入できないなら、監督を前提とした自動進行は開始・継続しない。
必須演習では、この条件を事例に適用して説明する。発展で実操作する場合は、観測と停止の方法を事前に確かめる。

### 作業名だけで止めるかを決めない

| 状況 | 判断の考え方 |
| --- | --- |
| 同じACの追加調査が必要 | 委任済みの読み取り範囲なら継続できる。未知の仕様の確定は人へ戻す |
| 新しいテストが必要 | 実装担当へテスト追加を委任済みか、AC・変更範囲・副作用が合意内かで決める。レビューAgentは作成しない |
| テストの期待値を変えたい | ACに照らした正当な訂正かを人が判断する。成功させるだけの変更は採用しない |
| 別の回帰確認を実行したい | 許可済みの確認範囲と環境内かを確かめる。名前が新しいという理由だけで一律に止めない |
| 依存・権限・外部接続を追加したい | 今回の委任範囲を越えるため止め、人へ戻す |
| 修正後の差分が増えた | 合意した修正との対応を調べ、無関係な変更や影響不明があれば介入する |

停止は取り消しではない。すでに変更されたファイルやDB、実行中の処理、外部への副作用が自動で戻るとは考えない。
発展実操作では、何が止まり何が残ったかを観測してから再開する。
参加者の未コミット変更の一括破棄・stash、対象不明のDBリセット、完成例の上書きを復旧手順にしない。

## 8. 指摘、追加検証、修正を結び付ける

### 8.1 レビューで揃える根拠

レビュー依頼には対象版・差分・AC・実行結果・未確認事項を付ける。
担当を変えるだけで独立した裏付けを得たとせず、コード・仕様・実行という異なる根拠を照合する。

| 観点 | 対応する条件 | 確認すること |
| --- | --- | --- |
| 条件の意味 | AC-01〜AC-05 | 未指定・空文字・片方だけ空、単独・複合AND、正常な0件 |
| 入力境界 | AC-06 | 不正値（コードと完全に一致しない値を含む）、同値を含む検索キーの重複、未対応キーを400とし、黙って無視しない |
| 経路と件数 | AC-07・AC-08 | 共有取得処理、同じ対象、一覧の実数と`count`、全体集計の不変 |
| 画面と既存機能 | AC-09・AC-10 | 選択・解除、詳細・作成・状態変更、入力検証、並び順・表示・配色 |
| 変更範囲 | AC-11 | SQLのパラメーター化、実データ・秘密情報・外部公開・不要な依存を追加しない |

影響の大きさと根拠の確かさを別に書く。
重大そうだが未確認の指摘は、優先して調べる候補であって、確認済みの不具合ではない。
「改善できる」「一般にはこうする」という提案も、現在のAC違反と区別する。

### 8.2 採用・見送り・保留

| 判断 | 根拠と次の行動 |
| --- | --- |
| 採用 | ACと問題条件が対応する。必要な確認を踏まえ、修正範囲と再確認を決める |
| 見送り | 指摘が仕様と矛盾する、対象外、既に別の根拠で否定できる等の理由を示す |
| 保留 | 仕様、対象版、実行結果等が足りない。不足と追加確認、判断を再開する条件を示す |

見送り理由を「AIが間違えたから」だけにせず、どの根拠と矛盾するか説明する。
保留を放置せず、品質判断を妨げるものと対象外の提案を分ける。
コード構造や無関係な変更の有無は、差分・参照関係・ACでも評価できる。すべての指摘に失敗テストを要求しない。
一方、実行で確かめるべき振る舞いを、コードの説明だけで実行済みにはしない。

### 8.3 修正と再レビュー

修正依頼は、採用した指摘、AC、原因の根拠、変更範囲、同じ確認と必要な回帰に絞る。
検証Skillの報告から実装担当へ戻す流れを維持し、検証中に期待値を書き換えて成功にしない。
テストの訂正が必要なら、人がAC・fixture・実行対象との関係を確認する。

再レビューでは、指摘した箇所が変わったかだけでなく、原因が解消したか、確認がその原因を捉えているか、別の条件を壊していないかを見る。
修正後の同じ版の根拠を渡し、コードの再修正があれば影響する確認を再実行する。
追加確認が不要と判断した部分も、既存の何で足りるかを説明する。

参照元のpytest・Ruff・mypy等は、参加者版の検証契約で対象を確定してから使う。
単一テスト、静的確認、開始版識別、完成例パッチの適用可否を、全ACやUIの確認の代わりにはしない。
具体的な起動・検証契約は[SEC-05第3節](05-implementation-and-debugging.md)とQ-005を参照する。

## 9. 品質、学習、実施方法を別々に記録する

### 9.1 指摘と根拠の記録

```text
対象: 本編 / 共通品質演習 / 判断用事例
版: コミット、未コミット差分の識別、作業コピー、データ
指摘: 対象箇所、問題条件、影響するAC、影響の大きさ
根拠: コード上の事実、実行済みの結果、未検証の仮説、原記録の参照先
判断: 人による採用・見送り・保留、理由、再開に必要な情報
修正: 許可した範囲、実際の差分、テスト訂正があればその理由
再確認: 修正後の版、同じ確認、必要な回帰、実行結果、未実施・未確認
関与: 適用した方針、必須判断点、継続・介入・停止・再開の判断と理由
方法と支援: 自分の操作 / 判断事例 / 講師記録の読解 / 講師支援
```

対象版と差分を伴わない「合格」を残さない。
要約には必要な出力と参照先を付け、再調査のために原記録へ戻れるようにする。実データ・秘密情報を含むログは渡さない。
事例の判断欄を埋めることと、実際に停止操作を行って結果を確認することは別の記録である。

### 9.2 S4の判定

| 判定材料 | 必要な状態 |
| --- | --- |
| 対象の識別 | 本編の最終候補と差分・データを特定できる |
| ACの根拠 | AC-01〜AC-11の確認方法と根拠が対応し、必要な振る舞い・画面・範囲を確認している |
| レビュー | 指摘の採否と理由があり、指摘なしの場合も確認範囲と不足が分かる |
| 修正と回帰 | 必要な修正と、修正後の同じ確認・必要な回帰が終わっている |
| 残課題 | 未実施・未確認・対象外を分け、品質判断を妨げる事項が残っていない |

必要なAC・回帰の根拠が不足していればS4未達または判断保留とし、不足する確認・修正へ戻る。
今回の対象外である本番化の不足などは、S4へ到達していても残課題として引き継ぐ。
共通欠陥の修正成功、方針票の完成、講師の正常版での再開だけでは、本編のS4を認定しない。
S4はローカル研修の品質判断であり、本番適合や完全なセキュリティ審査の認定ではない。

### 9.3 学習の到達と支援

| 評価するもの | 示す成果 | それだけでは達成としないもの |
| --- | --- | --- |
| 共通品質演習 | 反例、欠陥の検出、修正前後の同じ確認、再レビューの説明と実行根拠 | 解説を読んだことだけ |
| HITLの理解 | 必須判断点で、AC・根拠から採否と理由を説明する | 承認ボタンを押したことだけ |
| HOTLの理解 | 方針を作り、四事例に介入・継続・再開条件を適用して見直す | AIの作業を眺めたこと、方針だけを書いたこと |
| 使い分け | 委任範囲と人の判断点を本編に合わせて組み合わせる | 工程全体へ一つのラベルを付けること |
| 振り返り | 実際の判断と方針の差、必要・不要だった介入、改善案を説明する | 指摘数・承認数・停止数の多さ |
| 発展実操作 | 実際に監督・停止・再開した対象と結果を示す | 事例判断や講師記録の読解で代替したという扱い |

各欄に達成・未達・未実施、支援の種類、自分で説明・操作できた範囲を残す。
共通演習を講師記録の読解へ切り替えた場合は、読解できた成果を認めつつ、自力の実行・修正は未実施として残す。
本編が品質条件を満たしても関与方針を説明できなければ学習上の課題が残り、概念を理解しても本編の確認が不足すればS4には進まない。
発展の実操作が未実施でも、必須のHOTL理解は方針と事例への判断で評価できる。

### 9.4 SEC-07への引き継ぎ

```text
本編の対象版・差分・データ:
S4の判定と根拠、未達・保留ならその理由:
ACごとの確認結果と参照先:
指摘の採否、修正と再確認:
必要な起動・検証方法と確認範囲:
人の関与方針、実際の判断、次に人へ戻す条件:
学習方法、講師支援、発展実操作の実施範囲:
未実施・未確認、既知の非本番条件:
次の担当が確認・判断すること:
```

S4未達でも、講師が用意した版・根拠・要件票・骨組みでSEC-07の定義構成を学ぶ選択肢は残す。その際も本編の未達と、講師提供部分・自分の作業を分ける。
SEC-07では機能ACと配備・自動化の要件を分け、起動・依存・確認の契約をTerraformとAzure Pipelinesへ対応づける。未コミット差分を含む本編の版と、将来CIが取得する版の違いも引き継ぐ。
関与方針の記述を、技術的な制御や運用の停止・復旧手順を実装・検証したことにしない。

## 10. トークンエコノミーと実務への応用

効率は、必要な品質へ到達するまでの人とAIの進め方で考える。
人の判断を減らせば必ず効率が上がるわけではなく、判断材料の不足や介入の遅れで手戻りが増えることもある。
一方、条件内の確認まで毎回止めれば、同じ説明・承認待ちが繰り返される可能性がある。

| 観察すること | 改善を考える問い |
| --- | --- |
| レビューの入力 | AC・差分・結果・未確認が揃い、全体の再調査を避けられたか |
| 指摘の形式 | 条件と根拠が明確で、人が採否を判断できたか |
| 判断待ち | 必要な判断点だったか、同じ判断を繰り返していないか |
| 監督の負担 | 必要な情報へ到達でき、過剰なログで重要な変化を見失わなかったか |
| 介入と手戻り | 何を観測して介入し、不要な停止や遅れがどこにあったか |
| 担当間の引き継ぎ | 同じ根拠を再説明した負担と、役割分離による確認の価値は何か |

利用量を取得できる場合は、単位、要求・セッション等の集計範囲、入力・出力・キャッシュの内訳を記録する。
取得できなければ行動の観察として残し、未取得を0にしない。文字数から独自の費用や削減率を作らない。
実装だけの利用量を取り出して、レビュー、追加検証、人の判断、手戻りを無視した節約を主張しない。

共通教材でのHITL／HOTLの対比は学習用であり、順序・ヒント・情報の提示が同じではない。
これを検出能力やコストの優劣の実験とせず、SEC-08のA/Bへ数値を合算しない。
SEC-08では人の関与方針も共通前提にし、関連ファイルの明示だけを変える。必要に応じた実際の介入と条件差は記録する。

他の開発へ持ち帰るのは、特定のプロンプトや停止回数ではなく、影響と根拠に応じて関与を設計する方法である。
共通指示に残す規則、Agentの役割、Skillの確認手順、今回の委任範囲を分けて見直す。
コマンド、権限、データ、業務仕様、観測方法は移植先で調べ直す。
富士通固有の承認経路や標準を確認済みとはせず、一般化した開発課題で適用を考える。

## 11. ヒント、つまずき、停止・復旧

### 段階的なヒント

| 段階 | 講師が渡す内容 |
| --- | --- |
| 業務上の問い | 「両方指定したら、片方だけ一致する申請は表示されるか」「この件数は何を数えるか」 |
| データの手掛かり | 両方一致、片方だけ一致、どちらも不一致の行と、期待集合を考える材料 |
| 根拠の入口 | 関係する取得処理・条件分岐、対象版、欠けている実行記録の場所 |
| 判断の解説 | 採否、介入・継続・再開の理由を説明し、自分で到達した範囲と分ける |

ヒントの内容と提示時点を記録する。
ヒントなしの成功だけを価値とせず、受け取った根拠から自分の判断を説明できるかを見る。
事例のラベルや修正例を先に示した場合は、自力で発見した成果とは区別する。

### つまずきへの対応

| 状況 | 対応 |
| --- | --- |
| AIが欠陥を指摘しない | 指摘数を強制せず、AC・既知データ・結果の照合へ戻す |
| 誤指摘をそのまま採用しそうになる | 集計対象や契約を特定し、人が採否の理由を説明する |
| 成功の根拠が不足する | 判定を保留し、版・実行・確認範囲を補う。記録を創作しない |
| 新しいテストが起動・収集できない | 仕様不一致と分け、環境・fixtureを直してから確認する |
| 欠陥版で追加確認が通る | 対象版・データ・期待値・アサーションを調べる。別の故障を加えて失敗させない |
| 修正後だけを確認した | 保持した欠陥版の別コピーで同じ確認の検出能力を確かめる |
| 何でも止める・何も止めない | 委任範囲、観測できる条件、必須判断点へ戻す |
| レビュー担当が編集・実行しようとする | 実効ツールと役割を確認し、必要な仕事を正しい担当へ戻す |
| 同じ修正・確認を繰り返す | 新しい根拠が増えたかを確認し、影響する作業を止めて原因候補を整理する |
| 共通教材の確認を実行できない | 講師の確認済み記録で読解へ切り替え、実行・修正は未実施と残す |
| 判断事例が準備できていない | 当日の架空ログで埋めず、必須学習の未実施を明示する |
| 本編が未達だが後続へ進む | 成果を保持し、講師の教材での学習と本編の未達を分けて引き継ぐ |

復旧は、参加者の成果を保持したうえで、対象が明確な別コピーで行う。
コード、DB、会話の復旧を分け、会話の切り替えだけでファイルやプロセスも元に戻るとは説明しない。
モデル・権限・安全条件を無断で変更して進行を揃えない。

### 発展実操作を準備する場合

| 確認対象 | 開始前に必要なこと |
| --- | --- |
| 作業の上限 | 委任範囲と終了・停止条件が明確で、無制限な反復にならない |
| 観測と監督者 | 現在の作業・対象・結果を見て、監督者が必要時に介入できる |
| 停止の操作 | 対象の処理を止める方法と、継続してしまう処理・副作用を講師が確かめている |
| 保持と再開 | 差分・記録を保持し、停止理由を解消してから対象と権限を確認して再開できる |
| 判定 | 実際に行った監督・停止・再開と未実施を分けられる |

この条件を満たさなければ実操作は行わず、必須の方針・事例判断にとどめる。
安全条件を解除したり、新しい監督基盤の開発を参加者へ求めたりしない。
AC-08の集計対象の欠陥実装は別の発展候補であり、四事例の誤指摘を評価する学習とは区別する。
