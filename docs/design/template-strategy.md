## 2. GitHubテンプレートの性質

GitHubのテンプレートは、元リポジトリのディレクトリ構造とファイルを新しいリポジトリへ生成する仕組み。
通常は既定ブランチの内容を使用し、作成者は全ブランチを含めることも選べる。
テンプレートから作るリポジトリは単一コミットから始まり、元のコミット履歴を含むforkとは異なる。

テンプレートへアクセスできる人が生成できる。
したがって、元リポジトリをPrivateにしただけでは、参加者への配布や教材・履歴の共有範囲は決まらない。
生成先の所有者、公開範囲、利用できるアカウントや組織の条件も決める必要がある。

## 3. フォルダー分けと非公開化を混同しない

| 方法 | 整理の効果 | 情報を隠すためには不十分な理由 |
| --- | --- | --- |
| `instructor`などの別フォルダー | 用途を区別できる | 同じリポジトリを読める人は内容を読める |
| 別ブランチ | 進行や版を分けられる | 元リポジトリのアクセスや全ブランチ生成を考慮する必要がある |
| `.gitignore` | 追跡前の不要ファイルを除外できる | 既に追跡・公開したファイルや履歴を非公開にはしない |
| AIへ「解答を読まない」と書く | 演習の意図を伝えられる | 参加者やツールのアクセス制御にはならない |
| 既定ブランチから削除する | 今後の既定ブランチ生成から外せる | 元リポジトリの履歴を読める人には過去の内容が残る |

現在の設計文書には、講師のヒント、欠陥演習の意図、期待する結果が含まれる。
将来この同じリポジトリを参加者へ閲覧可能にするなら、設計書だけでなく過去のコミットも読めることを前提にする。
ヒント・解説を共通教材へ含めるD-033を前提とし、それらを講師限定にするための分離は必須にしない。「正式教材へ置き換えて古い文書を消せば、履歴からも情報が消える」とは考えない。
今回、履歴の書き換えや既存文書の削除は行わない。

## 4. 内容の分類案

| 内容 | 将来の参加者版 | 扱い |
| --- | --- | --- |
| 受け入れ条件、演習の依頼、確認・再開の説明 | 共通教材へ含める | MOAW本文を作成し、実起動手順は参加者版の準備後に確定する |
| 未実装の開始アプリ、架空データ、参加者向けテスト | 含める候補 | 指定状態から自分で実装できることを確認する |
| 共通指示、記入用ひな型 | 含める候補 | 解答への参照や不要な常時指示を除く |
| 設計ドラフトと変更理由 | 要判断 | 参加者に見せる範囲と、元リポジトリの履歴を含めて決める |
| 完成例の実装・パッチ | 開始アプリへの適用と、説明・復旧用の提供を分ける | 完成例のパッチ適用検査を参加者実装の合格条件にしない。実ファイルの範囲は後続で決める |
| 欠陥教材の解説・修正例・段階的ヒント | 共通教材へ含める | 既定を閉じ、本人が必要時に開く。課題用コピーのコードとは区別する |
| 実測ログ | 内容確認後に必要な範囲だけ | コード・プロンプト・パス・秘密情報を確認する |
| 既存教材の参照元情報 | 含める候補 | 由来・版・利用条件を記録し、参照元の権限を前提にしない |

講師と受講者の共用、自習での再開・反復を優先する。
解説を先に開いた場合も学習を続けられるようにし、本試行へ混入した情報やヒントは比較条件・介入として記録する。

### 今回のヒントと復旧教材の提示案

開発経験5年以上の個人参加、十分なヒントを既定で非表示にする条件はD-028・D-029で確認済み。
ヒントは「考える観点」「調べる場所・手段」「具体的な依頼・部分例」を、同じMOAW教材から必要時に開く。解説・解答例も同じ教材内でヒントと区別する。
課題、AC、対象外、権限、開始・終了条件はヒントへ隠さず、必要な段階で全員へ明示する。復旧用の完成コードを適用することは、解説を読むこととは別に管理する。

作業コピー内のMarkdownを折りたたんでも、Copilotはその本文を読める可能性がある。
既定の非表示は閲覧上の支援であり、アクセス制御ではない。共通教材を作業コピーに含める場合も、比較の入力・参照・人のヒントと実装コードの状態を区別する。
比較中のヒント閲覧・引用・追加指示は介入として記録する。ヒント利用だけを減点せず、支援後の説明と自力操作の範囲を確かめる。
今回は公式MOAWビューアによるローカル表示まで作る。実際の共有先、権限、保存の方針はQ-003・Q-010で確認し、公開サイトへの配備や参加者への配布を完了したとはしない。

## 5. 配布方式の選択肢

| 方式 | 満たす必要がある条件 | 留意点 |
| --- | --- | --- |
| 参加者が本リポジトリから生成する | 元リポジトリへのアクセスと、生成先の権限がある | 設計書・別ブランチ・履歴の閲覧を許容する必要がある |
| 管理者が本リポジトリから生成してコピーを渡す | 管理者が生成し、参加者へ生成先だけの権限を与える | 元リポジトリを見せずに配布できるが、配布操作と更新管理が増える |
| 参加者用に別のクリーンなテンプレートを用意する | 検討資料と配布元を明確に分ける必要がある | 同じリポジトリを使うという現在の意図を変更するため、別途判断が必要 |

本リポジトリを将来のテンプレートにする方針を第一候補として維持する。
今回の配布案は、参加者向けの現行内容を整理した本リポジトリから管理者が個人別コピーを生成し、参加者には生成先だけを提供する方式を第一候補とする。
元リポジトリの設計履歴を消す案ではない。生成物に共通教材の必要なヒント・解説を含め、秘密情報や不要な外部参照依存がないこと、完成コードを開始状態に混ぜていないことを確認する。
生成先の所有者・公開範囲、管理者の権限・作業量、参加者が利用するアカウントとアクセスをQ-010で決める。現時点でその配布方式や権限が承認・設定済みとはしない。
いずれの配布方式も今回の作業では実行せず、参加者の招待・権限変更・GitHub上の配布用リポジトリ作成は行わない。試走用の独立したローカルリポジトリとは区別する。

## 6. 既存アプリを移す際の確認

参照元はコミット `1a411cd13c02f28bb6f3ac30844af204f1f61d48`のPython製教材。
移植時は、アプリだけでなくREADME、AGENTS.md、テスト、パッケージ内容、起動方法の参照関係も確認する。

特に`tests\test_reference_patch.py`は、`workshop\filtering.patch`を読み、適用・逆適用とテストを実行する。
完成例パッチだけを外してこのテストを残すと依存が切れる。
逆に、その適用検査を参加者の変更後も必須にすると、独自の正しい実装が失敗し得る。解説を共用することと、完成例への依存を参加者用テストへ残すことは別である。
参加者の正しさは、完成例と同じ差分かどうかではなく、共通のACで確認する。

| 対象 | 後続で確認すること |
| --- | --- |
| 開始アプリ | 絞り込みが未実装で、既存操作が動く |
| データ | 架空データ、初期化、リセット対象、変更後の扱いが明示される |
| 参加者向けテスト | 完成例の所在や適用性へ依存せず、ACと回帰を確認できる |
| パッケージ検証 | 配布から外したファイルを必須にしていない |
| 指示とリンク | 講師専用の解答や非公開の外部文書を必須参照にしない |
| 環境 | ホストまたは承認済みDev Containerで、配布版単独の手順が成立する |
| 復旧 | コード、データ、会話を区別し、参加者の成果を破棄しない |
| 派生元 | 版、変更点、再利用条件、更新を取り込む責任が分かる |

各セクションをつなぐ開始確認・作業場所・受け渡しは、[共通シナリオ](common-scenario.md)第9節の実施手順案を使う。
教材化では、論理的な作業対象を実際のコピー・DB・サーバー・会話へ対応づけ、切り替え後も対象版と適用条件を追えることを確かめる。
準備・診断・本試行・分析の識別を維持し、参加者が未準備のコピー名や存在しないコマンドを推測して進める構成にしない。
復旧は共通シナリオ第11節の開始版・指示定義準備済み版・実装候補・品質確認後の版を案とし、本人の変更を保持して別コピーで再開する。S状態と同名のタグを配布済みとは扱わない。
実施時点の最新Stable版、D-031の候補から指定する一つの主モデル、非Previewの機能・観測で事前確認する。定義の直接編集を基本にし、Previewの管理UIやAgent Debug Logsを配布手順・復旧手順に含めない。

SEC-03では、同じ開始版からA: 既存指示、B: AGENTS.md改善のみ、C: 同じ改善版と条件付き指示、という比較用コピーを準備する。
参加者向けの指示や完成例依存の整理は全条件に共通の前処理とし、Aだけから安全条件や必要な情報を外さない。
コード・DB・会話・指示の条件差を分け、親ディレクトリ等の指示や他条件の成果が混入していないかも確認する。
別チャットにするだけでは作業コピーは分離されない。診断用に変更したコピーを本試行へ使い回さず、本編には指示と比較記録だけを戻す。
指示の適用パターンは、比較用と本編それぞれの配置で確認する。具体的なコピー構成と確認手順はQ-005・Q-013で決める。

SEC-04では、講師準備の共通小差分・品質確認・結果資料を、R0/R1とV0/V1の独立コピーへ揃えて配布する設計にする。
レビュー用の役割定義の有無と、検証Skillの有無を別々に比較し、最後に同じ版の検証結果をレビュー担当へ渡す。
参加者がSEC-03で生成したコードや、本編の実装途中のコードを比較の開始点にしない。

| SEC-04の準備対象 | 配布前に確認すること |
| --- | --- |
| Agentの配置と構成 | 候補の`.github\agents\portal-reviewer.agent.md`が利用基盤で発見・選択され、実在する読取・検索ツールだけを持つ |
| Skillの配置と参照 | 候補の`.github\skills\verify-portal\SKILL.md`で名前と親ディレクトリが一致し、本文・正本・必要な資料を参照できる |
| 補助資料・スクリプト | 必要な場合だけ含め、実在する参照、依存、入力、出力、終了状態、副作用、権限を確認する |
| R0/R1の条件 | 同じ課題票・差分・結果資料・指示・モデルを使う。実効ツールの差が残る場合は明示する |
| V0/V1の条件 | 同じ既定の担当と実効ツールを使う。V0で対象Skillが親・ユーザー・プラグイン等から読まれないことを確認する |
| 診断と本試行 | 診断用コピー・会話を分け、明示呼び出しと自動選択、発見と実行を別に記録する |
| 変更と復旧 | 検証中にコード・テストを修正せず、一時DB等の副作用を把握する。参加者の成果を保持して再開する |
| 引き継ぎと本編 | 定義と記録だけを戻し、本編でも配置・参照・適用・必要な利用を確認する。比較結果を本編の実行成功にしない |

上のパスは配布版の配置候補であり、配布用の実行ファイルは未同梱である。補助試走で作った定義のCLI上の発見・利用は、VS Codeでの利用確認とは区別する。
未設定の構造例を完成版として配らず、講師だけが読める資料や参照元の権限に依存しない構成にする。
検証Skillは検証・切り分け・報告までとし、修正は実装担当、追加実行は実行担当または人へ戻す。
演習でのAgent・Skillの配置・試用と、実務で常用するかの採否を分ける。講師提供版で後続へ進む場合も、本人の定義・適用の不足を残す。
安全条件を無断で無効化して比較環境を揃えない。具体的な構成・ツール・診断はQ-006、比較・引き継ぎ・停止・復旧の試走はQ-014で管理する。

SEC-05は、本編の計画・指示・検証手順を使い、代表ACのテスト先行と、変更単位ごとの実装・検証・修正を行う設計にする。
自然な不具合が出なかった場合には、講師が事前に再現確認した失敗記録を読解する。成功した参加者のコードへ故障を入れず、SEC-06のAND/OR欠陥やSEC-08の比較題材を先取りしない。

| SEC-05の準備対象 | 配布前に確認すること |
| --- | --- |
| 開始確認と機能追加後の確認 | 開始版の表示・UI不在・検索拒否を確かめるテストと、追加後のAC・回帰を確かめるテストを区別する |
| 完成例依存の分離 | パッチ、参照テスト、パッケージ検証の依存を揃えて整理し、参加者の正しさを完成例の適用可否で判定しない |
| 代表ACのテスト先行 | 指定開始版で対象テストが実行され、未実装を理由に失敗し、実装後に同じ契約で成功する |
| データと期待値 | 小さな既知データから期待集合を説明できる。説明用F1等を実DBのIDと混同せず、製品コードと同じ処理だけで期待値を作らない |
| 変更単位と検証手順 | 各単位の確認範囲と途中の未実装が分かり、Skillの報告から実装担当の修正・再実行へ進める |
| 講師の失敗記録 | 実際の版・データ・コマンド・失敗出力、原因確認、修正、同じ確認と回帰の結果が揃う。推測のログで補わない |
| 記録の配布と提示 | 機微情報と解答の公開範囲を確認し、観測情報の後に調査・修正の根拠を提示できる。原記録の参照先と閲覧条件も確認する |
| 実行環境と画面 | 一時DBと手動用DB、起動中のコピー・サーバー・ポート、再起動の手順を識別できる |
| 支援・復旧・S3 | 自分の作業を保持して再開し、未実施・未確認、講師記録の読解、支援利用を根拠付きで引き継げる |

代表AC以外の確認を省く方針ではなく、全ACをテスト先行にすることだけを必須にしない。
参加者の記録読解を、自力の再現・修正・再実行や本編の合格と扱わない。実装候補の状態と学習の達成を分けて記録する。
参加者版の検証契約・配布はQ-005、代表AC・変更単位・講師記録・提示・支援はQ-015、進行全体はQ-011で試走する。
これらのテストや記録はまだ作成していない。配布の不備による失敗を当日の意図的なデバッグ教材にしない。

SEC-06では、共通品質演習でレビュー・追加検証と人の関与を学び、その後に本編S3へ適用する。
HOTLは監督方針と介入・継続・再開の判断を必須にし、自動進行の監督・停止・再開の実操作は発展扱いにする。必須演習の成立を、新しい自動進行基盤や権限拡大へ依存させない。

| SEC-06の準備対象 | 配布前に確認すること |
| --- | --- |
| 正常・欠陥・修正版 | 絞り込み実装済みの正常版から複合条件の結合だけを変え、同じ確認で検出と回復を示す。検索未実装の400と混同しない |
