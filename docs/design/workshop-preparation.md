### 3.1 原本を変更しない事前試走

参照元の固定コミットから、試走専用の独立したローカルGitリポジトリを作り、参照元を指すremoteを外す。元のリポジトリへcommit・pushせず、試走用のDB、比較コピー、会話、設定、依存環境も分ける。比較用のコピーは同じ開始版から作り、前の条件で生成したコードを次へ渡さない。

原本のブランチ・参照版を開始前後で読み取り確認する。ただし、参照元で他の人が進めた変更があれば、自分が書いたものと混同して戻さない。試走後は、改善した教材と必要な集約記録を残し、試走用リポジトリ、DB、依存環境、ダウンロード、ブラウザープロファイル、起動プロセスを所有範囲に限って片付ける。

### 3.2 依存・一時ディレクトリの事前確認

アプリのルートで`uv sync --locked`を実行し、ロックを変更せずに依存を準備する。TLSやダウンロードが失敗した場合は、起動前の環境不備として記録する。証明書検証を無効にしたり、未検証の別パッケージへ置き換えたりしない。社内で承認されたミラーや別の取得経路を使う場合も、ロック上の版とハッシュを照合する。

Windowsでは、長い作業パスにpytestの一時コピーが重なると、パス長による起動・ファイル作成の失敗になる場合がある。新しいPowerShellで、試走専用の短い一時ディレクトリを指定して切り分ける。

```powershell
$trialTemp = Join-Path $env:LOCALAPPDATA ("Temp\copilot-ws-" + [guid]::NewGuid().ToString("N"))
New-Item -ItemType Directory -Path $trialTemp | Out-Null
$env:TEMP = $trialTemp
$env:TMP = $trialTemp
```

設定はその端末内だけで使う。終了時には対象プロセスを止め、`$trialTemp`が今回作成した場所であることを確認して片付け、端末を閉じる。共有のTempや既存のユーザー環境は削除しない。
初期テストが対象のアサーションに到達していなければ、検索機能の未実装を検出した「赤」として扱わない。

### 3.3 初回のデータ作成とリセット

実習アプリの作業コピーで、初回は`uv run --locked python -m request_portal seed`またはアプリの起動によってデモDBを作る。`seed`は既存の申請を保持するため、操作済みのDBを初期12件へ戻すコマンドではない。

リセットが必要な場合は、起動中のサーバーを止め、現在地と`instance\portal-demo.sqlite3`が自分の実習用DBであることを確認してから、`uv run --locked python -m request_portal reset-demo --confirm request-portal-demo`を実行する。まだDBがない状態ではリセットは失敗する。データを保持したい場合はリセットせず、別コピー・別DBで確認する。

### 第4章: AgentのR0/R1、SkillのV0/V1

第3章で参加者が生成したコードではなく、同じ共通小差分と同じ版の確認資料を用意する。R0/R1とV0/V1は別の比較であり、AgentとSkillの優劣を比べるものではない。

| 比較 | 固定するもの | 変えるもの |
| --- | --- | --- |
| R0/R1 | 小差分、結果資料、品質条件、モデル、指示 | 既定の担当か、読み取り中心のレビューAgentか |
| V0/V1 | 小差分、確認資産、担当、実効ツール、モデル、指示 | 対象の検証Skillを使うか |

Agent・Skillの配置、必須メタデータ、使えるツール識別子、選択・呼び出し経路、参照先を実施環境で確認する。レビュー担当へ編集・任意実行・最終承認を許可せず、Skillから禁止操作を迂回できる構成にしない。
検証Skillは実行・切り分け・報告までとし、修正は別の責務へ戻す。V0へ別経路のSkillが混入していないことも確認する。支援用の定義を渡した場合は提供部分と自力の設計・利用を分ける。
R0/R1に渡す差分と結果資料は、講師または準備担当者が用意する。両端のコミットID（省略しない形）と差分の作り方（`git diff ［開始版］ ［対象版］`）、レビュー用コピーの状態（`git status`に出るのは結果資料のフォルダーだけ）、同じ版での確認結果、確認から外したテストとその理由を添える（D-050の試走で、R1がこれらを求めた）。
共通小差分については、次の事実を事前に確かめておく。外から見える動作は開始版と同じであること（HTTPの応答で比べる）。講師用パッチの確認テスト（`tests\test_reference_patch.py`）は、対象版では2件のうち1件が失敗すること。共通小差分が講師用パッチの適用先（`request_portal/__init__.py`の検査処理）を変えているためで、差分の欠陥ではなく、この差分は本編へ戻さない。既存のテストは、未対応のキーを画面だけで、重複したキーをAPIだけで確かめていること。結果資料には除外の理由を書いておき、除外した確認についての指摘は、その理由と照らして判断する（D-050の試走で、R0がパッチを適用できなくなる可能性を講師への影響として挙げた）。

### 第5章: 本編の実装と失敗の確認

部署の絞り込みを代表ACにし、対象テストが実際に起動・収集され、未実装の仕様で失敗し、実装後に同じ契約で成功することを確認できるようにする。
実装は、最小の経路、条件・入力境界、画面操作の三単位で進める。APIと画面のデータ対応、既存操作、配色、並び順、パラメーター化を確認する。

```powershell

uv run --locked ruff check .
uv run --locked ruff format --check .

```

開始版の配布検品では、除外せず全件を実行する。`tools\verify_browser.py`も参照版では`starter`と`reference`向けであり、`participant`を勝手に`reference`と呼び替えない。参加者版の表示・機能と、実行対象の専用DBに合うブラウザー確認を別途用意する。

段階名の変更では、開始版・完成例・演習版を正しく区別する分岐を残す。演習版でテストが通っても、実行していない開始版の分岐まで正しいとは限らない。

### 第6章: AND/ORの品質演習と判断事例

絞り込み実装済みの正常版から、結合がANDではなくORになる欠陥版を独立して用意する。変更後のコードが狙った欠陥の形になり、単独条件が維持されていることを確かめる。変更バイトがあるだけでは十分ではない。
完成例に含まれる絞り込みのテスト（`tests/test_filtering.py`）は、この欠陥を直接検出する。欠陥版には含めず、既存のテストが欠陥版で成功し、受講者が追加するテストで初めて検出できることを確かめる。レビューに渡す差分は、開始版から欠陥版までの変更全体とする。
両方一致、部署だけ一致、状態だけ一致、どちらも不一致を含むデータで、期待集合、長さ、値、`count`、回帰を確認する。欠陥版での検出と修正後の回復は同じ確認で確かめる。
D-047の試走のように完成例から欠陥版を作ると、AC-10の注記を満たさない解除リンクもそのまま残る。レビューAgentがこれを指摘した場合は正しい指摘として扱い、6-4の修正範囲（AC-04）とは分ける。

四つの判断事例は本文に含めるが、実測ログとして扱わない。HITL／HOTLの方針・事例判断は必須、監督・停止・再開の実操作は非Previewで事前確認した環境を使う発展とする。
独立演習の成功と本編の品質判断を分け、本編へコード・DB・成功結果を戻さない。

### 第7章: 定義を作る入力とローカル確認

初期要件はDR-01〜DR-10とDR-13、追加要件はDR-11・DR-12とする。アプリの起動・依存・確認方法と、Terraform・Azure Pipelinesの最小骨組みを用意する。

### 11.4 準備担当への注意

- 組織のAgentと指示：1.145.2では、GitHubの組織が用意したCustom Agentと指示を読み込む設定（`github.copilot.chat.organizationCustomAgents.enabled`・`github.copilot.chat.organizationInstructions.enabled`）が既定で有効である。専用のユーザーデータで起動しても、エージェントの選択欄に組織のAgentが2件並んだ。試走では両方を`false`にし、ウィンドウを開き直して、一覧がAgent・Ask・Planだけになったことを確かめた。組織の指示が依頼に加わったかは確かめていないため、講師が環境ごとに設定を確かめる（W01）。
- モデルの設定と新しい会話：GPT-6.1 Terraには、推論の度合い（Effort Level：Low〜Max）とContext Size（272K・872K）の設定がある。1.145.2では、新しい会話でもエージェント・モデル・これらの設定が前の会話のまま残った（1.144.0では既定に戻った）。ツールの設定（Configure Tools）だけは既定に戻るため、会話ごとに確かめる（W02・W04）。
- 読取・検索への限定：Askのツールの設定では、memoryはvscodeの中にある。executeには、コマンドの出力やテストの失敗を読む道具（getTerminalOutput、testFailure）だけが選ばれた状態で残る。これらはコマンドを実行しない（W04）。
- 利用量の表示：入力欄の下にあるコンテキストの使用状況のボタンから、会話全体のクレジット（Session Cost）とコンテキストの使用量を見られる。872Kを選んでも、使用量の上限は1Mと表示された（回答用の予約分を含む）。依頼ごとのクレジットと所要時間は、回答にポインターを合わせると表示される（W03）。
- 続行の確認：読み取りだけの長いレビュー（7-5）で、32手順・9分10秒の時点で「Continue to iterate?」が表示され、最終の回答がないまま止まった。Continueを押すと続き、42秒で回答した。エージェントが一つの依頼の中で行う要求の上限は設定`chat.agent.maxRequests`で決まり、拡張機能の既定値は50である。画面に表示された手順の数（32）との対応は確かめていない。長い依頼で表示されたときに続けてよいかを、講師が案内する（O14）。
- 定義ファイルの書き込み：AgentやSkillの定義ファイルを書き込む前に「Allow edits to sensitive files?」の確認が出た（3-2に追記、E03）。
- 危険度の表示：作業コピーの中で`git show`を使って読み取るだけのコードを、許可の画面が「remote」と表示したことがあった。3-2の「表示の色ではなくコマンドそのものを読む」で扱える。
- 作業フォルダーの信頼：信頼したフォルダーの一覧と最近開いた項目は、VS Codeがユーザーデータの場所に関係なく共有する保存先（`~/.vscode-shared/sharedStorage/state.vscdb`）にある。このため、専用のユーザーデータで起動しても開始時から普段のVS Codeと同じフォルダーを含み、試走で信頼したフォルダーや開いたフォルダーも普段の一覧に加わる。`globalStorage\agent-host-config.json`は、VS Codeがこの一覧をエージェントホストへ渡す写しである（E02。2026-11-07に訂正）。共用の端末では、後片付けで確かめる場所にこの保存先を加え、VS Codeを閉じてから削除する。
- 起動元の環境：試走の起動方法の影響で、ステータスバーのCopilotの表示に「Monitoring: Enabled」（ループバックへの書き出しで、プロンプトや回答の内容は含まない）が出た。教材の手順とは関係しない（E01）。
