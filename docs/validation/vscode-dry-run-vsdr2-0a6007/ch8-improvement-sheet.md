## 採用するかの判断と理由

- 実際に起きたこと：A・B とも、API の count を返す一覧の件数にする1か所の修正と、全体集計の確認で AC-08 を満たした。その後、開始版にある別の不具合（条件を解除すると配色 scoutTheme が失われる。AC-10）を見つけ、配色のテストを足し始めた。人が止め、配色のテストを取り消して別件として報告するよう追加説明を送った。B は関連ファイルを早めに読んだが、依頼1の読み取り・検索の回数は A より少なくなかった。A も自分で同じ3ファイルにたどり着いた。
- 原因の仮説：両条件の手戻りは、関連ファイルの有無ではなく、開始版の別の不具合をどう扱うかが依頼に書かれていなかったことから起きたと考える。
- まだ言えないこと：B の credits・承認・時間が少なかったことが、関連ファイルの明示によるものか。1組だけで、両方に同じ寄り道と人の停止が入り、順序と監視の条件も違うため。
- 判断：追加評価。正しいパスが確定しているときに出発点として示しても害は見られなかったが、探索や手戻りを減らした根拠はない。
- 採用する条件：範囲外の不具合の扱いを共通の依頼に書いたうえで、順序を入れ替えて（A→B と B→A を少なくとも1組ずつ）比べ、どの組でも同じ品質で B の credits と承認が少ない場合。使うのは、パスを確定できる課題に限る。
- 見直す条件：示したパスが誤っている・古い、B だけ品質が下がる、反復すると差が消える場合。
