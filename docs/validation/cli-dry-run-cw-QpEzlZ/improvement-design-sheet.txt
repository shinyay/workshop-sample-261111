8-4｜条件、品質、負担の順に採否を決める

【読解訂正】
準備時の校正記録（アプリテスト95合格・3失敗、固定オラクル32失敗）は、意図的に壊した
基線を検出できることの確認であり、A/Bの最終結果ではない。A/Bの最終記録は、両方とも
アプリテスト98件合格、固定オラクル132リクエスト・失敗0件である。Aのツール総数は
7+1+8+1=17件であり、16件ではない。

事前に揃えた条件は、同じ対象・要求、同じソースとseed DBのバイト列、同じモデル・指示・
権限・固定チェックである。意図した条件差は、Bにだけ関連ファイルの参照を明示したこと
（refs/conditions.json に記録された request_portal\__init__.py と
tests\test_workshop_filters.py）である。AとBの探索範囲が異なったことは実行中の観測結果で
あり、後から条件不一致にはしない。Aの全Pythonファイル検索、Bのアプリ・テスト限定検索は
そのまま保持し、両者に同じ参照を渡したりAの探索を制限したりして問いを変えない。

1. 条件と品質
   Aはcount-a、Bはcount-bとして各一回実行された。A/Bとも同じ修正済みソースで98件中98件
   合格、失敗・エラー・スキップ0件、4つの固定CLI確認がすべて成功した。固定の132件
   UI/APIオラクルも両方失敗0件で、品質到達を確認できる。準備時の32件失敗を最終結果へ
   繰り入れない根拠は refs/result-ledger.json、条件と変数の根拠は refs/conditions.json
   である。

2. 同じ取得範囲で読める負担
   観測できた同じ範囲の指標は、A/BそれぞれのネイティブCLI記録である。Aは入力135239、
   出力1913、経過55.570秒、ツール総数17、ツールまたはチェック失敗0件。Bは入力97264、
   出力1972、経過47.577秒、ツール総数15、ツールまたはチェック失敗0件である。入力には
   cache_read/cache_writeの内訳が含まれるため、それらを入力合計へ再加算しない。出力と
   reasoningを合算しない。実行中の介入は両方0件で、参照準備・調整・コーディネータ確認は
   試行負担から除外される。

   品質が揃い、この一対ではBの入力トークン・全体時間・ツール回数が小さい。ただし出力
   トークンはBの方が多く、pytest部分もAの5.70秒に対してBは10.44秒と長かった。Aが先、Bが後で
   共有ランタイム・キャッシュの順序効果が残り、参照準備・保守負担、金銭的費用、正確な
   思考時間は測定していない。参照指定が原因であるとはまだ断定できない。

3. 観測、原因仮説、未確認
   観測した事実は、同じ品質結果になったこと、Bの明示参照と異なる探索範囲、上記の利用量・
   時間・ツール数、A先行の順序である。原因の仮説は、Bの参照指定が関連箇所への到達を
   早めた可能性である。単発の順序付き一対なので、キャッシュ、順序、準備・維持負担を
   分離できず、モデル・Agent・Skill全体の優劣、一般的な削減率、金銭的効果、第三者評価、
   ブラウザーでのキーボード操作の品質は判断できない。

4. 採否
   判断者役による模擬判断は「追加評価」とする。両条件とも品質は達成したので即時の
   見送りではないが、一対だけで一般化や全面採用をする根拠もない。次の一対では参照指定
   を唯一の条件差として事前登録し、B→Aの順序で独立に実施する。ただし、両者の探索
   範囲を強制的に同じにせず、AへBの参照行も渡さない。これは今回観測した変数を保持する
   ためである。

   仮定への対応：
   - A/Bとも品質達成だが差が読み取れない場合：品質を満たした事実を採用根拠にするが、
     負担差がないと断定せず、限定採用または追加評価に留める。追加評価の条件を
     事前に固定する。
   - Bだけ未完了の場合：品質比較が成立しないため採用判断をしない。Bを未完了として
     記録し、その試行を安い成功とは扱わない。原因と残る品質不足から、見送りまたは
     追加評価を判断し、成功するまで同じ条件を繰り返して結果を置き換えない。
   - 品質達成だが利用量が未取得の場合：品質の到達は記録できるが、利用量の優位性は
     判断しない。取得できた時間・介入など別の負担だけを限定的に使い、利用量の追加
     計測ができるまでは利用量の比較だけを保留する。料金などの未取得は一律の停止条件にしない。

【比較の根拠】
共通課題・版・AC：
  共通課題はAC-08の件数不整合修正。対象は同じ要求と同じソース・seed DBのバイト列で、
  A=count-a、B=count-bを各1回実行した一対である。A/Bの開始ローカルGit IDはそれぞれ
  e53cc1a7ac2837930d2b4f797b7cd520461b92c5 と
  58d0b7fab81c7cf2eda87c9581fe82d7c30d09b1で、証拠上の識別子であり、取得可能な原本や
  リモート参照ではない。品質記録、条件、実験変数は refs/conditions.json、
  refs/result-ledger.json、refs/quality.json による。

揃えた条件／変えた参照指定：
  揃えたのは対象・要求、ソースとseed DB、モデル、指示、権限、固定チェック、実行回数。
  変えたのはBにだけ関連ファイルを明示した参照指定である。探索範囲の差は観測された結果
  であり、追加の設定差ではない。UI/APIの固定オラクルは同じ132リクエストの契約である。

A/Bの原記録と品質結果：
  Aは98/98合格、固定132件の失敗0、4つの固定CLI確認すべて成功。Bも98/98合格、
  固定132件の失敗0、4つの固定CLI確認すべて成功。Aのアプリ修正は
  request_portal\__init__.py、Bも同じ修正済みソースへ到達した。準備だけの校正記録
  （95合格・3失敗、オラクル32失敗）は最終結果から除外する。

取得できた指標と範囲／欠測・条件差：
  Aは入力135239、出力1913、55.570秒、ツール17件。Bは入力97264、出力1972、
  47.577秒、ツール15件。失敗と実行中介入は両方0件。入力合計はcache_read/writeを
  内包する。欠測は金銭費用、原因を特定した正確な時刻、参照準備・保守負担、第三者評価、
  ブラウザーの実キーボード操作である。A先行による順序・共有キャッシュ効果も除けない。

【採否と理由】
観測したこと：
  A/Bは同じ品質基準を満たし、Bの入力・全体時間・ツール回数はこの一対では小さかった。
  出力トークンとpytest部分の時間はBが大きかった。Bだけ参照指定を
  受け、AとBの探索範囲は異なった。条件差、品質、取得可能な負担、準備のみの失敗を
  混同していない。

原因の仮説／まだ言えないこと：
  参照指定が関連箇所の特定を助けた可能性はあるが、順序・キャッシュ・単発性から因果と
  は言えない。モデル、Agent、Skill全体の優劣、実測の一般削減率、費用対効果、未測定の
  負担、実承認は言えない。

限定採用・追加評価・見送りと理由：
  判断者役による模擬判断は追加評価。品質が揃ったため限定的に次の評価へ進める一方、
  単発・A先行・準備負担欠測のため全面採用やBの勝利は結論にしない。今回の比較自体の
  実行や再測定、実承認は行わない。

採用する条件／見直す条件：
  新しい独立な共通基点、同じデータ、同じ検証入口、固定した参照指定差、記録可能な
  使用量・時間・介入が揃い、両条件の品質が成功する場合に限り、限定評価を継続する。
  未完了なら未完了として残す。欠測はその指標の判断を保留し、条件逸脱、確認手順自体の
  不備、準備資産不足、安全上の問題があれば停止する。既知の欠陥の赤は後述の修正範囲で
  扱う。複数の順序・反復で品質と負担の差が再現し、準備・保守負担も取得できた
  ときだけ、別途採否を再判断する。

【次に使う手順】
開始に必要な版・入力・準備：
  準備役が、過去のローカルGit IDや作業コピーを取得するのではなく、新しい共通基点で
  完成済み品質確認済みアプリを再構成する。別の件数のみ壊れた検出用fixture、同じseed
  データ、開始状態のファイル・データ一覧とハッシュ、独立してバイト一致するA/B入力、
  関連参照、4つの固定CLI入口と共通オラクルを準備する。新しい版に必要なACと回帰範囲を
  固定し、両条件で入口を実演する。過去の98テスト・132要求は実績値であり、将来の件数を
  そこへ合わせて検査を省いたり弱めたりしない。校正は「正しい版で成功」「件数欠陥だけの
  版で意図した失敗」を確認する。入口の同等性はrefs/quality.jsonの契約で判断する。
  比較用の一時資源は試行後に清掃し、旧パスや旧IDを再開条件にしない。

依頼と、明示する参照：
  依頼には対象版、AC-08、目的、対象外、実験変数を記載する。A/Bに同じ要求・権限・
  検証条件を渡す。過去の2パスは例であり、準備役が新しい開始版で存在と責務を確認して
  参照を確定し、Bの依頼だけへ一行で追加する。行番号、修正方法、完成差分、Aの結果は
  追加しない。Aの探索を制限せず、両者の探索範囲を同一化せず、
  実際の検索結果を記録する。試行後は refs/quality.json と refs/decision.json 相当の
  原記録を保存する。

既存の指示・Agent・Skillを使う理由／追加しない理由：
  既存の指示は条件、入力、検証入口、停止・記録の共通契約を十分に表現している。既存の
  Agent/Skillを使えば同じ役割・入出力・道具を再利用でき、今回の差は参照指定として
  明示できる。新しいAgentやSkillを追加する必要はない。追加すると役割差が新たな実験
  変数になり、今回の問いと保守対象を広げるためである。

実行する確認と終了条件：
  準備役が新しい基線・データ・パス・固定入口を検証し、欠落がないことを記録する。各
  条件を事前登録した順序で一回ずつ実行し、A/Bの原記録、使用量集計、時間、検索・読取・
  編集・確認の呼出しと失敗、介入、品質結果を保存する。指定された入口は
  rehearsal-pytest.cmd、rehearsal-lint.cmd、rehearsal-format.cmd、
  rehearsal-types.cmdだけを、各々入口名一つで別々に起動する。終了条件は、同じ最終ソース
  で全入口が実行済み、予定したACと回帰のテストが正の件数で収集され、失敗・エラー・
  スキップ0、共通オラクル成功、共通の指示・依存・テストが不変であることだ。
  「同じ最終ソース」は、各条件の確認結果をその条件の最終ソースに対応させる意味で、
  A/Bの最終コードや差分のバイト一致は要求しない。許容パスと不変ファイルのハッシュは
  新しい試行前に一覧化し、変更後に照合する。過去の範囲はrefs/quality.jsonに記載する。
  今回は手順設計と読解確認だけで、追加の実行・再測定はしない。

人が判断・監督すること：
  判断者役が、条件対応、Bだけの参照指定、品質、欠測、順序、介入、範囲逸脱を原記録と
  照合し、限定採用・追加評価・見送りを模擬判断する。人の判断点は、開始前の資産充足、
  実行中の安全・範囲逸脱、完了後の品質と負担の解釈である。これは判断者役による模擬判断
  であり、人が承認したことを示さない。実承認、第三者評価、クラウド接続は行わない。

停止条件／保持する記録／戻し先／再開条件：
  既知の件数欠陥を示すテスト失敗は、実装担当が許容パス内で修正・再確認を続ける。
  その途中の赤と手戻りを記録し、失敗した事実を消さない。チェック自体の不備や
  未知のスキップ・収集不足は、単なるアプリの赤とは分ける。
  開始版・データ・必須資産の欠落や不一致、チェック自体の不備、解法の混入は停止して
  準備役へ戻す。仕様・許可範囲・安全に関する問題は判断者役へ戻し、承認を推測しない。
  保持するのは対象版と現在のハッシュ、未コミット差分、入力、参照、実行済みチェックと
  原出力、停止理由、作業コピー・一時DBの識別子、清掃状態である。
  品質・版・条件の必須証拠がなければ完了扱いにしない。利用量が欠測なら利用量の比較を
  保留し、取得できた品質・時間・介入は別に扱う。未取得の料金、思考時間、第三者評価を
  すべて解消することは再開条件にしない。
  修正を続けるだけなら、同じ試行の差分と記録を保持して許可範囲で再開する。
  共通条件や確認資産を訂正する場合は、準備役が新しい共通基点・データ・参照・確認契約を
  A/B双方で校正し、新しい一組として開始する。旧結果は旧条件のまま保持する。
  清掃後は実行資産の再準備が必要であり、旧ローカルcommitだけでは再開できない。

次の試行で一つだけ変えること：
  新しい一組の条件間では、参照指定の有無だけを変数として保持する。前回に対する
  計画上の変更は、順序をB→Aと事前に決めることである。
  探索範囲を制限・統一せず、参照をAへ追加せず、モデル、Agent、Skill、データ、基線、
  指示、権限、固定チェック、測定定義は、その新しい一組の条件間で揃える。
  前回の削除済み基点を再取得する意味ではない。これは実行結果ではなく、次の試行の
  手順設計である。
