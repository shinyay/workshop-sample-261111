【採用するかの判断と理由】
実際に起きたこと：A は修正前に失敗を再現してから直した。B は再現せずにコードを読んで直した。どちらも示されていないファイル（README、list.html など）も読んだ。B の credits は約13%少なく、許可は2回少なかった。
原因の仮説／まだ言えないこと：差の大部分は A が失敗を再現した手順の違い（許可2回分）で説明できる可能性がある。関連ファイルの明示が探索を減らしたとは、この1組では言えない。順序の影響も分けられていない。
限定採用・追加評価・見送りと理由：追加評価。品質は同じで、負担の差は小さく、原因を一つに絞れないため。
採用する条件／見直す条件：順序を入れ替えた組でも、失敗の再現の有無をそろえたうえで B の負担が小さければ、関連ファイルを分かっている場合だけ書き添える運用を限定採用する。差がなければ見送る。

【次に使う手順】
開始に必要な版・入力・準備：比較教材の同じ開始版を2つ用意し、追跡ファイルの一致を確かめる。共通の品質確認を開始版で一度実行し、想定どおりの失敗（件数の確認だけが失敗）を記録する。
依頼と、明示する参照：対象版・AC-08・対象外（無関係な機能や依存の追加、確認の削除・弱体化）・共通の品質確認を書く。「修正の前に、失敗を一度再現してから直す」を両方の依頼に加える。B だけ関連ファイルの1行を同じ行の末尾に続ける（改行すると送信が分かれる）。
既存の指示・Agent・Skillを使う理由／追加しない理由：AGENTS.md の確認コマンドと tests.instructions.md で足りたため、新しい Agent・Skill は追加しない。
実行する確認と終了条件：共通の品質確認がすべて成功し、確認担当が各条件の最終コードで独立に再実行して同じ結果になったら終了。
人が判断・監督すること：コマンドごとの許可（内容を読んでから許可）、差分を読んでから Keep、比較条件が崩れたときの中止。
停止条件／保持する記録／戻し先／再開条件：対象版の違い、品質確認の不備、解法の混入、依頼文の欠落（送信が分かれた場合を含む）で止める。止めたら会話ログとコピーの状態（git status）を残し、準備担当へ戻す。コピーが開始時と同じであることを確かめてから、新しい会話で再開する。
次の試行で一つだけ変えること（試行しない場合はその理由）：実行順を B→A に入れ替える。
