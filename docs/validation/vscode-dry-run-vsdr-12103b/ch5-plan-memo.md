# 調査・実装計画メモ（本編）

第2章の調査・計画と、第5章の着手前に人が決めたことをまとめたメモです。受け入れ条件は `ac-memo.md` を参照します。

## 現状

- 一覧の画面 `GET /requests` と API `GET /api/requests` は、どちらも `read_requests()` から `_validate_query_keys()` と `storage.list_requests()` を使う（`request_portal/__init__.py`、`request_portal/storage.py`）。
- 画面だけ `status_counts()` で全体の集計を表示する（別のSQL）。
- 開始版は検索キーを受け付けず、有効な検索キーも400になる。`scoutTheme` は未指定・空・`light`・`dark` だけを許可し、重複は400。
- 画面とAPIの結果が同じ申請IDと件数になるかは、まだ実行して確かめていない。

## 本編の要求

- 対象：AC-01〜AC-11（部署・状態による絞り込み）。
- 対象外：詳細から一覧へ戻ったときの条件の保持、並行更新時の同時点の一致、ページ分割、新しい依存の追加。

## 人が決めたこと

1. 一覧の上に、部署・状態の選択（「すべて」は空文字）、「絞り込む」ボタン、「条件を解除」リンクを置く。0件のときは「条件に一致する申請はありません」と解除リンクを表示する。
2. 不正な入力は400とし、どのキーや値を受け付けないかを短く説明する。不正が複数あるときは一つ目の説明でよい。
3. 画面とAPIの一致は、同じDBの状態で申請IDの集まりと件数を照合して確かめる。
4. `scoutTheme` はAC-10の注記どおり、フォーム送信と条件の解除の後も保つ。
5. 段階名：内部名 `exercise`、画面の表示名「演習版」。変更単位1で切り替える。開始版（`starter`）と講師用の完成例（`reference`）の分岐は残す。画面上部の説明は、その時点で実装済みの範囲に合わせ、完成時に「部署・状態を組み合わせて絞り込めます。」とする。
6. 既存テストの段階ごとの期待：演習版の分岐では段階名と表示名だけを確かめる。「フォームがない」「複合条件は400」のような途中段階の期待は固定しない。
7. `README.md` の段階の説明は、変更単位3で演習版の見分け方を短く追記する。
8. 回帰確認は `uv run --locked pytest --ignore=tests/test_reference_patch.py -q` とし、除外した理由（講師用の完成例パッチを開始版のコピーへ当てる検品のため）を記録する。
