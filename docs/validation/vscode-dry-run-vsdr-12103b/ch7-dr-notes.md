## DR 別の対応方針

各行の「判断者」は候補役割であり、担当者は未割当て。確認方法は提案であって、実施結果ではない。

| DR | アプリ・現在の資料から分かること | 対応方針・確認方法 | 未決事項・判断者／実環境での確認 |
| --- | --- | --- | --- |
| DR-01 同じ版を追跡する | HEAD と未コミット差分の両方が対象。過去の自動確認にはハッシュがあるが、今との一致は未確認。 | 対象を合意したコミットに確定し、コミット ID、依存ロック、確認結果、成果物の識別子・ハッシュを関連付ける。差分を含める必要があるなら未追跡も含む再現可能な記録方法を合意し、確認前後の一致を検証する。 | 対象コミットと未コミット変更の扱い: アプリ責任者・リリース責任者。実環境では投入済み成果物と承認した成果物の識別子を照合。 |
| DR-02 合意した仮想構成に限定する | 現状はローカル専用。App Service Linux の単一アプリは仮案。`infra/versions.tf` はバージョン制約のみで構成を定義していない。 | アプリ1つ以外の構成要素や接続先を勝手に追加せず、構成図・境界・前提を人が承認する。Terraform 定義案と承認済み構成を照合する。 | リソース範囲、ネットワーク・アクセス制御、利用環境、採否: アーキテクト・セキュリティ責任者・アプリ責任者。実環境の制約と合意内容の一致を確認。必要な要素が範囲外なら設計に戻る。 |
| DR-03 実行・依存・確認の条件を揃える | Python 範囲、Flask、ロックファイル、ローカルの起動・確認方法は上記のとおり。 | Python・OS・依存導入・起動・テスト条件を明記し、CI と配備候補の差分を検証する。ロック済み依存と実際のランタイムを照合し、必要な環境でアプリとヘルス確認を行う。 | Python バージョン、サーバー、起動ポート、Host 設定、秘密鍵の供給方式: アプリ責任者・運用担当。App Service の対応と起動・フォーム・セッションの動作を実環境で確認。ローカル専用の制約を変更する場合は別途承認。 |
| DR-04 データと秘密情報を持ち出さない | デモ SQLite は実行中に変更される。既定の秘密鍵は起動時生成。認証はない。 | ソースとビルド入力を明示的に選び、`instance/`、DB、秘密情報、環境ファイル等を成果物・ログ・テスト報告へ含めない。生成物の内容を検査し、秘密値を表示しない。架空データに限定する。 | データ分類、除外規則、秘密情報の管理方法: セキュリティ責任者・データ管理者。実環境で保管・ログ・アクセス権を確認し、実データ持込みを許可しない。 |
| DR-05 Terraform の入出力を説明する | `infra/versions.tf` に Terraform `1.16.6`、`hashicorp/azurerm` `5.10.0` の制約がある。変数・出力・リソースはこのファイルにない。バージョンの利用可能性は未検証。 | 定義案では各入力の目的、型、必須性、制約、値の決定者と、各出力の目的・利用者・機密性を説明する。実値や秘密を文書に埋めず、承認構成と照合する。state の管理・アクセス制御も設計する。 | 入出力、バージョン、state の保管先と権限: インフラ責任者・セキュリティ責任者。実環境の利用可能性・権限・state 保護は未確認。実行は本作業の対象外。 |
| DR-06 必要な品質確認を省かない | 必須4コマンド、演習版の全体回帰、過去の結果と除外理由は上記のとおり。 | 対象版に対応したテスト・Ruff・フォーマット・mypy を CI の必須条件として案に記載し、演習版では全体回帰の除外と理由を明記。必要な画面・起動確認も別途記録する。結果と対象版を紐付ける。 | CI の必須ゲート、ブラウザー確認の要否と責任者: 品質責任者・アプリ責任者。実環境の起動・画面・DB と、必要なら Python 3.13 も対象版で確認。 |

| DR-08 確認した入力から成果物を作る | この作業ツリーは変更・未追跡を含み、HEAD 単体で確認済み入力を表さない。 | CI で確定したソースとロック済み依存から成果物を一度作成し、成果物の内容・ハッシュを記録する。その成果物自体または同一の入力・環境で必要な確認を行い、確認後に作り直さず同じ成果物を引き渡す。 | ビルド方式、成果物の形式、依存取得元、検査・保管・保持期間: ビルド責任者・リリース責任者。実環境への投入物と承認済みハッシュを照合する。 |
| DR-09 CD は実行せず定義案だけを作る | 現在のアプリ資料はローカル実行が前提で、配備成功の証拠はない。 | CD は対象成果物、品質ゲート、手動承認、配備・検証・失敗時の扱いを文章または定義案で設計するだけとする。接続・配備・パイプライン実行はしない。 | 承認者、実行権限、配備方法、ロールバック、いつ実行を許可するか: リリース責任者・運用責任者。将来の実行前に実環境での検証と明示的な承認が必要。 |
| DR-10 未設定・未検証と判断者を残す | App Service の適合性、実値、承認者、実環境結果はいずれも未確定。 | この表と将来の設計・確認記録に状態、根拠、判断者、判断時期を残す。空欄を架空の実値や成功結果で埋めない。 | 全項目の担当者と期限: プロジェクト責任者が割当て。運用責任者が実環境で結果と証拠を記録し、判断者が採否を決定。 |
| DR-11 環境ごとに資源と設定・state を区別する | 現行アプリに環境の自動切替機構はなく、state の管理先も未合意。 | 環境識別子と環境別の入力・資源名・state キー・権限を対応付ける。設定と state を混同しないよう、実行前に対象を照合する。 | 環境一覧、命名、入力値、state 保管先・鍵・権限: インフラ・運用・セキュリティ責任者。実環境の分離とアクセス制御は未確認。 |

| DR-13 CI を始めるきっかけと対象を示す | 現状の確認コマンドと対象テストは分かるが、CI のトリガー・対象ブランチは未合意。 | 案: 対象ブランチへのプルリクエスト作成・更新と、そのブランチへの push で開始し、イベントに対応するコミットを checkout してロック済み依存で必須確認を行う。対象版・イベント・結果を記録し、同じ版から成果物を作る。 | 対象ブランチ、PR と push の範囲、手動実行、必須チェック・権限: 開発責任者・品質責任者。将来の CI 環境でイベント、checkout したコミット、対象ファイル、ゲートを検証する。 |

## 採用判断までの保留事項

1. アプリ責任者とリリース責任者が対象版を確定し、同じ版の品質結果と成果物を追跡できる状態にする。
2. アーキテクト・運用・セキュリティ責任者が単一 App Service 案の範囲、公開条件、認証のないアプリへのアクセス制限を合意する。現行の `serve` と Host 制限を無断で変更しない。
3. アプリ・運用担当が実環境で Python、依存、起動、Host、セッション、SQLite の保持・権限・同時アクセスを確認し、必要な変更とデータ運用を判断する。
4. 品質・リリース責任者が必須確認、未実施の扱い、CI トリガー、Terraform 入出力と CD 定義案を承認する。実行の承認とは区別する。

## 7-2 Terraform 定義案

この節は 7-2 時点の初期 DR に対する定義案と確認記録であり、配備・構成採用の承認ではない。現在の入力・資源名・state 方針は末尾の 7-4 の変更で補正する。`infra/versions.tf` は準備担当の Terraform `1.16.6`、AzureRM `5.10.0` の指定を変更していない。7-1 時点にはなかった変数・リソース・出力を 7-2 で追加した。

### 資源と関係

`infra/main.tf` は AzureRM プロバイダー、リソースグループ1つ、その中の Linux App Service プラン1つ、そのプランを参照する Linux Web App 1つを定義する。場所はリソースグループから他の2資源へ渡す。既存のリソースグループを利用する構成ではなく、新規作成を想定した未承認の案である。アプリ本体の配備、DB、ネットワーク接続先、認証やアクセス制御の資源は定義していない。

`https_only = true` と `public_network_access_enabled = false` は暫定設定である。後者はインターネット公開を許可しない意図であり、これだけでアクセス経路は用意されない。プライベート接続等は仮構成に含めず、接続可能とも安全な運用が成立するともしない。公開条件と必要なアクセス経路が合意されなければ、この案を実行できる構成とは扱わない。

### 入力

`infra/variables.tf` の入力はすべて `string`、必須、既定値なし、null 不可。実値は未設定。以下の役割・指定方法は提案であり、担当者と実値は未決定である。将来は承認済みの実行環境で Terraform の入力変数として渡し、リポジトリには実値入りの変数ファイルを置かない。`.gitignore` は `infra/` 直下の `*.tfvars` と `*.tfvars.json` を除外する。入力には資格情報、秘密鍵、DB 内容を入れない。入力値も state や実行ログに現れ得る。

| 入力 | 意味・制約 | 決定者と指定場所の案 |
| --- | --- | --- |
| `subscription_id` | 対象 Azure サブスクリプションの識別子。認証情報そのものは含めない。 | インフラ責任者が対象を承認し、承認済み実行環境の変数として AzureRM プロバイダーへ指定。認証方式・権限は別途決定。 |
| `resource_group_name` | この案で新規作成するリソースグループ名。 | インフラ責任者が命名規則とともに決定し、Terraform 入力へ指定。 |
| `location` | リソースグループ、プラン、アプリの Azure リージョン。 | インフラ責任者と運用責任者が利用可能性・配置条件を判断し、Terraform 入力へ指定。 |
| `service_plan_name` | Linux App Service プラン名。 | インフラ責任者が決定し、Terraform 入力へ指定。 |

## 7-3 Azure Pipelines 定義案

この節は 7-3 時点の案と確認記録であり、成果物の識別・公開先は末尾の 7-4 で補正する。`pipelines/ci.yml` と `pipelines/cd-draft.yml` は未登録・未実行の案。ソース連携先、ブランチ方針、タスクの利用可能性、承認や配備方法は未決定であり、実行・配備の承認ではない。アプリとインフラの実環境への適合は引き続き未確認。

### CI の開始と準備

- `ci.yml` は暫定案として `main` への push と `main` 宛て PR を対象とし、パスフィルターは `*`、つまり全ファイルを対象とする。ブランチ・ファイル範囲の最終判断は開発・品質責任者。登録すると自動起動し得るので、合意前に登録しない。
- 連携先は Azure Repos か GitHub か未決。GitHub の YAML PR トリガーと Azure Repos のブランチポリシーによるビルド検証は別物で、Azure Repos では YAML の `pr` だけでは PR 検証は設定されない。選定後に連携、対象ブランチ、PR ポリシー・必須チェック、push と重複する実行の扱い、権限、保持期間を YAML 外で設定・確認する。PR の場合は実際に checkout する検証対象コミットと、成果物として採用する条件も確認する。
- 案では Microsoft-hosted `ubuntu-24.04` と Bash、`UsePythonVersion@0` で Python 3.14 を選択し、`.devcontainer/Dockerfile` と同じ `uv==0.13.0` をインストールする。`uv sync --locked` と `uv run --locked` を使い、Python の自動ダウンロードを無効にする。依存取得に公開 PyPI への接続が必要。イメージ・Python・pip・uv・タスクの利用可能性と取得先・信頼性は将来の CI 環境で確認する。タスク名・バージョンをこの文書だけで検証済みとしない。
- checkout した HEAD と `Build.SourceVersion` の一致、追跡済みファイルの差分なしを確認する。ZIP の各入力はさらにそのコミット内のバイト列と比較する。未追跡ファイルは対象版の一部として扱わず、梱包対象にも加えない。CI が検証するのは実際に checkout したコミットであり、現在の未コミット作業版の検証ではない。

### 品質ゲートと成果物

- `AGENTS.md` の `uv run --locked pytest tests/test_portal.py -q`、`uv run --locked ruff check .`、`uv run --locked ruff format --check .`、`uv run --locked mypy` と、`README.md`・`AGENTS.md` の演習版全体回帰 `uv run --locked pytest --ignore=tests/test_reference_patch.py -q` を実行する案。pytest には結果確認用の JUnit XML 出力引数を加えている。
- `tests/test_reference_patch.py` は開始版のコピーに講師用完成例を当てる検品であり、変更済み演習版には適さないため除外する。開始版自体を検証する場合の扱いは別途判断する。演習版の実ブラウザー確認や配備先の検証は CI 案に含まず、未実施として別途判断・記録する。
- pytest の終了コードに加え、両結果の testcase が1件以上で失敗・エラー・スキップがないことを確認する。スキップされた個別テストも失敗扱いとする厳しい案であり、環境依存テストの扱いは品質責任者が決める。全必須確認の成功時だけ、そのジョブ固有の証跡を作る。梱包はその証跡とコミット一致を確認してから行い、ZIP 作成成功後だけ公開条件を満たす。失敗・中断・必須確認の未実行・テスト0件は先に進めない。実際のジョブ条件・キャンセル・スキップ時の挙動は Azure Pipelines 上で未検証。
- `pipelines/package.py` は `.python-version`、`pyproject.toml`、`uv.lock` と `request_portal` の実行用 Python・テンプレート・CSS を個別に列挙し、`build-info.json` にコミット ID と各入力の SHA-256 を入れた `portal.zip` を作る。ファイルの追加・改名時は一覧を見直す。入力のシンボリックリンクは拒否し、Git の対象版と異なる内容は CI の `--verify-git` で拒否する。
- DB・秘密情報・state・仮想環境・キャッシュは列挙しないため ZIP に含めない。ただし列挙されたファイル自体の中に秘密が混入していないことまで自動保証するものではない。内容検査・取得先のアクセス権は別途必要。ZIP 自体の SHA-256 は CI ログに出力する案で、成果物・確認結果とハッシュをどのように保管・照合するかは未決。PR 成果物をそのまま配備可能と判断しない。
