# 申請ポータルの検証

## 用途と入力

申請ポータルの変更や既存動作について、指定された受け入れ条件、回帰、静的確認を検証するときに使う。検証の依頼を受けてから実行する。

依頼から対象の版や変更、作業場所、確認したい範囲・受け入れ条件、使用可能な環境、データの状態と変更可否、実行上の制約を把握する。指定がない項目は正本と実際の状態から確認し、判断に必要な情報が不足する場合は推測せず、何が必要かを明示して依頼者に確認する。確認できない範囲は未実施として報告する。

## 手順

1. 作業対象のリポジトリと作業ディレクトリ、対象版・変更、実行環境を確認する。`AGENTS.md`と`README.md`を読み、適用される制約、受け入れ条件、確認方法を把握する。初期アプリと完成例は期待動作が異なるため、対象版を取り違えない。利用可能なら画面上部や稼働中アプリの`/healthz`も版の確認に用い、情報が食い違う場合は解消を依頼する。参加者の作業中は講師用の完成例の差分を読まない。
2. 検証対象のデータと影響を確認する。テスト用の一時DBと実行中アプリの専用デモDBを区別する。実ブラウザー確認は専用デモDBに申請を追加し状態を変更するため、正本の前提条件と対象DBを確認し、データ変更について依頼者の明示的な許可を得た場合だけ選択する。リセットや初期化は自動で行わない。必要なデータや許可がなければ該当確認を未実施とする。
3. 依頼の範囲と対象版に合う確認を、`AGENTS.md`と`README.md`に記載された手順から選ぶ。変更に対応するテストを優先し、必要に応じて全体テスト、静的確認、任意のブラウザー確認を選択する。未提供のコマンド、手順、参照先、期待結果を作らない。手順や受け入れ条件が不足する場合は、その不足を報告して確認を求める。
4. 前提条件と影響を確認したうえで、許可された確認を適切な作業場所で実行し、コマンド、結果、終了状態、関連する出力を記録する。依存関係が未準備なら、無断でインストール・同期せず未実施とする。依存取得を伴う実行を避けるため、必要に応じて正本に記載されたオフライン実行を使う。設定や環境を無断で変更しない。
5. 失敗時は出力と正本を照合し、対象版や作業場所の不一致、環境・依存の不足、データ・前提条件の不一致、アプリまたはテストの不具合候補を切り分ける。根拠が足りなければ断定せず、不明な点と追加で必要な情報を示す。コードやテストを修正せず、依存追加・設定変更も行わず、実装担当または人へ戻す。
6. 対象版・作業場所・検証範囲、実施した確認と結果、失敗の再現情報と根拠、データへの影響、未実施項目と理由、不足入力、引き継ぎ先や必要な対応を報告する。実行していない確認を成功と扱わない。
